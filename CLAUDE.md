# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Tooling

**Always use Bun** — not Node, npm, or npx. Use `bun`, `bunx`, `bun add`, `bun run`, etc.

## Project Overview

A portfolio web application with a Bun workspace monorepo structure:
- **client/** — SvelteKit 3 frontend (Svelte 5 with runes, Skeleton 5, Tailwind CSS 4, `@sveltejs/adapter-bun`)
- **server/** — Elysia backend API (Bun runtime, MongoDB via Mongoose)
- **common/** — Shared code used by both client and server (the two languages of the site, `common/i18n.ts`: `LOCALES`, `getLocale`, `defineMessages`, `plural`, `intlLocale`, see "Languages" below; `ExperienceType`, `EXPERIENCE_LIMITS` (field lengths and counts the API enforces and the editor validates), domain-name validation, `DEFAULT_GOOGLE_CLIENT_ID`, the résumé import time limits `RESUME_IMPORT_TIMEOUTS`, booking calendar dates: `bookingHorizon`, `splitDateRange`, job postings: `JobPostingInput`, `JOB_LIMITS`, `normalizeJobPosting`, `validateJobPosting` (the rules the API enforces and the job editor shows) and their display labels, account spaces: `USER_MODES`, `RECRUITER_PLANS`, the hiring journey: the step types' manifests (`WorkflowStepManifest`, `stepManifest`, `stepManifests`), `parseWorkflow` (the rules of a journey the API enforces and the owner's editor shows), `newWorkflowStep`, `openWorkflowSteps`, `DEFAULT_WORKFLOW_STEPS`, `WORKFLOW_LIMITS`, `NOTE_STEP_LIMITS`, step suggestions: `STEP_SUGGESTION_LIMITS`, `parseStepSuggestion` (the rules of the "Suggest a step" form, enforced by the API, checked on the text `cleanStepSuggestionText` keeps), the terms of use and age confirmation (`common/models/legal.ts`): `LEGAL_VERSION`, `MINIMUM_AGE`, `AGE_CONFIRMATION_KEYS` / `ageConfirmationKey()` (the key of the confirmation's wording, one per language), `legalMessages` (that wording, and the messages of a refused confirmation such as `legalMessages.staleTerms`), `ConsentInput`, `CONSENT_SOURCES`, `parseConsent` / `consentProblem` (the rule the API enforces), `currentConsent()` (what the client sends once the box is ticked), the address search: `ADDRESS_SEARCH`, `addressSearchText`, `AddressSuggestion`, `OfficePlace` (`common/models/address.ts`), the perfect job: `PERFECT_JOB_CRITERIA`, `parsePerfectJob` (the rules of the criteria a candidate rates, enforced by the API and shown by the admin tab), `scorePerfectJob` (a job posting scored against them out of 100), `JOB_FIELD_CRITERIA` (for every field of a job posting, the criteria that read it))

Bun 1.4.4 is pinned in the root `package.json` (`packageManager`); the text lockfile `bun.lock` uses the isolated linker (each workspace has its own `node_modules`).

## Common Commands

All from the repo root (`bun run --cwd <workspace> <script>` runs a workspace script from there).

### Development
```bash
bun install                       # Install all workspaces (CI and Railway use --frozen-lockfile)
bun run db:up                     # Local MongoDB 7 (as in production) via Docker (compose.yaml), waits until healthy
bun run db:seed                   # Seed owner user + 'louis.gentil' domain (idempotent)
bun run dev                       # API (port 3000, watch) + SvelteKit dev server (port 5173) in parallel
bun run dev:server                # API only
bun run dev:client                # Web only
bun run db:down                   # Stop MongoDB (data kept in a Docker volume)
```

### Build & Run
```bash
bun run build:client              # Build SvelteKit for production (client/build)
bun run start:server              # Start the API without watch mode (production behaviour needs NODE_ENV=production)
bun run start:client              # Start built client (port 4000)
```
`build:client`, `start:server` and `start:client` are the Railway build/start commands: do not rename them, and do not add a root `build`/`start` script. `start:server` sets no `NODE_ENV`: production behaviour (Secure cookie, no `/swagger`) needs `NODE_ENV=production`, which Railpack sets on Railway. Do not add it to the script (the local e2e flow and CI run it over plain http).

### Testing
```bash
TEST_MONGO_URL=mongodb://127.0.0.1:27017/portfolio-test bun run test   # Server tests (need MongoDB) + client unit tests
TEST_MONGO_URL=mongodb://127.0.0.1:27017/portfolio-test bun run --cwd server test   # Server tests only (bun test tests/)
bun run --cwd client test:unit    # Vitest unit tests (single run)
bun run --cwd client test:e2e     # Playwright E2E tests (needs the API running + seeded DB)
```
The e2e tests serve the production build on port 4173 against the API at `PUBLIC_PORTFOLIO_API_URL` (default `http://localhost:3000`), seeded with `bun run --cwd server seed` and `bun run --cwd server seed:e2e` (the `e2e-owner` domain of `client/tests/experiences-owner.test.ts`, the `e2e-import` domain of `client/tests/resume-import.test.ts` and the `e2e-journey` domain of `client/tests/hire-journey.test.ts`, whose journey and perfect job that file alone changes, each with its own owner; the recruiter `e2e.recruiter@example.com`, fixed id, no domain, and the `e2e-applicant` domain of `client/tests/recruiter.test.ts` and `client/tests/jobs-apply.test.ts`, which share that recruiter and only touch the postings named with each test's tag; job API helpers in `client/tests/support/jobs.ts`; the candidate `e2e.candidate@example.com`, fixed id `65e2e0000000000000000002`, no domain, no recruiter space, no acceptance of the terms, of `client/tests/account.test.ts` and the signed-in steps of `client/tests/landing.test.ts`, which answer `PUT /me/consent`, `DELETE /me`, `POST /domain/claim` and `PUT /me/mode` in the browser so it stays that way). `client/tests/legal.test.ts` checks the legal pages (it passes with or without the `LEGAL_*` variables). The owner and recruiter tests sign in without Google (`client/tests/support/owner.ts`: `ownerSession`, `recruiterSession`), with a session JWT signed with the API's secret: run them with `JWT_SECRET` set to it (they are skipped without it); see the e2e job of `.github/workflows/main.yml`. The résumé and job description imports are stubbed in the browser (`page.route`): Claude is never called.
Server tests load `server/.env`; without `TEST_MONGO_URL` they write to its `MONGO_URL` (the dev database). The Eden suite starts the API on `PORT` (default 3000): stop `bun run dev` first or set another `PORT`.
Server tests must pass in any order (CI runs them with `--randomize`; replay a failure with `--seed=N`): each test creates its own data, named with a unique suffix, and removes it, never relying on an earlier test or on seeded data.

## Architecture

### API Communication (Type-Safe)
The client uses **Eden Treaty** (`@elysiajs/eden`) for type-safe API calls. The Elysia server's type (`Portfolio`) is imported directly by the client, so API changes are caught at compile time. See `client/src/services/portfolio.ts`.

### Routing
SvelteKit dynamic routes under `[domain]/`; each portfolio is loaded by domain name via `+layout.server.ts` calling the API. The root (`/`) is the candidate landing page (no longer a redirect: `louis.gentil` is linked as an example). Three route groups: `(site)/` (the landing page, `/legal/*`, `/account`), `(app)/` (recruiter space and public job pages), and `[domain]/`. Since `(site)` owns `/`, link to it with `resolve('/(site)')` (`resolve('/')` does not type-check). The `(site)` layout passes `showSignIn={false}` to `Header.svelte`: no Login button, so no Google script and no One Tap on those pages (the session check and the account menu still run); it ends with `LegalFooter`. `(app)` and `[domain]` end their scrolling page with compact `LegalLinks`, so the legal pages are reachable from every page. `(site)` and `(app)` have no bar of links under the header: the account menu leads from one space to the other and to the job board, the header's logo is a link to the landing page there (`homeLink`; a portfolio's logo is not a link), and `LegalFooter` has the links a signed-out visitor needs ("Browse jobs", "For recruiters"). The light/dark switch (`ThemeToggle.svelte`, one per page) is in the footer on those pages (`LegalFooter`, and next to the compact legal links in `(app)`) and in the rail (`LeftBar.svelte`) on a portfolio; the language switch (`client/src/lib/i18n/LanguageSwitch.svelte`, one per page too) sits next to it in each.

In the three layouts the page scrolls in `main#page`, which is `relative`: keep it. A page's absolutely positioned elements (the hidden input of a Skeleton `Switch`, `sr-only` text, live regions) are then placed in it and scroll with the page; placed in the box around it, focusing one scrolls that box and the whole page goes out of sight (`client/tests/hire-journey.test.ts`, "keeps the page in sight").

New top-level route segments must be added to `RESERVED_DOMAIN_NAMES` (`common/models/domainName.ts`): a domain with that name would be hidden behind the route. Reserved today, among others: `account`, `about`, `contact`, `cookies`, `help`, `legal`, `privacy`, `report`, `signup`, `start`, `terms`.

**Navigation rail.** The portfolio's rail (`client/src/lib/components/LeftBar.svelte`, mounted by `[domain]/+layout.svelte`) is a drawer laid over the page, collapsed to a handle on the left edge: hovering or pressing the handle opens it over the page. On load it shows for 3 s, as a hint, only where it fits in the margin beside the page (`--peek-fits` in its CSS, which its script reads): from 72rem for content centred in at most 56rem (`max-w-4xl`), from 96rem on a page with a `data-page-wide` element (at most 80rem, `max-w-7xl`: the timeline). A page under `[domain]/` keeps its content centred within `max-w-4xl`, or marks what is wider with `data-page-wide`; `client/tests/experiences-owner.test.ts` ("the navigation rail") fails when the rail shows over a page on load. The peek ends early when it stops fitting (a resize, a page that becomes wide), and a collapsed rail's links are hidden with `visibility` in the CSS, not `inert`, so they are out of the tab order before the page hydrates too. Its labels are `Navigation.TriggerText` (12 px: the page's text size does not fit the rail).

### Languages (English and French)
The whole site is in English and French: pages, API answers, the labels and validation messages of portfolio-common. Full rules, French style and glossary: `docs/I18N.md`. The language of a page request is, in order: `?lang=fr|en` in the URL (which also saves it for a year in the `lang` cookie, unless the visitor had already chosen and the link comes from another site: a shared link never replaces a choice; only a page load saves it, never a SvelteKit data request), that cookie, the browser's `Accept-Language`, English (`client/src/hooks.server.ts`, which writes it on `<html lang>`; `hooks.client.ts` reads it there). It is ambient: `getLocale()` of portfolio-common gives it anywhere, both servers keeping it per request with `AsyncLocalStorage` (the client's hook; `server/services/locale.ts`, an Elysia `wrap` that reads the `Accept-Language` the client sends with every API call, `client/src/services/portfolio.ts`); outside a request (unit tests, scripts, module load) it is English. The language switch is a plain link to the current page with `?lang=`, loaded from the server: a page never changes language while it lives, nothing is reactive. Search engines find each language at its own address: English is the address alone, French adds `?lang=fr` (`localeAlternate` of `client/src/lib/i18n/urls.ts`); `client/src/lib/i18n/LocaleLinks.svelte` writes the canonical and `hreflang` links for the job pages and the portfolios (mounted by the `(app)` and `[domain]` layouts), the landing page and the legal pages write their own.

**Every text a person reads is a message**: `{ en, fr }` (two strings, two functions for a text with values, or two arrays) declared with `defineMessages()` in a `*.messages.ts` file next to the code that shows it (`Foo.svelte` → `Foo.messages.ts`, `+page.svelte` → `page.messages.ts`, `services/foo.ts` → `foo.messages.ts`; shared words in `client/src/lib/i18n/common.messages.ts`). Rules to keep: **read a message when it is shown, never at module load** (a module-level constant holding a text is English for everyone: use the messages object, a function or a getter); whole sentences, never glued fragments; plurals through `plural()`; dates and numbers with `intlLocale()`; a sentence with a link in it stays one message with the passage tagged (`'the <terms>terms of use</terms>'`), rendered by `client/src/lib/i18n/Rich.svelte`; English is the reference and the tests read it. Not messages: what people wrote, names, log lines (the API logs in English whatever the visitor's language), texts sent to a model or filed on GitHub, and the API bodies the client compares (`'Domain not found'`...), which stay English constants (`server/protocol.ts` lists them with the client code that matches each; the client then says it in its own words). In the API an error takes a function reading its message (`new BadRequestError(() => m.invalidDate)`, `server/errors.ts`): the answer is in the visitor's language and the error keeps the English for the log. The legal texts stay one component per document and language. **Portfolio is the site's name**, a brand: capitalised, without an article, never translated ("On Portfolio, a skill is not a keyword", « Sur Portfolio… »); the common noun is kept for one person's page ("your portfolio", "a candidate's portfolio"), never "a portfolio" or "portfolios" for the product (`docs/I18N.md`, "Portfolio is a name"). A portfolio's title is its owner's, and the words that head a portfolio without one (`Header.svelte`) are not translated either. `client/src/lib/i18n/i18n.test.ts` and `server/tests/i18n.test.ts` fail when a `*.messages.ts` file lacks a language or its tags differ; TypeScript refuses a message without its French.

### Landing page and onboarding
`routes/(site)/+page.svelte` (rendered on the server, in English or French: title, description, canonical and `hreflang` links (English is `/`, French `/?lang=fr`), Open Graph and `twitter:card` tags, image `client/static/og-image.png` or `og-image-fr.png`, 1200×630), its texts in `routes/(site)/page.messages.ts`: hero ("Your portfolio, your way. No more calls about the wrong job."; "Create your portfolio" scrolls to the onboarding card and focuses its address field; "See an example" → `/louis.gentil/experiences`), "Calls you can stop taking" (three cases the perfect job's criteria stop: too far, underpaid, not remote enough), "First the match, then the call" (the journey's steps, the perfect job), "Make it yours" (themes, title and tagline, list or timeline, skills backed by projects), how it works, FAQ. The page is written for talent and sells the site as their job matchmaker: it saves them the calls about jobs that do not fit, then lets them make the portfolio their own. It does not sell the address (a portfolio is a path of the site, not a domain of its own): keep the copy to what the code does. Two sections have a demo, `client/src/lib/components/landing/DemoVideo.svelte`: a silent recording of the app on a phone (`client/static/landing/demo-style.*`: the experiences page in five themes, as a list and a timeline; `demo-journey.*`: a recruiter whose job fails the commute deal-breaker; `.webm`, `.mp4` and the first frame as `.jpg`), downloaded and played only while it is on screen, with a pause button, and not started by itself with "reduce motion". They are recorded from the real app, in English, with `client/scripts/landing-demos/` (`seed.mjs`: a fictional candidate and recruiter in the local database; `record.mjs`: the steps filmed, how to run it at its top): record them again when what they show changes. The share images carry the hero's headline, read from the page's messages by `client/scripts/og-image/render.mjs`: run it again when the headline changes. The onboarding card is `client/src/lib/components/landing/CandidateOnboarding.svelte`, a stepper of three steps:
- The address field shows from the start, signed out too: a live preview `{host}/{name}` (`portfolioUrlPreview` of `client/src/services/account.ts`) and an availability pill from `checkDomainAvailability` (350 ms debounce, `AbortController`, stale answers dropped; invalid and reserved names answered locally, without a request), backed by the public `GET /domain/:name/availability` (advisory: the claim decides). What was typed before signing in is kept (`suggestDomainName` fills only an empty field).
- **1. Sign in with Google**: the `AgeTermsConsent` checkbox comes first, and Google's script (accounts.google.com) is loaded and its button rendered **only while it is ticked** (the legal pages state this: keep it); the handler checks the box again and calls `login(credential, 'candidate', currentConsent())`. Until `$sessionCheckedStore`, no step is highlighted (no flash of the wrong step).
- **2. Claim your address**: `claimPortfolio(name, consent?)` then `switchMode('candidate')`; the checkbox shows again when the account has not accepted the current terms or the API answers with cause `consent`.
- **3. Add your résumé**: when `GET /experiences/import` is enabled with imports left, "Upload my résumé (PDF)" (with the notice that the PDF goes to Anthropic in the US) → `/<domain>/experiences?import=1`; otherwise "Add my experiences". The experiences page opens the résumé import for `?import=1` once the owner's import status is known (an info toast when it is not available), then removes the parameter with `replaceState`, so a reload or Back does not reopen it.

### Legal pages, consent and account deletion
**Legal pages**: `/legal` (legal notice), `/legal/privacy`, `/legal/terms`, `/legal/cookies`, rendered on the server in the site's language (see "Languages": English or French; `?lang=fr` asks for French and is the French version's canonical address); `(site)/legal/+layout.server.ts` reads the `LEGAL_*` variables (see Environment Variables) and returns `{ publisher }`; each page reads its language with `getLocale()` (the language the page was loaded in, like its header and footer, not that of a later data request). The texts are Svelte components, one per document and language, in `client/src/lib/components/legal/content/` (`LegalNoticeEn.svelte`, `PrivacyFr.svelte`...; English and French share their section ids), shared facts (host, CNIL, Calendar scope, session length, import limit) in `content/facts.ts`, document metadata, helpers and `LOG_RETENTION` (the log retention figure the operator must confirm) in `legalDocuments.ts`, the page shell in `LegalDocument.svelte` ("Last updated" is `LEGAL_VERSION`). Without a publisher name and contact email the pages say "Publisher details are not configured yet." (never a made-up identity). The texts describe what the code does (data kept, processors, cookies and localStorage keys, retention): **when a change alters any of it, update both languages, and when the Terms of use or the Privacy policy change materially, bump `LEGAL_VERSION`** (`common/models/legal.ts`): accounts that accepted an older version see the checkbox again (landing sign-in, claim forms, `/account`) and must accept before their next claim, and a page loaded before the bump gets a 422 on `consent.termsVersion` (`legalMessages.staleTerms`: reload). The cookies page lists the `lang` cookie (the language a visitor chose) next to the session cookie: a new cookie or localStorage key goes there, in both languages.

**Consent record**: `AgeTermsConsent.svelte` (`client/src/lib/components/legal/`) is the shared unticked checkbox (`legalMessages.ageConfirmation`, in the page's language, links to the terms and privacy policy in a new tab so the form keeps what was typed). Once ticked the client sends `currentConsent()` (`{ termsVersion: LEGAL_VERSION, ageConfirmed: true }`); `parseConsent` accepts only that. The API appends an entry to `User.legalAcceptances` (`recordConsent` of `server/services/legal.ts`: one atomic update, never twice for the same version; the key of the wording ticked, `ageConfirmationKey()`, is the request's language's; no birth date, no IP) from `POST /login` (`consent`, source `landing`: checked before the Google token, a 422 creates no account and issues no session), `PUT /me/consent` (source `claim` or `account`, default `account`; `landing` refused) or `POST /domain/claim`. A claim requires the current terms: an account that has not accepted `LEGAL_VERSION` sends `consent` with it or gets a 422 on `consent` (after the 400 of an invalid name, before the 409s); portfolios claimed before the terms existed stay online. `UserDto` has `termsVersion` (the latest acceptance) only when set; `hasAcceptedCurrentTerms` of `client/src/services/account.ts` hides the checkbox for accounts that already accepted. Eden Treaty parses the date-like `termsVersion` (`'2026-11-14'`) into a Date: `readUser` of `client/src/services/authentication.ts` (used by every account request) reads it back as text with `termsVersionText`, which also reads the ISO string a session persisted before. Every claim flow shows it: the landing card, `SpaceChooser.svelte`, `apply/ClaimPortfolioForm.svelte`, `modals/ClaimDomainModal.svelte` (which signs in and claims: the box comes before its Google button, and the consent goes with both `login` and `claimPortfolio`).

**Account page**: `/account` (`routes/(site)/account/+page.svelte`, data read in the browser; signed out: a sign-in hint), reached from the account menu's "Account & privacy": account details, the terms accepted (`components/account/TermsAcceptance.svelte`, `acceptTerms('account')`), the data summary with links to the legal pages, and "Delete your account" (`components/account/DeleteAccountDialog.svelte`: lists what goes, the person types `DELETE`, no closing or navigating while it runs). `deleteAccount()` of `account.ts` calls `DELETE /me` with `{ confirm: 'DELETE' }`, then removes this user's drafts from localStorage (`clearUserBrowserData`: `experienceDraft:<id>:*`, `resumeImport:<id>:*`, `jobDraft:<id>:*`, `jobImportDraft:<id>`), the session and Google auto-select; a 401 keeps the drafts. The API side is `deleteAccount` of `server/services/accountDeletion.ts`: it revokes the Google Calendar grant at Google first (best effort, 5 s, never blocks), then deletes the owned Domains and their Experiences, the Workflow, WorkflowInstances where the account is owner or visitor, JobApplications (to its postings, as candidate, for its domains), AppointmentBookings and AppointmentSchedules, its JobPostings, its Domains, and the User last (an interrupted deletion can run again); Skills and RateLimitCounters stay. It logs one line with the user id and counts (no email, domain or token). A new model with a user reference must be added there (and to `tests/accountDeletion.test.ts`).

### Experiences page
`routes/[domain]/experiences/+page.svelte` lists the experiences (sorted by `sortExperiences` of `client/src/services/experienceDates.ts`) and mounts one editor dialog for the owner: `client/src/lib/components/experience-editor/ExperienceEditor.svelte` (add, edit, delete, unsaved-changes guard, drafts in localStorage; form helpers and validation in `client/src/services/experienceForm.ts`). Card helpers live in `client/src/lib/components/experience-list/`. The filters (`Filters.svelte` there, logic in `client/src/services/filters.ts`) keep the selected skills in the URL (`?skills=kafka&skills=go`). Toasts: `toaster` from `client/src/services/toaster.ts`, whose group is mounted in `routes/[domain]/+layout.svelte`. The owner's résumé import (shown when `GET /experiences/import` says `enabled`) is `client/src/lib/components/resume-import/ResumeImport.svelte`: upload (PDF, 4 MB, checked in the browser), reading (up to ~3 minutes; the browser waits 4.5, longer than the API's own deadlines: `RESUME_IMPORT_TIMEOUTS` in portfolio-common), then a review of the drafts, added one by one through `POST /experiences` (leaving the page is held while they are added); Edit swaps it for the editor (`initialForm` = the draft, with a draft key of its own: what the editor keeps without saving, after a reload or an expired session, goes back into the review; only one dialog can be open, an open one makes the rest of the page inert). Mapping to the editor's form, duplicate detection (same normalised title + company) and the review kept in localStorage per user and domain (a paid extraction survives a reload) are in `client/src/services/resumeImport.ts`. Its e2e test stubs `/experiences/import` in the browser (Claude is never called).

**Floating corner.** The page has no row of its own for visitors: the view switch floats in the bottom right corner (`data-page-dock` in `+page.svelte`, `position: fixed`, first in the DOM so the keyboard reaches it before the list), with next to it "Hire me" (a link to the Hire page) for everyone but the owner, or the owner's "Add experience" on small screens once their toolbar has scrolled away. The owner keeps a heading ("Experiences") and their buttons above the filters. "Hire me" is in the server render (the server cannot know the visitor); in the browser it steps aside as soon as the persisted session says this is the owner's portfolio, before the API confirms it. The corner is always one row, which the page's bottom padding, its scroll padding (`scroll-padding-bottom` on `main#page`: what is scrolled into view stops above the corner) and the toasts' offset count on: the owner's button reads "Add" there (its name stays "Add experience") and the view switch shows icons alone under 360 px.

**Views.** The page has two views of the same experiences, switched with `ViewSwitch.svelte` and kept in the URL like the filters (`?view=timeline`; the list is the default and leaves no parameter): the list of cards, and the timeline (`client/src/lib/components/experience-timeline/Timeline.svelte`, layout in `client/src/services/timeline.ts`). `buildTimeline` counts in months (dates have month precision) and places each experience on a lane and each project on a row inside its experience: what overlaps gets a lane (or row) of its own, jobs take the top lanes, and ending the month the next one starts is a handoff, not an overlap (the first is drawn up to the second's start). An ongoing bar runs to the current month, a project without an end stops with its experience when that one ended (`projectEnd` of `experienceDates.ts`; the cards and the previews show the same months, `formatProjectMonths`), a project without a start begins with its experience (dashed; it covers it unless it has an end), and experiences that cannot be placed (no start of their own and none in their projects) are listed under the chart. The bars are placed with percentages (`placeSpan`) in CSS grid rows, so the server render needs no measuring. Pressing a bar shows that experience's card under the timeline (the owner edits from there).

**Timeline zoom.** The zoom is the width of a month in pixels, state of `Timeline.svelte` (not in the URL). It opens so that the shortest bar drawn is 120 px wide (`defaultMonthWidth`, `TIMELINE_ZOOM` of `timeline.ts`: a 2-month project makes a month 60 px), scrolled so that the latest end of a bar (the current month for an ongoing one, later for one planned further) is near the right edge (not the axis' end: the axis runs to the end of that year, which can be a screen or more of nothing at this zoom), and goes from the whole axis in sight (the scroller's measured width, which that zoom keeps following; a page wider than the axis stretches it) to 240 px a month (`closestMonthWidth`, which also caps the axis at 48,000 px). When the experiences change under it (the owner saves one from the timeline), the zoom stays within the new limits and the month at the left edge stays where it was, also when the save changed the zoom it opens with (a shorter shortest bar). The wheel zooms around the pointer once the pointer was moved over the timeline (a page scrolled under a resting pointer keeps scrolling, also when the timeline left from under it and comes back; at a zoom limit the wheel goes back to the page; a sideways or Shift wheel scrolls the axis; Ctrl + wheel, a trackpad's pinch, always zooms), two fingers pinch it on touch screens (`touch-action: pan-x pan-y` keeps the page's own zoom off it), and the footer has Zoom out / Zoom in buttons. The axis' lines follow the zoom (`timelineTicks`: months, quarters, half-years, years, round numbers of years, at least 72 px between two labels); the server, which cannot measure, draws those of a 320 px page when the axis is shorter than that.

The filters do not behave the same in both views: the list keeps the experiences having a selected skill and tints the projects using it (`Project.svelte`, `data-matched`); the timeline hides nothing, draws those projects bigger and filled, and mutes the rest (`projectMatchesFilters` of `filters.ts`).

**Previews.** Hovering a skill tag (a filter's or a card's), focusing a filter's tag with the keyboard, or tapping a card's tag shows a short card with only the projects using that skill and the time they add up to ("Used in 5 projects (5 years 3 months)": `skillMonths` of `projectPreview.ts` counts the calendar months of those projects as the timeline places them, `projectMonthSpan`, each month once however many of them ran that month, up to the current month; no time when none can be placed), and points at them on the page while it shows (the page's `previewSkill`): the list outlines them in their cards and dims the cards that have none (`Experience.svelte`: `previewSkill`, `muted`; nothing is dimmed when no listed card has the skill, which the filters can hide), the timeline outlines their bars. The card lists them; for a filter's tag on the timeline view it draws them instead as a small timeline of their own, a line of text and a bar each, the earliest first (`skillTimeline` of `projectPreview.ts`, on the axis `timelineAxis` gives; the list again when none of them can be placed: their experiences have no dates). A tag inside an experience's card keeps the list on both views, the card under the timeline included. A bar of the timeline previews its own project or experience. One component for the page, `client/src/lib/components/experience-list/ProjectPreview.svelte`, follows every element with a `data-preview` attribute (`previewTarget` of `client/src/services/projectPreview.ts`: `skill:<key>`, `experience:<id>`, `project:<id>:<index>`), so a tag or a bar only names what it previews. It is a tooltip (`role="tooltip"`, `aria-describedby` on its anchor), not a dialog: it takes no focus, the pointer can move onto it, Escape closes it. It closes when its anchor leaves the screen, except for a tag focused with the keyboard that the page is still scrolling into view: it waits for it until it was placed once (scrolled away afterwards, it closes and the page stops pointing at its projects).

### Hiring journey (workflow)
The Hire page (`routes/[domain]/hire/+page.svelte`) is the portfolio's hiring journey: the steps a recruiter goes through, in the order the owner chose. A journey is a list of steps `{ id, type, config }` (`common/models/workflow.ts`): the id is unique in the journey (a visitor's progress is kept under it), the type names a step type, `config` is that type's settings. The same type can appear more than once unless its manifest sets `max`. Adding a step type, and the rules a step must keep: `docs/WORKFLOW_STEPS.md`.

A step type is defined in three places under the same `type` name, each with a registry (`index.ts`): its manifest in `common/models/workflowSteps/` (`kind` `requirement`|`access`, label and description (getters over the messages of `workflowSteps.messages.ts`), `max`, `needs`: the step types it needs earlier in the journey, `defaultConfig`, `parseConfig`: the settings' rules), its behaviour in the API in `server/services/workflowSteps/` (`ServerStep` of `types.ts`: `evaluate` → the visitor's `status` and `view`, optional `visitorConfig`, `submit`, `describe`; the context gives a step its own `config` and `data`, and `earlier`: the steps before it with what they stored) and its entry in `client/src/lib/components/hire/steps/` (`ClientStep` of `types.ts`: what the visitor sees, the settings form of the owner's editor, and for an `access` type the `goal` the Hire page is titled after). `server/tests/workflows.test.ts` fails when the API's registry and the manifests differ. Four types today: `note` (the owner writes a Markdown note, the visitor reads it and confirms; any number per journey), `job` (the recruiter picks or writes one of their open job descriptions; one per journey; writing a job goes through `/recruiter/jobs/new?journey=<domain>`, back on the Hire page with `?job=<id>`), `job-match` ("Match the perfect job": the job picked on the job step is scored out of 100 against the owner's perfect job, see "Perfect job" below; settings `minScore` and `showDetails`; `failed` under the minimum; needs a `job` step before it; one per journey; nothing to submit, nothing stored), `meeting` (book a meeting, `client/src/lib/components/hire/MeetingBooking.svelte`; one per journey).

The engine is `server/services/workflows.ts`: it owns the order, the locks and the storage, and knows nothing about what a step is. A step is open once every step before it has the status `succeeded` (`openWorkflowSteps`; statuses `pending`|`succeeded`|`failed`; only the job match produces `failed`, which stops the journey like `pending` and shows the step to the visitor as not passed, with what its type says: `failedNote` of its client entry); nothing stores a status, each type's `evaluate` computes it at every read. A stored step whose type no longer has a manifest or a server step is kept and can never succeed: the journey fails closed, it never skips a step. The owner is never stopped by their own journey. The owner edits the steps in the admin tab "Hiring journey" (`client/src/lib/components/admin/WorkflowsTab.svelte`: add, remove, move up and down, each step's settings; `GET`/`PUT /workflow`); `PUT` goes through `parseWorkflow` (at most 12 steps, unique ids, known types, `max`, each type's `parseConfig`, a step's `needs` before it, a requirement step needs an access step after it) and answers 422 naming `steps`, `steps.<index>` or `steps.<index>.config.<field>`. An owner who never saved has `DEFAULT_WORKFLOW_STEPS` (one `meeting` step: the page is the booking page, open to anyone, as before journeys).

Visitors read the journey with `GET /workflow/domains/:domainName` (optional session: the route reads the cookie itself, `server/services/session.ts`): each step with its `status`, the `config` its type's `visitorConfig` returns (settings are private otherwise; what it returns is public, signed in or not) and the `view` its type gives the signed-in visitor about their own progress. Anonymous callers and the owner are `pending` on every step (`own: true` for the owner). A visitor submits a step with `POST /workflow/domains/:domainName/steps/:stepId`, body `{ input }` (session; `submitStep`: 403 on one's own portfolio, 409 when the journey has no such step or its type takes no submission, 403 until the steps before succeeded); the type's `submit` checks `input`, which is untrusted, and returns the data to store. Progress is kept per step id: reordering keeps it, removing a step (or giving its id another type) drops it, a step entering the journey starts from nothing whatever was left under its id, changing a step's settings keeps it. The journey's routes go through `portfolioTextApi` in the client (`client/src/services/portfolio.ts`: Eden Treaty without its date parsing, so a note titled "2027-01-01" stays text).

The API enforces the journey on `available-dates`, `available-slots` and `book` (`openStepOfType` of `server/services/workflows.ts`, for the type `meeting`: 404 when the journey has no meeting step, 401 signed out, 403 until the steps before succeeded). `book` puts in the invitation the lines of each earlier step's `describe` (the job step: title, company, public link from the request's allowed `Origin`), and records the booking on the meeting step (`recordStepData`: only for a visitor who already has progress with this owner, an open booking page keeps no trace of its visitors). Pure client helpers in `client/src/services/workflow.ts`.

The job step offers the recruiter's PDF import too (`JobStep.svelte` mounts `components/job-import/JobImport.svelte` when `GET /jobs/import` says it is available): the draft opens in the job editor with `?journey=<domain>&import=1`, and saving it comes back to the Hire page like a job written by hand.

**Perfect job.** The admin tab "Perfect job" (`client/src/lib/components/admin/PerfectJobTab.svelte`, its controls in `admin/perfect-job/`, form helpers in `client/src/services/perfectJob.ts`; `GET`/`PUT /perfect-job`, owner only) is where the owner says what they look for in a job: thirteen criteria (`PERFECT_JOB_CRITERIA` of `common/models/perfectJob.ts`: job titles, seniority, management, work mode and remote days, location, commute, contracts, working time, RTT days, pay, skills wanted and avoided, travel), each read from the fields a recruiter fills in for a posting, each switched on with an importance from 1 to 5 and an optional deal-breaker flag. `PUT` goes through `parsePerfectJob` (422 naming `criteria` or `criteria.<criterion>.<setting>`; lists cleaned, settings that do not apply and unknown keys dropped). `scorePerfectJob` scores a posting out of 100: each criterion counts for its importance by how well the job matches it (some match partly: pay down to 20% under, remote days, hours, RTT days, the share of the job's skills that are wanted), what the posting does not state counts as not matching, a deal-breaker not matched at all brings the score to 0, and no criterion at all scores 100. The `job-match` step uses it (`server/services/workflowSteps/jobMatch.ts`, which reads the job through `pickedPosting` of the job step). Rules to keep: the perfect job is private (no route returns it to anyone but its owner); a visitor gets their score and the step's minimum, and with the owner's `showDetails` the name of each criterion and its outcome (`match`|`partial`|`miss`, not stated, missed deal-breaker), never what is asked or a criterion's importance; a stored minimum that is not a score reads as 100 (fails closed).

**Criteria and job fields go together.** A candidate can only ask for what a recruiter can say: `JOB_FIELD_CRITERIA` (`common/models/perfectJob.ts`) lists, for every field of a job posting (`JobFieldPath`, the dotted paths of `JobPostingInput`), the criteria that read it, or none on purpose. Adding a field to `JobPostingInput` does not compile until it is listed there and has an input in the job editor (`FIELD_OF_PATH` of `client/src/services/jobPosting.ts`). Adding a criterion means reading it from posting fields declared there: `server/tests/perfectJobScore.test.ts` fails when a criterion is read from no field, or when its scorer reads a field it does not declare (or declares one it does not read); `server/tests/perfectJob.test.ts` that the API stores and returns every field (`tests/completePostings.ts`: postings that state everything), `server/tests/jobExtraction.test.ts` that the PDF import can read every scored field, `client/src/services/tests/jobPosting.test.ts` and `client/tests/recruiter.test.ts` that the editor has and shows an input for each.

**Commute.** The `commute` criterion is the travel time the owner accepts a week (`maxMinutesPerWeek`), from an address they give (`from`; `place`, where the API found it, is set by the API on save whatever the client sends) by the modes they accept (`COMMUTE_MODES`: `transit`, `bike`, `car`, `walk`). A job counts the way there and back for each day at the office (`officeDaysPerWeek`: 5 on site, 5 minus the remote days of a hybrid job, 4 when it does not say, none when fully remote, which always matches): once a week can be further than every day. Over the time accepted it matches less, and not at all 50% over (`COMMUTE_TOLERANCE`). The travel time is not in the posting: the API computes it (`server/services/commute.ts`, `commuteContext`) and passes it to `scorePerfectJob` as its `context`; without one (travel times off, a service that did not answer, the daily cap reached) the criterion is `unavailable`: left out of the score and of the deal-breakers, and shown to the recruiter as "could not be computed". A posting whose address is not found counts as not stated. Off unless `COMMUTE_TIMES=true` (`GET /perfect-job` says `commute: { enabled, modes }`; a new address is refused with 422 while off). Services: the Géoplateforme (IGN, `server/services/geoplateforme.ts`: geocoding, the way by car and on foot; by bike the time is estimated from the distance on foot, `BIKE_METERS_PER_MINUTE`) and, for public transport, the service `COMMUTE_TRANSIT` names (`server/services/transit.ts`): `here` with `HERE_API_KEY`, the HERE Public Transit API (`server/services/hereTransit.ts`: commercial, a free monthly allowance, its key in the URL of each request, which is never logged), or `transitous` with `COMMUTE_CONTACT`, Transitous (`server/services/transitous.ts`; its usage policy is for open-source, non-commercial projects). `GET /perfect-job`'s `commute.transit` and the job match step's `view.transit` name the service in use, which the owner's tab and the Hire page credit. A posting gained `location.address` (street and number, optional) for this; without it the town is used, as when the street is not found. Rules to keep: every answer is cached (`CommuteCache`, keys are HMACs of the question) and every outside call counted against `COMMUTE_DAILY_LIMIT`; a failure is remembered for 10 minutes so a read never waits twice; redirects are never followed; the owner's address and place are never logged, never cached (they live in their `PerfectJob` only) and never reach a recruiter (`server/tests/commute.test.ts`, which fakes the three services); the tests and CI never call them (the e2e test answers `/perfect-job` in the browser).

**Address search.** The two fields that take an address, the commute's `from` (`PerfectJobTab.svelte`) and a posting's office address (`JobEditor.svelte`), are `client/src/lib/components/address/AddressSearch.svelte`: a text field that is also a combobox (ARIA: arrows, Enter, Escape closes the list only), which after a 300 ms pause in typing asks `GET /addresses/search` (`q`, and the `postalCode` and `city` a posting already has, which narrow it; client helpers in `client/src/services/addressSearch.ts`, shared rules `ADDRESS_SEARCH`, `addressSearchText`, `AddressSuggestion` in `common/models/address.ts`) and lists the addresses the Géoplateforme knows. Picking one writes it as the map service does (the owner's field takes the whole label; a posting takes the street, postal code and town in their fields), so the address kept is one the lookup on save or at scoring finds again; what is typed without picking stays as typed. Under a posting's address, `job-editor/OfficePlace.svelte` says where the office is found (`GET /addresses/office`: its street, only its town, which is a warning when a street was typed, or nowhere), looked up when the three fields are left and for the office the editor opened with; an address picked in the list is not asked again. API side: `server/plugins/addresses.ts`, `server/services/addressSearch.ts`. Rules to keep: session required, and the browser never calls the map service itself; both routes answer `enabled: false` and send nothing while `COMMUTE_TIMES` is off (the field is then a plain text field: the component stops asking for the page); what is typed is never logged, cached or stored; searches have their own limits (60 a minute per account, 10,000 a UTC day for the site), not `COMMUTE_DAILY_LIMIT`; an office lookup goes through the commute's cache and daily cap like at scoring (`locateOffice`), at most 40 new ones per account and UTC day; suggestions carry no coordinates. `server/tests/addressSearch.test.ts` fakes the geocoder; the e2e tests answer both routes in the browser (`client/tests/support/addresses.ts`).

**Step suggestions.** Under the step types, the owner's editor shows "Missing a step? Suggest a step" (`client/src/lib/components/admin/StepSuggestion.svelte`, helpers in `client/src/services/stepSuggestion.ts`) when `GET /workflow/step-suggestions` says `enabled`: a form (name, what a recruiter would do, why it would help) that `POST /workflow/step-suggestions` files as an issue labelled `enhancement` in `GITHUB_ISSUES_REPO`, with the operator's `GITHUB_ISSUES_TOKEN` (feature off without it: `enabled: false`, `POST` 404). Logic in `server/services/stepSuggestions.ts`: portfolio owners only (403), portfolio-common's `parseStepSuggestion` (422 naming `name`, `description` or `reason`), 3 per owner and 20 for the site per UTC day (`RateLimitCounter`s, 429 with `Retry-After`), then one `fetch` to `api.github.com` (10 s, `redirect: 'manual'`: never followed); a refusal by GitHub (a redirect included) → 503 and the suggestion is given back, no answer → 503 and it still counts; the requests sent to GitHub are capped too (10 per owner per UTC day, never given back), so a refusing GitHub cannot be retried in a loop. Rules to keep: the owner's text is untrusted and public on GitHub, so it only ever goes inside fenced code blocks whose fence is longer than any run of backticks in it (nothing in it mentions, links or renders), nothing invisible is filed (portfolio-common's `cleanStepSuggestionText`: controls, every `Default_Ignorable_Code_Point` such as zero-width, bidi and tag characters, lone surrogates; the rules are checked on what is left), the title cannot mention or reference (`@ name`, `# 12`, `GH- 12`), and the issue names nobody (the user id and issue number are in the API's log only); the token never reaches a response or a log line (`tests/stepSuggestions.test.ts` fails if it does). The form never signs the page out on a 401 (the journey editor around it would lose its unsaved steps): it says so and keeps the text. The e2e test answers the two routes in the browser: GitHub is never called.

### Authentication Flow
Google OAuth 2.0 → server verifies token → upserts user in MongoDB → records the age and terms confirmation when the body has `consent` (see "Legal pages, consent and account deletion") → issues JWT (7-day, httpOnly cookie). Client tracks auth state via `svelte-persisted-store`. Protected server routes use the `userLogged` Elysia plugin middleware.

### Server Plugin Structure
Elysia routes are organized as plugins in `server/plugins/` (every request runs in its language, `server/services/locale.ts`, see "Languages") — `auth.ts` (`POST /login` with optional `consent`, `GET /isLogged`, `GET /logout`; `clearAuthCookie` is shared with `DELETE /me`), `domain.ts` (`GET /domain/:name`, the public `GET /domain/:name/availability`: `{ name, available, reason?: 'invalid'|'reserved'|'taken' }`, one `Domain.exists`, never the owner, 600 per IP per hour (IPv6 per /64) then 429, logic in `server/services/domainAvailability.ts`; `POST /domain/claim` `{ name, consent? }`, gated on the current terms), `experiences.ts` (POST, PUT and DELETE `/experiences`, owner only), `workflows.ts` (the hiring journey, see above: `GET`/`PUT /workflow`, `GET /workflow/domains/:domainName`, `POST /workflow/domains/:domainName/steps/:stepId`, the same routes for every step type, and `GET`/`POST /workflow/step-suggestions`; engine in `server/services/workflows.ts`, one file per step type in `server/services/workflowSteps/`), `perfectJob.ts` (`GET`/`PUT /perfect-job`: the owner's perfect job, see "Perfect job" above; logic in `server/services/perfectJobs.ts`), `addresses.ts` (`GET /addresses/search`, `GET /addresses/office`: the address search of the forms, see "Address search" above; logic in `server/services/addressSearch.ts`), `appointments.ts` (Google Calendar: admin schedules + public booking; Google calls live in `server/services/googleCalendar.ts`, slots in `server/services/slotComputation.ts`, booking reservations and rate limits in `server/services/appointmentBookings.ts`), `resumeImport.ts` (`GET`/`POST /experiences/import`: Claude Haiku 5.5, `claude-haiku-5-5`, extracts experience drafts from a PDF résumé via `@anthropic-ai/sdk`; nothing is saved, the client saves the accepted drafts through `POST /experiences`; flow and quotas in `server/services/resumeImport.ts`, the Claude calls shared with the job import in `server/services/claudePdfExtraction.ts`, output schema, prompt and normalisation of the untrusted model output in `server/services/resumeExtraction.ts`), `account.ts` (`GET /me`, `PUT /me/mode`: the account's spaces, see "Recruiter space" below; `PUT /me/consent` `{ termsVersion, ageConfirmed: true, source? }` → `{ user }`; `DELETE /me` `{ confirm: 'DELETE' }` (422 otherwise) → 204 with an empty body and the `auth` cookie cleared, see "Legal pages, consent and account deletion"; request schemas in `server/models/elysia/legalRequest.models.ts`), `jobs.ts` (job postings, their applicants and the public job pages; logic and DTOs in `server/services/jobPostings.ts`), `jobImport.ts` (`GET`/`POST /jobs/import`: a job description PDF to a job posting draft, same model and safety rules as the résumé import; flow and plan quota in `server/services/jobImport.ts`, schema, prompt and normalisation in `server/services/jobExtraction.ts`). Custom error classes live in `server/errors.ts`.

### Recruiter space
One Google account can be a candidate (it owns a portfolio domain) and/or a recruiter (job postings); the spaces, labels and plans are `common/models/account.ts`. The recruiter space is free and created by the first `PUT /me/mode` to `recruiter`; `activeMode` only decides what the client shows (the account menu, `client/src/lib/components/AccountMenu.svelte`, and the space chooser after login), the API authorises on what the account has. Client pages live under `client/src/routes/(app)/`: `/recruiter` (private, rendered in the browser only: signed out, `components/recruiter/RecruiterLanding.svelte`, which sells what a portfolio shows of a skill, the projects it was used in and for how long, so a recruiter finds people with exactly the skills they need; keep it to what the code does: there is no search of portfolios by skill; signed in, the dashboard, `/recruiter/jobs/new`, `/recruiter/jobs/:id`, `/recruiter/jobs/:id/edit` with `client/src/lib/components/job-editor/JobEditor.svelte`) and the public `/jobs` and `/jobs/:id` (rendered on the server; applying in `components/apply/ApplyPanel.svelte`). Rules the API keeps: public job responses never name the recruiter (`GET /jobs/:id/application` answers `own: true` to the posting's own recruiter); `GET /jobs` lists the 100 most recently published open postings, at most 10 per recruiter, without descriptions; `PUT /jobs/:id` with the `updatedAt` the editor loaded answers 409 when the posting changed since (the editor sends it). Job descriptions are Markdown rendered without raw HTML (`Markdown.svelte` with `html={false}`), and the job import removes HTML from the drafts.

### Résumé import quotas and limits
Billed to the operator's `ANTHROPIC_API_KEY` (feature off without it, `GET /experiences/import` then says `enabled: false` and `POST` answers 404). Per user: `RESUME_IMPORT_MONTHLY_LIMIT` imports per 30-day window; whole site: `RESUME_IMPORT_DAILY_LIMIT` per UTC day; per user: `RESUME_IMPORT_ATTEMPTS_PER_DAY` attempts per UTC day (never given back); all `RateLimitCounter`s, taken after the file checks (base64, 4 MB → 413, `%PDF-`) and before a free `countTokens` pre-check (over 60,000 input tokens → 422). Over a limit → 429 with `Retry-After`. The paid call is streamed (`messages.stream(...).finalMessage()`), sent once (`maxRetries: 0`) with a 3-minute deadline (`resumeImportTimeouts`). Never give an import back once the paid request may have run the model: it counts once sent (drafts; refusal or `max_tokens` → 422; deadline, lost connection or an error event in the stream → 503 "did not finish"), and only failures before it or an HTTP error status from Anthropic (429/5xx/529, 400/401/403/404: not billed → 503) are given back (`refundRateLimit`). A count_tokens 400 is an operator problem (503, logged at error with the masked API message), not the user's PDF. The SDK client is built with `logLevel: 'warn'` and `openTelemetry: { traces: { contentMode: 'metadata_only' } }` so neither the PDF nor the extracted data reaches logs or spans; `tests/resumeImport.test.ts` fails if the key or the PDF appears in any response or log line. Request bodies: Bun caps them at 6 MB (`app.ts`); every route but the PDF imports (`POST /experiences/import`, `POST /jobs/import`) is capped at 1 MB (413), by `Content-Length` in `onRequest` and by the bytes actually read in a global `onParse` (chunked or repeated-`Content-Length` bodies); a PDF import without a valid session JWT gets 401 in `onRequest`, before its body is read. Traces: `RedactingSpanProcessor` (`instrumentation.ts`) drops bodies, cookies and `Authorization` as spans end, before the `BatchSpanProcessor` queue (the exporter redacts again).

### Metrics and Grafana dashboards
With telemetry on, the API exports two metrics of its own every minute: the request counter and duration histogram of `server/app.ts` (`http.server.requests`, `http.server.request.duration`; attributes `method`, `route`: the matched route pattern, never the raw path, and `status`: the status of the answer, `responseStatus`), and `portfolio.records` (`server/services/siteMetrics.ts`, registered by `index.ts`): one gauge with a `kind` attribute (`SITE_RECORD_KINDS`: portfolios, accounts, recruiters, experiences, job postings, open job postings, job applications, journeys started, upcoming bookings), read from MongoDB at most every 5 minutes, only when metrics are exported, and reporting nothing while MongoDB is away. Counts only: a metric attribute must stay a small fixed set (never a portfolio name, a user id or a path: each value is a series kept in memory and billed). The three Grafana dashboards that read them, with the logs and traces, are in `docs/grafana/` (JSON exported from the stack's Portfolio folder, and what each panel reads: `docs/grafana/README.md`): a new record kind or a renamed route, metric or `OTEL_SERVICE_NAME` means updating them. The site counts no views in the browser: the privacy and cookies pages say "no analytics", so a view counter would change them (and `LEGAL_VERSION`).

### Database Models
Mongoose schemas in `server/models/database/`. Key entities: Domain, User, Experience, Company, Project, Skill, Workflow (an owner's hiring journey: its ordered `steps`, each `{ id, type, config }` as portfolio-common's `parseWorkflow` returned it, `type` without an enum (the registries validate it) and `config` a `Mixed` kept even when `{}`; unique on `user`, collection `hiringworkflows`; the old `workflows` collection is no longer read), WorkflowInstance (a visitor's progress in an owner's journey: `steps`, a map from step id to `{ data, updatedAt }`, what each step's type stored for this visitor; created by the visitor's first submit; unique on `(owner, visitor)`), AppointmentSchedule, AppointmentBooking (slot reservations of `POST /appointments/book`, unique on `(schedule, start)`, released on cancellation; logic in `server/services/appointmentBookings.ts`), RateLimitCounter (Mongo fixed-window counters of `server/services/rateLimit.ts`: booking and availability rate limits, résumé and job import quotas, step suggestions; `takeRateLimit` / `refundRateLimit` / `peekRateLimit`), CommuteCache (what the travel time services answered, `server/services/commute.ts`: `_id` is the kind of answer and an HMAC of the question, `value`, `expiresAt` with a TTL index), PerfectJob (an owner's perfect job: `criteria`, a `Mixed` holding what portfolio-common's `parsePerfectJob` returned, read again through `storedPerfectJob`, which leaves out a criterion that is not one anymore; unique on `user`), JobPosting (a recruiter's job description: the fields of portfolio-common's `JobPostingInput`, normalised and validated there, `publishedAt` the first time it leaves draft), JobApplication (a portfolio owner on a posting's applicant list, `source` `applied` or `added_by_recruiter`, unique on `(job, candidate)`, removed with the posting). The User's `activeMode` (`candidate`|`recruiter`, unset until chosen) and `recruiter` space (`enabledAt`, `plan`, `jobImportsUsed`, created by `enableRecruiterSpace` of `server/services/recruiters.ts`). The User's `legalAcceptances` (unset until the first): append-only history of the terms accepted, `{ version, acceptedAt, ageConfirmationKey, source }` (`source` one of `CONSENT_SOURCES`), written only by `recordConsent` of `server/services/legal.ts`. The User's Google Calendar OAuth tokens (`googleCalendar.refreshToken` / `accessToken`) are `select: false`: only `services/googleCalendar.ts` loads them (`.select('+googleCalendar.refreshToken')`), and `tests/appointments.test.ts` fails if any API response contains one. Every Calendar call goes through `callGoogle` there: a grant Google refuses (`invalid_grant`, `unauthorized_client`, Calendar 401) is cleared (`googleCalendar.revokedAt` set) and becomes a 409 `GoogleCalendarReconnectRequiredError`, not a 500. Disconnecting the calendar, a refused grant and account deletion revoke the grant at Google with `revokeGoogleToken` there (`POST https://oauth2.googleapis.com/revoke`, the token in the form body, never the URL, 5 s, `redirect: 'manual'`, never throws, never logs the token). Elysia request validation schemas use TypeBox in `server/models/elysia/`.

### Client Path Aliases
Node [subpath imports](https://svelte.dev/docs/kit/$lib) in the `imports` field of `client/package.json`, resolved natively by Vite, Vitest and TypeScript: `#lib/*` → `src/lib/*`, `#components/*` → `src/lib/components/*`, `#images/*` → `src/lib/images/*`, `#services` → `src/services/index.ts`, `#services/*` → `src/services/*`. Subpath imports do no extension or `index` lookup, so write the full file name: `#components/Header.svelte`, `#services/authentication.ts`, `#services/stores/index.ts` (`.ts` works because SvelteKit's generated tsconfig sets `allowImportingTsExtensions`). Do not reintroduce the SvelteKit `alias` option or the removed `$lib`: `alias` is deprecated in SvelteKit 3.

## Pull Requests

**Every pull request targets `develop`** (the default branch) and is squash-merged. The only pull requests into `main` are releases, from `develop` itself: the `Release` workflow opens them (see "Deployment"; their description is what the release brings, not the template below) and they are merged with a merge commit (never squash). The `Release guard` workflow fails any other pull request into `main`.

Follow `.github/pull_request_template.md` (Summary, Screenshots, Test plan, Deployment notes).

**Every PR that changes something visible in the UI shows it with screenshots in the PR description**: desktop and mobile (390 px), light and dark when colours are involved, the notable states (loading, empty, error), and before/after when it changes existing UI. Capture them with Playwright against the real app running locally (seeded MongoDB; stub only external services such as Google), and look at each one before posting. A PR without UI changes says "No UI change" under Screenshots.

The GitHub API cannot upload attachments, so screenshots travel through the PR branch: commit the PNGs under `.github/pr-assets/pr-<number>/`, embed them with commit-SHA URLs (`https://github.com/lomithrani/portfolio/blob/<sha>/.github/pr-assets/pr-<number>/<file>.png?raw=true`), then delete the folder in the next commit. PRs are squash-merged, so the images never reach `develop`, while GitHub keeps the PR's commits and the links keep working.

## Deployment

Two stages, each two services from the repo root: **staging** deploys every push to `develop` (`develop.portfolio.gentil.tech`, `develop.api.portfolio.gentil.tech`), **production** every push to `main` (`portfolio.gentil.tech`, `api.portfolio.gentil.tech`). `main` only receives `develop` through a release pull request (base `main`, compare `develop`, titled with the new version: `Release v1.2.0`), merged with **Create a merge commit** so `main` keeps `develop`'s history and the next release merges cleanly; `main` has no commits of its own. Both branches are protected by the rulesets in `.github/rulesets/` (applied on GitHub by importing them: pull request required, required CI checks, no force-push or deletion; squash only into `develop`, merge commit only into `main`; a PR into `develop` must be up to date with it, which `main` cannot require of a release): renaming a CI job means updating them. All services are built with **Railpack** (it reads Bun 1.4.4 from `packageManager` and runs `bun install --frozen-lockfile`): API (start `bun run start:server`, healthcheck `/health`) and web (build `bun run build:client`, start `bun run start:client`, healthcheck `/healthz`). Settings live in the Railway dashboard; there is intentionally no `railway.json` (Config as Code is deprecated and stops being read on 2026-12-01) and no `nixpacks.toml`. Full runbook: `docs/DEPLOYMENT.md`.

Live layout (verified 2026-11-15): Railway project `personal-api`, environment `production` (holding both stages): production web `portfolio web` and API `portfolio api` (branch `main`), staging web `portfolio` and API `portfolio api develop` (branch `develop`), and `MongoDB` (`mongo:7` with a volume), shared by both stages with one database each (production's holds the real data). Each stage has its own `JWT_SECRET`, `ALLOWED_DOMAINS` and `PUBLIC_PORTFOLIO_API_URL`. All app services use the Railpack builder and Root Directory `/` (see the runbook for the full settings).

CI (`.github/workflows/main.yml`) runs on push/PR to `develop` and `main`: quality (lint, svelte-check, server tsc, client build), tests (server + client unit against MongoDB 7, like production, and 9) and Playwright e2e; `.github/workflows/release-guard.yml` ("Only develop merges into main": the source branch, and the next semantic version in the title, one step after the latest `vX.Y.Z` tag) on PRs to `main`; `.github/workflows/release.yml` makes a release when run by hand (`workflow_dispatch`, with patch, minor or major): it opens the release PR from `develop` into `main`, titled with the next version, with auto-merge on (it needs the repository secret `RELEASE_TOKEN`, a maintainer's token: the CI of a pull request opened with the workflow's own token waits for someone to approve it, and a merge made with it starts neither the publication nor the CI on `main` that the production deploy waits for; it only ever asks for auto-merge, never a plain merge, which an admin's token would be let through before the checks), and when a release PR is merged, opened by it or by hand, it publishes the GitHub Release (tag `vX.Y.Z` on the merge commit, generated notes). Its "Tag only" input merges nothing: it publishes `main`'s current commit, for a release merged without its tag. The `develop` branch is the main development branch and the default branch.

## Claude Code Setup (new device)

Everything portable is committed to the repo:
- **CLAUDE.md** (this file) — project instructions
- **.mcp.json** — project MCP servers (railway, github, context7, svelte, chrome-devtools), auto-enabled via `.claude/settings.json`
- **.claude/settings.json** — shared permissions allowlist; local overrides go in `.claude/settings.local.json` (gitignored)
- **.claude/launch.json** — dev server configs for the browser preview (client:5173, server:3000)
- **server/.env.example**, **client/.env.example** — templates for every env var (required ones preset for local dev)
- **compose.yaml** — local MongoDB (`bun run db:up`)

Manual steps on a new device:
1. Install Bun **1.4.4** (the `packageManager` version, see README) and Docker, then run `bun install` at the repo root.
2. Copy the `.env.example` files to `.env` (the defaults work locally; never commit `.env`), then `bun run db:up` and `bun run db:seed`.
3. Export `GITHUB_PERSONAL_ACCESS_TOKEN` in your shell profile — the github MCP server in `.mcp.json` (GitHub's hosted server at `api.githubcopilot.com/mcp/`) sends it as a Bearer token.
4. Install the Railway CLI (`bun add -g --trust @railway/cli`, or `scoop install railway` on Windows, `brew install railway` on macOS) and run `railway login` — the railway MCP server in `.mcp.json` is `railway mcp`, which proxies to Railway's hosted MCP with the CLI's credentials.
5. The other MCP servers (context7, svelte, chrome-devtools) run through `bunx` with pinned major versions; nothing to install.
6. claude.ai connectors (Gmail, Calendar, Railway, etc.) are tied to the Anthropic account, not the repo — re-authorize them in claude.ai connector settings or via `/mcp` in an interactive session if needed.
7. Install Graphify (see below) — the skill files in `.claude/skills/graphify/` are committed, but the CLI must be installed per device.

## Graphify (knowledge graph)

[Graphify](https://github.com/Graphify-Labs/graphify) builds a queryable knowledge graph of the repo (code via local tree-sitter AST parsing, docs via a semantic pass) exposed as a `/graphify` skill in Claude Code.

**Install on a new device** (the CLI is machine-level, the skill is committed):

```bash
winget install astral-sh.uv        # Windows; Mac: brew install uv
uv tool install graphifyy          # NOTE: package is 'graphifyy' (double y) — other graphify* packages on PyPI are typosquats
graphify install --project         # registers the skill into .claude/skills/graphify/ (committed to this repo)
```

**Usage:** type `/graphify .` in Claude Code to (re)build the graph, then prefer `graphify query "<question>"`, `graphify path A B` and `graphify explain "<concept>"` over grepping when exploring the codebase.

**Outputs** land in `graphify-out/` (graph.html, graph.json, GRAPH_REPORT.md) — gitignored, regenerate locally with `/graphify .`.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
