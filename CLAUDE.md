## Common Commands

All from the repo root (`bun run --cwd <workspace> <script>` runs a workspace script from there).

### Development
```bash
bun install                       # Install all workspaces (CI and Railway use --frozen-lockfile)
bun run db:up                     # Local MongoDB 7 (as in production): Docker (compose.yaml) when it runs, else a local mongod (scripts/db.ts)
bun run db:seed                   # Seed owner user + 'louis.gentil' domain + the curated skill catalogue (idempotent)
bun run dev                       # API (port 3000, watch) + SvelteKit dev server (port 5173) in parallel
bun run dev:server                # API only
bun run dev:client                # Web only
bun run db:down                   # Stop MongoDB (data kept in a Docker volume)
```

### Build & Run
```bash
bun run build:client              # Build SvelteKit for production (client/build)
bun run start:server              # Start the API without watch mode (production behaviour needs NODE_ENV=production)
bun run start:client              # Start built client (port 4000)
```
`build:client`, `start:server` and `start:client` are the Railway build/start commands: do not rename them, and do not add a root `build`/`start` script. `start:server` sets no `NODE_ENV`: production behaviour (Secure cookie, no `/swagger`) needs `NODE_ENV=production`, which Railpack sets on Railway. Do not add it to the script (the local e2e flow and CI run it over plain http).

## Architecture

### API Communication (Type-Safe)
The client uses **Eden Treaty** (`@elysiajs/eden`) for type-safe API calls. The Elysia server's type (`Portfolio`) is imported directly by the client, so API changes are caught at compile time. See `client/src/services/portfolio.ts`.

### Routing
SvelteKit dynamic routes under `[domain]/`; each portfolio is loaded by domain name via `+layout.server.ts` calling the API, through `portfolioTextApi` (Eden Treaty without its date parsing, so a title, a subtitle or an experience titled "2027-01-01" stays text), then `reviveExperienceDates` of `client/src/services/experienceDates.ts` makes Dates of the only real dates, the `start` and `end` of each experience and project. The root (`/`) is the candidate landing page (no longer a redirect: `louis.gentil` is linked as an example). Three route groups: `(site)/` (the landing page, `/legal/*`, `/account`), `(app)/` (the recruiter space, with under it the reviewers' page of matching, `/recruiter/reviews`: see "Matching", `/opportunities/[id]`, the private page of a job description shared with a candidate: see "Hiring journey", and `/opportunities`, the candidate's inbox of matching: see "Matching", Screens; there is no job board: `/jobs` answers 410 Gone, `routes/(app)/jobs/+server.ts`, in the visitor's language, and `/jobs/[id]`, where meeting invitations linked a job before, answers 308 to `/opportunities/[id]`, `routes/(app)/jobs/[id]/+server.ts`), and `[domain]/`. Since `(site)` owns `/`, link to it with `resolve('/(site)')` (`resolve('/')` does not type-check). The `(site)` layout passes `showSignIn={false}` to `Header.svelte`: no Login button, so no Google script and no One Tap on those pages (the session check and the account menu still run); it ends with `LegalFooter`. `(app)` and `[domain]` end their scrolling page with compact `LegalLinks`, so the legal pages are reachable from every page. `(site)` and `(app)` have no bar of links under the header: the account menu leads from one space to the other (and, for a portfolio owner while matching is available, to "Opportunities", `/opportunities`, with a badge of their mutual interests not seen yet: see "Matching", Screens), the header's logo is a link to the landing page there (`homeLink`; a portfolio's logo is not a link), and `LegalFooter` has the link a signed-out visitor needs ("For recruiters"). The light/dark switch (`ThemeToggle.svelte`, one per page) is in the footer on those pages (`LegalFooter`, and next to the compact legal links in `(app)`) and in the rail (`LeftBar.svelte`) on a portfolio; the language switch (`client/src/lib/i18n/LanguageSwitch.svelte`, one per page too) sits next to it in each.

In the three layouts the page scrolls in `main#page`, which is `relative`: keep it. A page's absolutely positioned elements (the hidden input of a Skeleton `Switch`, `sr-only` text, live regions) are then placed in it and scroll with the page; placed in the box around it, focusing one scrolls that box and the whole page goes out of sight (`client/tests/hire-journey.test.ts`, "keeps the page in sight").

New top-level route segments must be added to `RESERVED_DOMAIN_NAMES` (`common/models/domainName.ts`): a domain with that name would be hidden behind the route. Their pages must also choose whether search engines list them (see "Search engines" under "Languages"); a page under `[domain]` is never listed. Reserved today, among others: `account`, `about`, `contact`, `cookies`, `help`, `jobs`, `legal`, `opportunities`, `privacy`, `recruiter`, `report`, `signup`, `start`, `terms`. ### Languages (English and French)
The whole site is in English and French: pages, API answers, the labels and validation messages of portfolio-common. Full rules, French style and glossary: `docs/I18N.md`. The language of a page request is, in order: `?lang=fr|en` in the URL (which also saves it for a year in the `lang` cookie, unless the visitor had already chosen and the link comes from another site: a shared link never replaces a choice; only a page load saves it, never a SvelteKit data request), that cookie, the browser's `Accept-Language`, English (`client/src/hooks.server.ts`, which writes it on `<html lang>`; `hooks.client.ts` reads it there). It is ambient: `getLocale()` of portfolio-common gives it anywhere, both servers keeping it per request with `AsyncLocalStorage` (the client's hook; `server/services/locale.ts`, an Elysia `wrap` that reads the `Accept-Language` the client sends with every API call, `client/src/services/portfolio.ts`); outside a request (unit tests, scripts, module load) it is English. The language switch is a plain link to the current page with `?lang=`, loaded from the server: a page never changes language while it lives, nothing is reactive. Search engines find each language of a page they list at its own address: English is the address alone, French adds `?lang=fr` (`localeAlternate` of `client/src/lib/i18n/urls.ts`); `client/src/lib/i18n/LocaleLinks.svelte` writes the canonical and `hreflang` links for the recruiter landing (mounted by the `(app)` layout, which leaves it out on its pages that are not listed), the landing page and the legal pages write their own; a portfolio, which is not listed, has none (see "Search engines").

**Search engines.** Portfolios are not listed by search engines but stay crawlable (`client/src/lib/robots.ts`): every page under `[domain]`, the pages under `/recruiter/jobs`, `/recruiter/reviews`, `/opportunities` and `/account` (`NOINDEX_ROUTES`, matched on whole segments of the route id) answer with `x-robots-tag: noindex, nofollow, noarchive` (`NOINDEX`, portfolio-common's `ROBOTS_NOINDEX`), which `client/src/hooks.server.ts` sets on every answer of those routes, their `__data.json` and error pages included (the 404 of a name nobody claimed is the root `+error.svelte`, without the portfolio's layout: it has the header alone), and carry a robots meta: `client/src/lib/components/PortfolioHead.svelte` in the `[domain]` layout (the robots meta alone, and no canonical or `hreflang`: a page that asks not to be listed names no address to list; the preview tags are the pages' own, see "Link previews"), the `(app)` layout on its routes of `NOINDEX_ROUTES` (written in the browser: the recruiter space and `/opportunities` are not rendered on the server), the account page. The API sends the same `X-Robots-Tag`, the same `ROBOTS_NOINDEX`, on every answer, errors (4xx and 5xx), unmatched 404s and CORS preflights included (Elysia's default headers, `server/app.ts`). `client/static/robots.txt` refuses nothing, on purpose: a crawler must fetch a page to read its noindex, LinkedIn or Slack fetch a shared portfolio to preview it, and a `Disallow` could not name portfolios (top-level paths); in production Cloudflare puts its managed rules above it (`docs/DEPLOYMENT.md`, "Search engines"). The landing page, the legal pages and the recruiter landing stay listed, with their canonical links. **A page added under `[domain]` is not listed, by its route**; a new page elsewhere must choose, under one of `NOINDEX_ROUTES` or among the listed pages of `client/src/lib/robots.test.ts`, which fails until it has (and when the `[domain]` layout stops mounting `PortfolioHead`, or a page under it resets its layout); `client/tests/robots.test.ts` checks the headers, metas and robots.txt of the running site. A text that says who can find a portfolio (the landing FAQ, the privacy policy's `#summary` and `#data-portfolio`) says that search engines are asked not to list it, never that it cannot be found.

**Link previews.** A portfolio's pages a visitor is sent to, the experiences page and the page for recruiters, write the preview a shared link gets (LinkedIn, Slack, messaging apps), in the server's HTML: `client/src/lib/components/OpenGraph.svelte` writes every `og:*` tag, `twitter:card` (`summary_large_image`) and `twitter:image:alt` (X reads the picture's alternative text only there), once (`og:url` is the page's address without its states, with `?lang=fr` in French, `og:locale` its language, `ogLocale` of `client/src/lib/i18n/urls.ts`, which every page writing one uses, `og:site_name` Portfolio). They say only what the page shows anyone (`client/src/services/linkPreview.ts`): the experiences page the name the portfolio is headed with (`portfolioName`: its title, or its address name, as the `[domain]` layout's header, which its `<title>` and description use too) and its tagline (or the page's description), the page for recruiters its title ("Propose a role to <name>", « Proposer un poste à <name> ») and description (the steps of its journey, by their type's label, and about how long they take: `journeyDescription`, from the journey the server rendered; when it leads to a meeting nobody can book, the owner's calendar offering no meeting type, neither the steps nor a duration: only that the owner takes no meeting requests online); the picture is generic, the same for every portfolio, one per kind of page and language (`PREVIEW_IMAGES`: `client/static/og-portfolio.png`, `og-portfolio-fr.png`, `og-hire.png`, `og-hire-fr.png`, 1200×630, as an absolute URL on the page's origin), drawn by `client/scripts/og-image/render.mjs` from `client/src/services/linkPreview.messages.ts`, which also holds their alternative text (`og:image:alt`): render them again when one of those texts changes, and keep them true of every portfolio and every journey (the default one is a meeting alone, open to anyone signed out: the picture of the page for recruiters names no step, counts none, and promises nothing a journey may not ask, a sign-in, a job or a score) and neutral (anyone sees them where the link is posted: they never call the owner a candidate). No picture is made per portfolio. The admin page has no preview. `client/src/lib/robots.test.ts` fails when another page or layout under `[domain]` writes an `og:` or `twitter:` tag, or `PortfolioHead.svelte` does; `client/src/services/tests/linkPreview.test.ts` checks the pictures' files and sizes, and what the picture of the page for recruiters never says; `client/tests/robots.test.ts` checks the rendered tags and the values in the server's HTML a crawler reads (the bare address people copy, sent on to the experiences page, in both languages, and the escaped title and tagline of `e2e-preview`).

**Every text a person reads is a message**: `{ en, fr }` (two strings, two functions for a text with values, or two arrays) declared with `defineMessages()` in a `*.messages.ts` file next to the code that shows it (`Foo.svelte` → `Foo.messages.ts`, `+page.svelte` → `page.messages.ts`, `services/foo.ts` → `foo.messages.ts`; shared words in `client/src/lib/i18n/common.messages.ts`). Rules to keep: **read a message when it is shown, never at module load** (a module-level constant holding a text is English for everyone: use the messages object, a function or a getter); whole sentences, never glued fragments; plurals through `plural()`; dates and numbers with `intlLocale()`; a sentence with a link in it stays one message with the passage tagged (`'the <terms>terms of use</terms>'`), rendered by `client/src/lib/i18n/Rich.svelte`; English is the reference and the tests read it. Not messages: what people wrote, names, log lines (the API logs in English whatever the visitor's language), texts sent to a model or filed on GitHub, and the API bodies the client compares (`'Domain not found'`...), which stay English constants (`server/protocol.ts` lists them with the client code that matches each, those of the recruiter space and of matching mirrored once in `client/src/services/apiBodies.ts`, whose test reads the server's files; the client then says it in its own words). In the API an error takes a function reading its message (`new BadRequestError(() => m.invalidDate)`, `server/errors.ts`): the answer is in the visitor's language and the error keeps the English for the log. The legal texts stay one component per document and language. **Portfolio is the site's name**, a brand: capitalised, without an article, never translated ("On Portfolio, a skill is not a keyword", « Sur Portfolio… »); the common noun is kept for one person's page ("your portfolio", "a candidate's portfolio"), never "a portfolio" or "portfolios" for the product (`docs/I18N.md`, "Portfolio is a name"). A portfolio's title is its owner's, not translated either; a portfolio without one is headed by its address name (`[domain]/+layout.svelte`). `client/src/lib/i18n/i18n.test.ts` and `server/tests/i18n.test.ts` fail when a `*.messages.ts` file lacks a language or its tags differ; TypeScript refuses a message without its French.

### Skill catalogue
The `Skill` collection (`server/models/database/skill.ts`) is the site's skill catalogue, shared by every portfolio and linked to no account: one document per spelling people typed (`displayName`, unique; `names`, the casings of its own name people typed and nothing else; lookups ignore case, `SKILL_NAME_COLLATION`), which the experiences reference (`projects.hardSkills.skill`, `softSkills.skill`). What the catalogue knows of a skill beyond its name is metadata on that document:
- `category`: one of portfolio-common's `SKILL_CATEGORIES` (`language`, `framework`, `infrastructure`, `data`, `security`, `practice`, `tool`, `soft`, `other`, in the order the experiences page lists them; labels `skillCategoryLabel`).
- `parent`: the skill it is part of, strictly "is a flavour, an edition, a distribution or a part of" (`.NET Core` of `.NET`, `Debian` of `Linux`), never skills merely used together or built on one another (`C#` is not part of `.NET`). One level: a skill that has a parent is never a parent itself, never its own parent, no cycle.
- `aliasOf`: this document is another spelling of that skill (`K8s` of `Kubernetes`; an abbreviation, a spelling or a rename, `SKILL_ALIAS_KINDS`). Never chained: it points at a skill without `aliasOf`. An alias has no category or parent of its own, and stays a document of its own, the one the experiences that typed it reference: nothing of it is added to the skill it points at (never a name in that skill's `names`).
- `classification` `{ status, at, attempts, held? }`: `pending` (a skill without one is pending too; `held`: created beyond its account's allowance of new names, kept and never asked until released, see below), `classified` (the classifier recognised it), `rejected` (not a skill: kept, shown to its owner as typed, never suggested, and nothing points at it), `manual` (set by the operator or a seed: the classifier never modifies it, though another skill can point at it). The recognised skills are `SUGGESTABLE_SKILL_STATUSES`: `classified` and `manual`.

**Written as typed, resolved when read.** An experience save calls `Skill.findOrCreate(name)` (`resolveSkills` of `server/models/database/experience.ts`), which returns the document of the spelling typed, created when there is none, never the skill it is another spelling of: experiences are never rewritten. **An edit keeps the spellings stored**: the editor sends back the names the API showed, which for an alias is the canonical name, so `PUT /experiences/:id` reads what the experience stores first (`storedSpellings`: each entry with the skill it is shown as, by the presentation's own rule) and, project by project (`matchStoredProjects`: the stored project of the same name, at the same place first, else the one at its own place), a name the request gives keeps the stored entries that were shown as it (`skillRefs`): the experience typed `K8s` and shown as Kubernetes still references `K8s`, two stored spellings shown as one skill are both kept (the first with the level the request gives, the one that was shown, the others with their own), a skill taken out in the editor takes all its spellings out, and a name typed in a new project stores its own document. Without it any save from the editor would store the document a model's answer chose, and unsetting the alias would no longer bring the spelling back. **An account adds `SKILL_CLASSIFICATION.newNamesPerDay` (200) new names a UTC day to what the classifier is asked** (`server/services/skillAllowance.ts`: the route gives the save `newSkillNamesAllowance(userId)`, the `skill-names:user` counter keyed by a hash of the account, every name counted, never given back; `Skill.namesToQueue` finds in one query the names the catalogue lacks or holds back): a save is never refused, the names beyond are stored and shown to their owner as typed but held back (`findOrCreate(name, { held: true })`: `classification.held`, never sent), and a save within an account's allowance that names one again releases it (the same account another day, or anyone else who types it: nobody keeps a skill from being classified by typing it first); the model file imports no rate limit (the seeds load it without `server/env.ts`). The API presents skills when it answers (`server/services/experiencePresentation.ts`: `presentExperience` on `GET /domain/:name` and on what `POST` and `PUT /experiences` return, read with `EXPERIENCE_POPULATE`): an entry stored under an alias is shown as its canonical skill, each skill once per list (two spellings of one skill are that skill, the first entry kept), with its category and the skill it is part of (portfolio-common's `PresentedSkill`: `_id`, `displayName`, `category?`, `parent?`). The skill an entry itself points at is the owner's, shown as typed whatever its status; the skills that one points at (an alias's target, a parent) are shown only once recognised: the classifier creates them from a model's answer, and a name nobody recognised yet is never put on someone's portfolio in place of, or above, what they typed. Never returned: a skill's `names`, nor where it stands with the classifier. So a wrong answer is undone by changing one document: every experience, saved before or after, shows the spelling typed again.

**Classifier** (`server/services/skillClassifier.ts`). Claude Haiku 5.5, the feedback's model (`SKILL_CLASSIFIER_MODEL` is `CLASSIFIER_MODEL` of `claudePdfExtraction.ts`; its `createClaudeClient`, so `logLevel: 'warn'` and metadata-only traces), says, of the skills still to classify (`classifyPendingSkills`: pending, under `SKILL_CLASSIFICATION.maxAttempts`, 3, tries, not held back, not an alias already, the oldest first), which are skills, how each is spelled, its category, the skill it is part of and the skill it is another spelling of, `SKILL_CLASSIFICATION.batchSize` (40) names a call at most. **A batch is the oldest skills of the whole site, whoever typed them, so one name must not hold the others back**: it holds skills with as many tries as the oldest one (40 never tried; then `retryBatchSizes`: 8 after one try, one alone after two), never more names than `batchCharacters` (1,500) characters (the answer repeats each name: a batch of long names is a few names, far from the deadline and the output limit), and after a call that passed its deadline with several names the next asks half as many (`skillBatchSizing.cap`, in memory, until a call is answered). **What is sent**: the system prompt, the names to classify and up to `SKILL_CLASSIFICATION.knownNames` (500) canonical names the catalogue already has (recognised, not aliases, the oldest first, so parents and aliases reuse them), as two JSON arrays between `<known_skills>` and `<skills>` tags no name can close (`<` is written as its JSON escape), read as data, never as instructions. Nothing else: no account, portfolio, experience or id. A name that cannot be one (portfolio-common's `classifiableSkillName`: `cleanSkillName` refuses a link, an email address (a package with its version, `react@18.2`, is none), several lines, a text over `EXPERIENCE_LIMITS.skillName`; `isSkillNameLike` what does not read like a skill name, over `SKILL_CLASSIFICATION.nameLength`, 60, characters or `nameWords`, 8, words, a host followed by a path, `t.me/jane`, a phone number: a sentence never shares a prompt with other people's names) is rejected there and never sent (when only such names are left, no call is made or counted). One call, sent once (`maxRetries: 0`), 30 s (`skillClassifierTimeouts`), no thinking, `output_config` with `effort: 'low'` and the JSON schema `SKILL_CLASSIFICATION_SCHEMA`, 6,000 output tokens at most. **What is checked**: the answer is untrusted (a model wrote it, from names people typed), so portfolio-common's `parseSkillClassification` checks each item (matched by its `index`, the first for a name decides; `recognised` a boolean; `canonical` kept only when it is the asked name ignoring case, spaces and compatibility forms (`sameSkillSpelling`: `c#` to `C#`, a full-width or circled letter to the plain one, which the catalogue's lookups already take for the same name, so a look-alike typed first is renamed to the plain spelling); `category` one of the list; `parent` and `aliasOf` cleaned and reading like a skill name (`classifiableSkillName`: never a sentence, a host with a path or a phone number), never the skill itself; `aliasOf` only with an `aliasKind`, and then neither parent nor category), and what breaks a rule is dropped for that skill alone, never the batch. `applySkillClassification` writes one result, only onto a skill still pending (every write is conditioned on it: one classified, rejected or set by hand meanwhile is `skipped`): not recognised, it is `rejected` and what pointed at it no longer does; a corrected spelling renames it, unless another document is displayed so, of which it then becomes an alias; an alias points at its target, which gets what pointed at the alias (its own other spellings, the skills that were part of it); a parent is the root of the target's family (one level; `familyRoot` never climbs to a rejected name or an alias, which a `manual` skill may still point at), and what was part of the skill becomes part of that root; in each case what points at the skill is re-pointed first and the skill is stamped last, so a failure in between leaves it to classify (the step is done again, its writes are idempotent), never stamped with a link still pointing at it; a target the catalogue lacks is created pending (classified by a later batch, shown on no portfolio and suggested to nobody until recognised itself); nothing ever points at a rejected name, and a `manual` document is never modified.

**Tries.** A try (`classification.attempts`) is a call Claude answered without settling the skill (no usable item for it, a refusal, an answer cut short or not the JSON asked for, or a result that could not be saved), and the call that settled it. A call that got no answer for reasons that are not the names' (no answer before the deadline, a lost connection, an HTTP error status: 429, 5xx, 529, 400, 401, 403, 404) counts none, so an outage or a refused key never parks skills, not even a name asked alone. From 3 tries a skill is skipped until an operator resets it; since a batch is sized by its tries (above), an answer that cannot be used for 40 names is asked again by 8, then name by name, and only the name at fault gets there.

**Job** (`server/services/skillClassificationJob.ts`, started by `server/index.ts`; its stop is a shutdown step before MongoDB closes, which waits 2 s for a sweep under way). A sweep runs every `SKILL_CLASSIFICATION_INTERVAL_MS` (default 10 minutes), about 15 s after the API starts (what was left to classify), and about 15 s after an experience save resolved a skill still to classify (`onPendingSkillResolved`: `findOrCreate` calls it in the save, it only sets a timer, the saves of the meantime share one sweep, and a sweep a save asked for that found the lease taken or a sweep running runs once it can). A sweep (`sweepSkillClassification`, which never throws) first takes a lease in MongoDB, one sweep started a clock minute for the whole site whichever instance of the API runs it (the `skill-classification:lease` counter, taken again before a batch once its minute is over; it is that minute's, not the sweep's: a call still under way when the minute ends can overlap another instance's next sweep, which asks the same names once more, its results skipped since each skill is written only while pending; one API instance per stage today), then makes at most `SKILL_SWEEP_BATCHES` (5) calls, each counted against `SKILL_CLASSIFICATION_DAILY_LIMIT` (default 100 a UTC day for the site: the `skill-classification:calls` counter, taken right before Claude is called, never when nothing would be sent, never given back), and stops at the first batch not worked through: nothing left, the day's calls used up, or a call that got no answer (the next would ask the same names); after an answer that could not be used it goes on, the next batch being a smaller one or other skills (`narrowed` of the batch's result). Off without `ANTHROPIC_API_KEY`, or with either variable at `0`; the startup line says `"skillClassification":"on (...)"` or why it is off. It logs one line per sweep that had something to do (`Skill classification sweep`: counts, tokens and the estimated cost) and its failures (the status, the error's name, the API's own message with the key masked), never a skill name, the request or the answer. Nothing is classified while someone types, and no request waits for it or fails for it.

**By hand.** An operator corrects the catalogue in MongoDB (`docs/DEPLOYMENT.md`, "Skill catalogue", has the updates): set a skill's `category`, `parent` or `aliasOf` together with `classification.status: 'manual'`, which the classifier never touches again (keep the invariants: one level of families, an alias never chained and without category or parent); unset an `aliasOf` to show a spelling as typed again on every experience; send a skill back to the classifier with `classification: { status: 'pending', attempts: 0 }` (a skipped one, a held one, or a wrong answer to ask again). The seeds apply a curated list the same way (`server/tests/seedSkills.ts`: `seedSkillCatalogue` writes `SEED_SKILLS` as `manual`, idempotent, a manual entry winning over what the classifier wrote; where case variants of a name exist, from before lookups ignored case, the skill is the document spelled as the list spells it and the others become other spellings of it), run by `db:seed` and `seed:e2e` (see "Testing").

**Search** (`GET /skills/search?q=`, `server/plugins/skills.ts`, logic in `server/services/skillSearch.ts`, the editor's typeahead: see "Experiences page", Skills field) → `{ skills }`, each a portfolio-common `SkillSuggestion` (`name`: the canonical spelling picking it adds; `category?`; `parent?`: the canonical spelling of the skill it is part of; `alias?`: the spelling that matched when it is not `name`). Session required (401); 422 on `q` for a text that is empty or longer than `EXPERIENCE_LIMITS.skillName` once cleaned (`skillSearchText`: nothing invisible, so a control character such as a NUL never reaches MongoDB, trimmed, its runs of spaces as one; `canSearchSkill`), in the request's language; 120 a minute per account (`SKILL_SEARCHES_PER_USER`, the `skill-search:user` counter, keyed by a hash of the account; 429 with `Retry-After`). Only recognised skills are found (`SUGGESTABLE_SKILLS`), and everything a suggestion says is recognised too: an alias is found under its own name and suggested as the skill it points at, never when that skill is not recognised, and a parent that is not is left out. The skill the text names first, then those starting with it, then those containing it, each by name, each skill once, `SKILL_SEARCH.results` (8) at most (each way of matching is read only while the answer is not full, 40 documents at most: a short text reads a few documents, never every skill that has the letter). **It reads the recognised skills alone**: the two indexes that start with the status and carry the search's collation (`status_displayName_ci`, `status_names_ci`) serve the exact name and the names starting with the text as ranges (`$gte` the text, `$lt` the text followed by U+FFFF, under the collation, never a regular expression) and bound the "containing" pattern to the recognised skills, so the names still to classify or rejected, which anyone can add by saving experiences, are never read (`skillSearchQueries`: each way's query, which the tests read the plan of). It reads the catalogue as it stands: nothing is classified there, no model is asked.

Rules to keep: only skill names are ever sent to Claude, never an account, a portfolio or an experience; a name is suggested to other accounts, or shown on someone else's portfolio (as the skill theirs is part of or another spelling of), only once recognised, and a rejected one never; nothing typed is logged or kept (the search's `q`, a GET's query string, which traces drop too, `server/instrumentation.ts`; no log line of the classifier or its job holds a skill name: `server/tests/skillSearch.test.ts` and `skillClassifier.test.ts` read the log lines); experiences are never rewritten, and aliases are resolved when read, never when written (`Skill.findOrCreate` stores the spelling typed, and an edit keeps the spellings stored: a new way of saving an experience passes `storedSpellings` too); one name never holds other people's back (a batch sized by tries and characters, a save's new names bounded per account, the search reading recognised skills only); the classifier never modifies a `manual` skill; matching reads none of it (the anonymous card shows the stored skill's own name, the spelling typed, and counts with `experienceMonths.ts` alone, whose existing functions keep their behaviour) and its services import nothing of the classifier (`server/tests/matchFeeds.test.ts` follows their imports and fails on one that reaches `@anthropic-ai/sdk`, which `skillClassifier.ts` imports); tests never call Claude (the job is off in tests, `tests/setup.ts`). The privacy policy describes it (`#data-skills`, the summary, `#legal-bases`, `#recipients`, `#retention`, `#ai`; the deletion dialog's `whatStays` and the policy say that skill names stay in the catalogue, linked to nobody, when an account is deleted): a change to what is sent to Anthropic, suggested to other accounts or kept means updating both languages (and `LEGAL_VERSION` when it is material). Tests: `server/tests/skills.test.ts` (portfolio-common's rules, pure), `skillCatalogue.test.ts` (the model and its indexes, the presentation, what is stored and what an edit from the editor keeps, an account's allowance of new names, the seeds' list), `skillClassifier.test.ts` (the request and what is never sent, the answers, `applySkillClassification`, tries and the batches they size, a sweep, the job, the settings), `skillSearch.test.ts` (the route, and the documents its queries examine), `server/tests/appointments.test.ts` (its route sweep calls the search).

### Hiring journey (workflow)
The Hire page (`routes/[domain]/hire/+page.svelte`) is the portfolio's hiring journey: the steps a recruiter goes through, in the order the owner chose. "Hire page" is its name in the code and the docs only: what people read is neutral, since having a portfolio says nothing about looking for a job (founder's decision): visitors follow "Propose a role" (the floating corner, the rail) to a page titled "Propose a role to <owner>" (« Proposer un poste à <owner> », its `<title>` and heading whatever the journey leads to; what it leads to is said under it, the `goal` of the step type), the owner reads "your page for recruiters" (« votre page recruteurs »), recruiters "a candidate's page for recruiters" (« la page recruteurs d'un candidat »). The `/hire` path stays, so links already shared keep working. The owner's preview starts with a note (every journey, the booking page alone included) with "Change the steps" (the admin's Hiring journey tab, `?tab=workflows`), "Copy your link" (`CopyLink.svelte`, with its caption `opens`: the link copied is the portfolio's, from which "Propose a role" leads here) and "More ways to share" (the admin's Share tab); while nobody can book (`closed`, below) it also says that recruiters cannot book, nor go through the steps, until the calendar is open, with "Open my calendar settings" (`?tab=appointments`). **The page is rendered on the server** from the journey as anyone signed out stands in it (`routes/[domain]/hire/+page.server.ts`: `GET /workflow/domains/:domainName` without a session, the web server never having the API's cookie, so only what the step types' `visitorConfig` makes public; `anonymousJourney` of `client/src/services/workflow.ts` keeps each step's id, type, status and those settings, never a `view` or `own`; 5 s at most): its title and intro, its description (`journeyDescription`: the steps and about how long they take, which a shared link's preview shows too), the steps (the first one open, the rest locked) and **"Before you start"** (`client/src/lib/components/hire/BeforeYouStart.svelte`): what each step asks (its type's `effort.asks`, with the settings visitors get, the job match's minimum), about how many minutes in all (`journeyEffort`), what to have at hand (each `StepNeed` once: a Google account for the steps a visitor submits, the job description and its pay range, or its PDF where import is offered, for the job step; "Nothing to prepare, and no account needed." for a meeting alone, which is booked signed out) and what happens once the step the journey leads to is done (its `goal.next`: the meeting's says that only then does the owner get the recruiter's name and email address). **Nothing promises a meeting nobody can book**: the server also asks the public `GET /appointments/domains/:domainName/schedules` (database only, never Google; it lists nothing while the calendar is not connected, Calendar is off or the journey has no meeting, and only the meeting types with hours: `bookableScheduleFilter` of `server/services/appointmentSchedules.ts`, the predicate the readiness checklist counts with, so the two always agree) and keeps only `bookable` (whether it listed a meeting type, never the types: a phone call's carries the owner's number; null when not known), which the page asks again in the browser unless the server found one, and follows as the booking lists them; the server render's two requests carry `x-portfolio-render: server`, which the dashboards leave out (`docs/grafana/README.md`). When the journey leads to a meeting (`goal.booking`) and `bookable` is false (`closed`), the intro says the owner takes no meeting requests online (and, with steps before the meeting, that they open once the owner does), the steps stay read-only for visitors (none unfolds or takes a submission: a recruiter never writes a job, or passes the score, for a meeting that cannot follow; the owner's preview keeps them), "Before you start" is left out, the description names no step and no duration, and the booking says "Online booking is not available right now." on the first paint. A page without JavaScript reads all of it (and a `<noscript>` line says the steps need it to be gone through, also when the server could not render them); nothing on the first paint reads "Loading": the meeting types hold their place with a placeholder. A placeholder that only scripts replace (the meeting types, a step waiting for the session, the journey the browser loads, the header's account) is hidden where scripts do not run (`noscript:hidden`, Tailwind's `@media (scripting: none)`), so a page without JavaScript shows no empty box. The browser then loads the journey again with the session (a signed-in visitor's own progress, the owner's preview); until it answers, a visitor the kept session names gets no control on the server's steps (they are anyone signed out's: the owner's own note, a step already done). It loads the journey alone, behind a placeholder, when the server could not (the API down or slow: the journey is then `null`), and on every navigation in the browser (a link, a preload on hover, the way back from the job editor: the server load asks the API only for the page's first, server-rendered request, not for `isDataRequest`). A later load that fails: steps the browser loaded for the same visitor stay, with a toast; the server's stay with the failure and "Try again" above them; another account's (after a sign-out) never stay, the server's take their place, else the failure does. A journey is a list of steps `{ id, type, config }` (`common/models/workflow.ts`): the id is unique in the journey (a visitor's progress is kept under it), the type names a step type, `config` is that type's settings. The same type can appear more than once unless its manifest sets `max`. Adding a step type, and the rules a step must keep: `docs/WORKFLOW_STEPS.md`.

A step type is defined in three places under the same `type` name, each with a registry (`index.ts`): its manifest in `common/models/workflowSteps/` (`kind` `requirement`|`access`, label and description (getters over the messages of `workflowSteps.messages.ts`), `max`, `needs`: the step types it needs earlier in the journey, `defaultConfig`, `parseConfig`: the settings' rules), its behaviour in the API in `server/services/workflowSteps/` (`ServerStep` of `types.ts`: `evaluate` → the visitor's `status` and `view`, optional `visitorConfig`, `submit`, `describe`; the context gives a step its own `config` and `data`, `earlier`: the steps before it with what they stored, and `later`: the ids and types of the steps after it) and its entry in `client/src/lib/components/hire/steps/` (`ClientStep` of `types.ts`: what the visitor sees, the settings form of the owner's editor, `effort`: what the step asks, about how many minutes and what to have at hand, for "Before you start" (every type has one: `registry.test.ts`), and for an `access` type the `goal`: what the Hire page says it leads to, under its title, and what happens once it is done). `server/tests/workflows.test.ts` fails when the API's registry and the manifests differ. Four types today: `note` (the owner writes a Markdown note, the visitor reads it and confirms; any number per journey), `job` (the recruiter picks or writes one of their open job descriptions, each listed with its pay and the day it was opened, which tell a duplicate from its source; one per journey; writing a job goes through `/recruiter/jobs/new?journey=<domain>`, back on the Hire page with `?job=<id>`; see "The version shared" below), `job-match` ("Get the job scored": the version of the job shared on the job step is scored out of 100 against the owner's perfect job, see "Perfect job" below; settings `minScore` and `showDetails`; `failed` under the minimum, where the recruiter picks another job, or duplicates this one, whose terms are locked since it was opened, into a new one that comes back to the Hire page, `?duplicate=<id>&journey=<domain>`; needs a `job` step before it; one per journey; nothing to submit, nothing stored), `meeting` (book a meeting, `client/src/lib/components/hire/MeetingBooking.svelte`; one per journey).

The engine is `server/services/workflows.ts`: it owns the order, the locks and the storage, and knows nothing about what a step is. A step is open once every step before it has the status `succeeded` (`openWorkflowSteps`; statuses `pending`|`succeeded`|`failed`; only the job match produces `failed`, which stops the journey like `pending` and shows the step to the visitor as not passed, with what its type says: `failedNote` of its client entry); nothing stores a status, each type's `evaluate` computes it at every read. A stored step whose type no longer has a manifest or a server step is kept and can never succeed: the journey fails closed, it never skips a step. The owner is never stopped by their own journey. The owner edits the steps in the admin tab "Hiring journey" (`client/src/lib/components/admin/WorkflowsTab.svelte`: add, remove, move up and down, each step's settings; `GET`/`PUT /workflow`); `PUT` goes through `parseWorkflow` (at most 12 steps, unique ids, known types, `max`, each type's `parseConfig`, a step's `needs` before it, a requirement step needs an access step after it) and answers 422 naming `steps`, `steps.<index>` or `steps.<index>.config.<field>`. An owner who never saved has `DEFAULT_WORKFLOW_STEPS` (one `meeting` step: the page is the booking page, open to anyone, as before journeys; it stays the default of a new portfolio), and `GET /workflow` says so: `{ steps, saved }`, `saved` false until the first `PUT` (`ownerJourney` of `server/services/workflows.ts`; reading stores nothing).

**Journey templates.** `journeyTemplate(name, { noteTitle?, noteText? })` of portfolio-common (`JOURNEY_TEMPLATES`) builds a whole journey to save through `PUT /workflow` in one click: `gate` is a note, a job step, a job match (`DEFAULT_JOB_MATCH_MIN_SCORE`, `showDetails: true`) and a meeting, under the ids `newWorkflowStep` gives (`note`, `job`, `job-match`, `meeting`), its note asking for the job with its pay range first (`workflowMessages.gateNote`, read when the template is built, so in the owner's language, unless the owner's own title or text are given; once saved it is the owner's text); `open` is `DEFAULT_WORKFLOW_STEPS`. Each template passes `parseWorkflow` as built, in English and French, within `NOTE_STEP_LIMITS` (`client/src/services/tests/workflow.test.ts`, `server/tests/workflows.test.ts`). The admin's Get started tab offers them (see "Admin page and \"Get started\"" under "Landing page and onboarding"); `DEFAULT_WORKFLOW_STEPS` stays the journey of a new portfolio.

Visitors read the journey with `GET /workflow/domains/:domainName` (optional session: the route reads the cookie itself, `server/services/session.ts`): each step with its `status`, the `config` its type's `visitorConfig` returns (settings are private otherwise; what it returns is public, signed in or not) and the `view` its type gives the signed-in visitor about their own progress, and `match` for the recruiter of a mutual interest with the owner (see "After a mutual interest" below). Anonymous callers and the owner are `pending` on every step (`own: true` for the owner). A visitor submits a step with `POST /workflow/domains/:domainName/steps/:stepId`, body `{ input }` (session; `submitStep`: 403 on one's own portfolio, 409 when the journey has no such step or its type takes no submission, 403 until the steps before succeeded); the type's `submit` checks `input`, which is untrusted, and returns the data to store. Progress is kept per step id: reordering keeps it, removing a step (or giving its id another type) drops it, a step entering the journey starts from nothing whatever was left under its id, changing a step's settings keeps it. The journey's routes go through `portfolioTextApi` in the client (`client/src/services/portfolio.ts`: Eden Treaty without its date parsing, so a note titled "2027-01-01" stays text).

The API enforces the journey on `available-dates`, `available-slots` and `book` (`openStepOfType` of `server/services/workflows.ts`, for the type `meeting`: 404 when the journey has no meeting step, 401 signed out, 403 until the steps before succeeded). `book` invites the address the visitor typed and the owner's account email (Google never emails an event's organizer, so the owner only gets the invitation when the schedule's calendar is not their sign-in account's primary one; `GET /appointments/upcoming` leaves the owner out of the guests it lists), puts where a meeting outside Google Meet takes place (the schedule's `locationDetails`: for a phone call the owner's number, which the visitor calls; the booking asks the visitor for none) in the event's `location` and the first line of its description, sets the event's reminders with `bookingReminders` of `server/services/googleCalendar.ts` (an email reminder Google sends the calendar's owner a minute after the booking, at most 4 weeks ahead, which is how the owner of a primary calendar is told, and a pop-up 10 minutes before, since they replace the owner's defaults), and puts in the invitation the lines of each earlier step's `describe` (the job step: the title and company of the version shared, and the link of the job's private page, `opportunityPath(id)` of portfolio-common (`/opportunities/<id>`), on the request's allowed `Origin`), and records the booking on the meeting step (`recordStepData`: only for a visitor who already has progress with this owner, an open booking page keeps no journey progress of its visitors; the slot reservation keeps the account of one who booked signed in, until the slot ends, for `GET /appointments/booked`). Pure client helpers in `client/src/services/workflow.ts`.

**The version shared.** The job step keeps the version of the posting the recruiter shared, not the posting alone: its `data` is `{ job, selectedAt, version, posting }` (`server/services/workflowSteps/job.ts`), `posting` a `JobSnapshot` of portfolio-common (the posting without its status, `toJobSnapshot` of `server/services/jobPostings.ts`: normalised, its pay range brought down to the top it is scored with, never its recruiter), `version` the posting's `updatedAt` then. That version is what the owner reads on the job's private page, what the job match scores (`pickedSnapshot` of the job step) and what the meeting invitation names; an edit of the posting reaches none of them until the recruiter shares it again. Read back, it is checked again (`storedJobSnapshot`: the request schema, `normalizeJobPosting`, `validateJobPosting`): a pick without a valid version (stored before versions were kept, or written by hand) holds nothing, the step is pending again and the recruiter shares the job again (fails closed), and a posting saved under rules it no longer passes is refused at the share (422 on `input.jobId`, which says to correct it or, when what breaks a rule is locked, to duplicate it) rather than stored and never holding. So a rule made tighter (in `jobPostingRequest`, `normalizeJobPosting` or `validateJobPosting`) sends every version kept that breaks it back to pending, and so does it to the mutual interests of matching whose version breaks it (they lead nowhere, see "After a mutual interest"), and to the jobs in matching it breaks (proposed to nobody): count those job steps, mutual interests and jobs before such a release and say so in its deployment notes (`docs/DEPLOYMENT.md`, "Versions of shared jobs (one-off)", has the queries), or rewrite the versions kept. A version never outlives its posting: deleting a posting (`DELETE /jobs/:id`) drops what the job step stored of it on every journey of its recruiter (`dropVisitorProgress` of `server/services/workflows.ts`; the step is to do again). The step's `view.job` has the version's title and company, the posting's status, `sharedAt`, and `outdated` when the posting now differs from the version in anything (`jobSnapshotsDiffer` of portfolio-common: the whole `JobSnapshot`, its status aside; a posting shared was opened, so its terms are locked: in practice its description, or a field no criterion reads, changed); the job step (`JobStep.svelte`) then says when it was shared and offers "Share the new version" (the same submit), and the step's line reads "changed since you shared it". On a journey that scores the job (a job match after the job step, `ctx.later`), each share counts: at most `JOB_STEP_LIMITS.scoredSharesPerDay` (5) per owner and recruiter per UTC day, whatever the job (`takeRateLimit` with `rateLimitKey('job-share', …)`, 429 with `Retry-After`, the client's `pickJobFailure` says it), since each share is a score and many versions would tell the recruiter more of the owner's criteria than a score is meant to; a refusal before the share counts nothing, nor does the job kept picked again unchanged (kept as it is, its date too: the step selects it when it opens), and a journey that scores nothing counts nothing.

**After a mutual interest (matching).** A recruiter can also arrive through matching (Path 2, see "Matching"): the owner, proposed to recruiters as an anonymous card, and the recruiter both interested in one of the recruiter's open jobs (a mutual interest). It leads into the owner's own journey, the same steps, notes and meeting: the engine reads, once per journey and only for a signed-in visitor who is not the owner, the latest mutual interest between the owner (the candidate) and that visitor that leads somewhere now (`activeMutualInterest` of `server/services/mutualInterests.ts`: both interested, the portfolio revealed, not ended, its version reading back (one a rule made tighter since leads nowhere: the recruiter shares a job as anyone does, rather than being held by a job the step cannot show); none while `MATCHING` is off), hands it to the steps (`StepContext.mutualInterest`) and says it to that visitor alone as `match` (`{ _id, job: { _id, title, company? }, matchedAt, changed? }`). The job step holds its job (the version the owner said yes to, `view.matched`, never `outdated`) while the posting is the recruiter's, open, and they accepted the terms in force, and its `submit` answers 409 `JOB_OF_MUTUAL_INTEREST` (`server/protocol.ts`): no other job while it lasts; the job match is frozen (`view.matched`, `frozenAt`: the score, minimum and outcomes then, the outcomes while the owner shows them; succeeded whatever the owner's criteria or minimum became since: their interest is their yes to that job; a frozen score under its minimum, which only a snapshot not written by a mutual interest can hold, is `failed`: it fails closed); notes are still the recruiter's to confirm, and the meeting opens after them; the invitation adds "Mutual interest on Portfolio" (« Intérêt réciproque sur Portfolio ») after the job's line (`mutualInterestLines` of the job step), and the engine adds the three lines itself when the journey has no job step before the meeting (the owner took it out since, or kept the meeting alone), so the invitation always names the job they met over. `handOffToJourney` of `server/services/matches.ts` records it in the visitor's progress when the mutual interest is made (`seedVisitorProgress` of the engine: the job step's share plus `match`, the job match's `{ via: 'mutual_match', match, job, frozenAt }`; on a journey without a job step, the progress alone, so the meeting booked is recorded there), but the steps read the mutual interest itself, so a journey the owner edits since (steps added again under new ids, the job step taken out) still leads there; what a mutual interest stored holds nothing once it no longer leads there (ended, or `MATCHING` off: the job step is `pending`, the recruiter shares a job as anyone does), and is removed when a side ends it or its job does (`dropHandOffs`: it never outlives the match, nor reads as a pick in the feeds). On the page for recruiters (client, 2.13), that recruiter reads `client/src/lib/components/hire/MatchBanner.svelte` above the steps, in place of "Before you start" (`match` read with `journeyMatch` of `client/src/services/workflow.ts`, only from a journey loaded with the session; one that does not read is none): "You're both interested", the job they met over (a link to its page in their recruiter space), since when, edited since (the owner keeps the version they said yes to), that the page holds that job (only while its job step holds it, `mutualInterestJob`; or, without a job step, that the invitation names it), what is left before the meeting (`mutualInterestNext`: what brings back a job the step does not hold now, the posting open again or the terms in force accepted, then the steps not done, or that nothing else is asked; nothing of a meeting nobody can book), what happens once it is booked (the goal's `next`, as "Before you start" says it), and "End it" (asked first, `endRecruiterInterest`, saying that a meeting booked stays booked; a refusal for the terms in force asks for them in the banner, `TermsAcceptance`; the journey is read again, the job step to do as anyone's, and should that read fail, the server's journey and the failure take the place of the steps it held); shown, it is marked seen, each time it shows. A mutual interest the page showed that a later read of the journey no longer has (the owner ended it, its job did, matching was turned off) is said in a toast (`matchEnded` of the page's messages), in place of "Complete the steps first" when a refused request read it again, the focus on the step shown (the page's heading for a meeting alone). The job step (`JobStep.svelte`, `pickedJob(view).matched`) shows that job alone: no list, no "Change" (`reopenLabel` of the step), nothing to share again, `?job=` ignored (`asksForAnotherJob`), and while it does not hold what brings it back (open again, or the terms in force); a share answered 409 `JOB_OF_MUTUAL_INTEREST` (a page loaded before the mutual interest; the client's copy pinned to `server/protocol.ts` by `workflow.test.ts`) is said in a toast and the journey read again (`pickJobFailure`, `matched`), the focus on the step shown once the form went. The job match (`JobMatchStep.svelte`, `jobMatch(view)`'s `matched`, `frozenAt`) says "Score when you were both interested, on <day>", that it no longer changes, with no "Check again" nor duplicate (under its minimum, which fails closed, that ending the mutual interest is the way to share another job). A step a mutual interest holds says what it holds even while a note before it is to do (`stepNote`), and a job it does not hold now what brings it back. `docs/WORKFLOW_STEPS.md`, "A job that comes from matching".

**Perfect job.** The admin tab "Perfect job" (`client/src/lib/components/admin/PerfectJobTab.svelte`, its controls in `admin/perfect-job/`, form helpers in `client/src/services/perfectJob.ts`; `GET`/`PUT /perfect-job`, owner only) is where the owner says what they look for in a job: thirteen criteria (`PERFECT_JOB_CRITERIA` of `common/models/perfectJob.ts`: job titles, seniority, management, work mode and remote days, location, commute, contracts, working time, RTT days, pay, skills wanted and avoided, travel), each read from the fields a recruiter fills in for a posting, each switched on with an importance from 1 to 5 and an optional deal-breaker flag. `PUT` goes through `parsePerfectJob` (422 naming `criteria` or `criteria.<criterion>.<setting>`; lists cleaned, settings that do not apply and unknown keys dropped). `scorePerfectJob` scores a posting out of 100: each criterion counts for its importance by how well the job matches it (some match partly: pay, remote days, hours, RTT days, the share of the job's skills that are wanted), the pay asked is placed in the job's range (`pay.min` to `pay.max`, brought to a year or a day, its top counted at most `JOB_LIMITS.pay.maxRangeRatio` (1.5) times its bottom, in cents as validation counts it (`highestPayMax`), so a range saved wider than that is scored as the range brought down to that cap; `PAY_MATCH`): under the bottom or up to 90% of the way to the top it matches, in the top tenth of the range it scores 0.7, up to 10% over the top 0.3, further over nothing (the only pay outcome that breaks a deal-breaker; a single figure has no top tenth: up to it matches). `validateJobPosting` refuses a top over 1.5 times the bottom (422 on `pay.max`, saying the most it can be: `payRangeTooWideMessage`, amounts written by `formatPayAmount`, the one formatter of pay amounts, which the client's `formatAmount` is), and so does `PUT /jobs/:id/status` when it first opens a posting saved wider before the cap (`requireOpenablePay` of `server/services/jobPostings.ts`: it is narrowed in the editor first; one opened before keeps its status changes), the job editor and the Perfect job tab tell how a candidate's ask is matched (a fixed pay included), and the PDF import never makes a ceiling ("up to 60 k€") the bottom (it leaves the minimum for the recruiter to give) and keeps a range wider than the cap as read, with a warning, for the recruiter to narrow. What the posting does not state counts as not matching, a deal-breaker not matched at all brings the score to 0, and no criterion at all scores 100. The `job-match` step uses it (`server/services/workflowSteps/jobMatch.ts`, which scores the version shared on the job step, read through `pickedSnapshot`). Rules to keep: the perfect job is private (no route returns it to anyone but its owner); a visitor gets their score and the step's minimum, and with the owner's `showDetails` the name of each criterion and its outcome (`match`|`partial`|`miss`, not stated, missed deal-breaker), never what is asked or a criterion's importance; a stored minimum that is not a score reads as 100 (fails closed).

**Criteria and job fields go together.** A candidate can only ask for what a recruiter can say: `JOB_FIELD_CRITERIA` (`common/models/perfectJob.ts`) lists, for every field of a job posting (`JobFieldPath`, the dotted paths of `JobPostingInput`), the criteria that read it, or none on purpose (the description, the company, the benefits...). Adding a field to `JobPostingInput` does not compile until it is listed there and has an input in the job editor (`FIELD_OF_PATH` of `client/src/services/jobPosting.ts`). Adding a criterion means reading it from posting fields declared there: `server/tests/perfectJobScore.test.ts` fails when a criterion is read from no field, or when its scorer reads a field it does not declare (or declares one it does not read); `server/tests/perfectJob.test.ts` that the API stores and returns every field (`tests/completePostings.ts`: postings that state everything), `server/tests/jobExtraction.test.ts` that the PDF import can read every scored field, `client/src/services/tests/jobPosting.test.ts` and `client/tests/recruiter.test.ts` that the editor has and shows an input for each. The fields a criterion reads are also a posting's terms, locked once it is opened (`LOCKED_JOB_FIELDS` is read from this list, see "Recruiter space"): a criterion that reads a new field locks it too.

**Commute.** The `commute` criterion is the travel time the owner accepts a week (`maxMinutesPerWeek`), from an address they give (`from`; `place`, where the API found it, is set by the API on save whatever the client sends) by the modes they accept (`COMMUTE_MODES`: `transit`, `bike`, `car`, `walk`). A job counts the way there and back for each day at the office (`officeDaysPerWeek`: 5 on site, 5 minus the remote days of a hybrid job, 4 when it does not say, none when fully remote, which always matches): once a week can be further than every day. Over the time accepted it matches less, and not at all 50% over (`COMMUTE_TOLERANCE`). The travel time is not in the posting: the API computes it (`server/services/commute.ts`, `commuteContext`) and passes it to `scorePerfectJob` as its `context`; without one (travel times off, a service that did not answer, the daily cap reached) the criterion is `unavailable`: left out of the score and of the deal-breakers, and shown to the recruiter as "could not be computed". A posting whose address is not found counts as not stated. Off unless `COMMUTE_TIMES=true` (`GET /perfect-job` says `commute: { enabled, modes }`; a new address is refused with 422 while off). Services: the Géoplateforme (IGN, `server/services/geoplateforme.ts`: geocoding, the way by car and on foot; by bike the time is estimated from the distance on foot, `BIKE_METERS_PER_MINUTE`) and, for public transport, the service `COMMUTE_TRANSIT` names (`server/services/transit.ts`): `here` with `HERE_API_KEY`, the HERE Public Transit API (`server/services/hereTransit.ts`: commercial, a free monthly allowance, its key in the URL of each request, which is never logged), or `transitous` with `COMMUTE_CONTACT`, Transitous (`server/services/transitous.ts`; its usage policy is for open-source, non-commercial projects). `GET /perfect-job`'s `commute.transit` and the job match step's `view.transit` name the service in use, which the owner's tab and the Hire page credit. A posting gained `location.address` (street and number, optional) for this; without it the town is used, as when the street is not found. Rules to keep: every answer is cached (`CommuteCache`, keys are HMACs of the question; a public transport answer's question names its provider, so a site that changes `COMMUTE_TRANSIT` asks again) and every outside call counted against `COMMUTE_DAILY_LIMIT`; a failure is remembered for 10 minutes so a read never waits twice; redirects are never followed; the owner's address and place are never logged, never cached (they live in their `PerfectJob` only) and never reach a recruiter (`server/tests/commute.test.ts`, which fakes the three services); the tests and CI never call them (the e2e test answers `/perfect-job` in the browser). Two ways to read a travel time: `commuteContext(criterion, location, { mayAsk, use })` asks what is not kept and waits for it (the job match step: one pair, in a request that can wait; `mayAsk`, called before each question that would go out, never for one kept or failed lately, keeps it in by answering false, or by throwing, which is never remembered as the service's failure: the job editor's office lookup counts its account's lookups with it); matching (`use: 'matching'`) scores many pairs in one GET, which Bun cuts after 30 s without data, so it reads with `cachedCommuteContext` (the cache only: no outside call, no wait, nothing counted or written), which answers `{ context, state }`: `known` (the travel time, or an office not found), `none` (no travel time is computed: no place, fully remote, travel times off, no mode the site offers; the commute does not count, which no warm-up changes), `missing` (not kept yet: a warm-up can find it), `failed` (a service did not answer lately: a later warm-up can), `unknowable` (below); `commuteWarmUpPossible(accountId)` (three counters peeked, nothing written, once per read) says whether a warm-up can still ask anything today, so that a feed stops waiting for its `missing` pairs and shows them as unknown. What a pair still needs is asked in the background with `warmCommute({ candidateId, location }, accountId)` (and `warmOffice`, a job's office alone), which reads the candidate's commute from their `PerfectJob` when it runs, and only while their consent to matching is in force (`DiscoveryProfile.enabledAt`, not lapsed): a candidate who withdrew, let it lapse, deleted their account or moved is never asked for from where they were; one warm-up at a time, a pause after one that asked (`commuteWarmUps`), one place for a pair already waiting (keyed by a hash, never logged), at most 100 waiting and 20 for one account (beyond, dropped and said in one warn line a minute at most, with how many: a later read asks again), each request counted against `DISCOVERY_COMMUTE_CALLS` (100 a UTC day for the account whose read wanted it, `discoveryCommuteKey`, a hash of it), against `MATCHING_COMMUTE_SHARE` (0.5) of `COMMUTE_DAILY_LIMIT` for all warm-ups together (the `discovery-commute-site` counter: the rest is kept for the job match steps of journeys, so that matching never leaves a page for recruiters without travel times) and against `COMMUTE_DAILY_LIMIT`, the failure memo kept; fire and forget, they never fail their caller (their chain survives any warm-up, a log line that throws included) and log nothing of the owner. `commuteModes(criterion, location, use)` (`use` required) says by which modes a pair is computed. Matching never asks Transitous, nor reads what it answered (its usage policy is for non-commercial projects): with `COMMUTE_TRANSIT=transitous` it computes by the other modes the owner accepts (`commuteAvailability('matching')`), whose time is then the most the way can take: kept only when the commute matches with it (`commuteMinutesPerWeek` within what the owner accepts), else `unknowable`, as is a commute by public transport alone, never `none`: a feed treats it as unknown (a recruiter feed holds a deal-breaker commute back) instead of leaving it out; the API warns at startup when `MATCHING=true` is set with it (`docs/DEPLOYMENT.md`, "Travel times").

French: « Donner votre avis », the noun is « avis » (`docs/I18N.md`). API: `server/plugins/feedback.ts`: public `GET /feedback` → `{ enabled, classifies }` (`enabled`: `GITHUB_ISSUES_TOKEN` is set; `classifies`: `ANTHROPIC_API_KEY` is set), `POST /feedback` (session) `{ message, context?: { route?, viewport?, theme? } }` → `{ created: true, kind, classified, issueUrl? }` (`issueUrl` only when GitHub's `html_url` is exactly `https://github.com/<GITHUB_ISSUES_REPO>/issues/<number>`); 404 while off, 422 on `message` (portfolio-common's `parseFeedback`; the context is checked by `parseFeedbackContext`, which drops what breaks a rule and never refuses), 429 with `Retry-After`, 503 when GitHub did not take it. Logic in `server/services/feedback.ts`; the GitHub plumbing it shares with the step suggestions (`fenced`, `issueTitleText`, the request itself: 10 s, `redirect: 'manual'`, the token never logged) in `server/services/githubIssues.ts`; the browser's description in `server/services/userAgent.ts` (`describeBrowser`). **Classification**: Claude Haiku 5.5 (`claude-haiku-5-5`, `CLASSIFIER_MODEL` and `createClaudeClient` of `claudePdfExtraction.ts`) sorts the text into `bug`|`feature`|`task` and writes a short neutral English title and summary; the issue gets the repository's issue type (`FEEDBACK_ISSUE_TYPES`: `Bug`, `Feature`, `Task`; when GitHub refuses the type, filed again once with the label `bug`, `enhancement` or `task`: `FEEDBACK_KIND_LABELS`) and the label `feedback`. Without the key, or when Claude fails, refuses, answers junk or times out, it is still filed, as a `Task` titled with the first words of the message, and the body says it was not classified (`classified: false`). Rules to keep: the issue names nobody (no name, email, user id or portfolio address: the user id, the issue number and its kind are in the API's log only); what the person wrote and what Claude derived from it are untrusted and public, so the body has them only inside fenced code blocks longer than any backtick run in them, the title goes through `issueTitleText`, nothing invisible is filed (`cleanIssueText`); the page is its SvelteKit route id (`/[domain]/experiences`, never the real path: `isFeedbackRoute` takes only ids under `/(site)`, `/(app)` or `/[domain]`), the browser and OS come from the closed lists of `userAgent.ts` (family and major version, "Firefox 132 on Windows", never the raw User-Agent), the language is the request's, then the viewport size and the theme. Limits (UTC-day `RateLimitCounter`s, keys from `rateLimitKey`, an HMAC of the user id): 5 per account and 30 for the site, and 10 GitHub-bound attempts per account, never given back (the request filed again without a type takes one too, and is sent only after a 422 that does not name another field); GitHub refusing → 503 and given back to the first two, no answer → 503 and it counts (as for step suggestions); 60 classifications for the site (`FEEDBACK_CLASSIFICATIONS_PER_DAY`), taken when Claude is called and never given back, then filed without one. Claude has 8 s and GitHub 12 s for both its requests (`feedbackTimeouts`): the whole request stays under the 30 s idle timeout Elysia sets on Bun's server (which Bun does not apply to a request with a body, see "Résumé import quotas and limits": keep the budget all the same). `issueTitleText` also breaks `://`, so a title holds no link. Feedback stores nothing in the database. The privacy policy covers it (`#data-feedback`, Anthropic and GitHub as recipients): a change to what is filed or sent means updating both languages (and `LEGAL_VERSION`). The e2e test `client/tests/feedback.test.ts` answers `/feedback` in the browser: neither GitHub nor Claude is called.

### Authentication Flow
Google OAuth 2.0 → server verifies token → upserts user in MongoDB → records the age and terms confirmation when the body has `consent` (see "Legal pages, consent and account deletion") → issues JWT (7-day, httpOnly cookie). Client tracks auth state via `svelte-persisted-store`. Protected server routes use the `userLogged` Elysia plugin middleware.

### Recruiter space
One Google account can be a candidate (it owns a portfolio domain) and/or a recruiter (job postings); the spaces, labels and plans are `common/models/account.ts`. The recruiter space is free and created by the first `PUT /me/mode` to `recruiter` (or `POST /login` with that mode), once the account accepted the terms in force, and its routes need them too (see "Legal pages, consent and account deletion"); `activeMode` only decides what the client shows (the account menu, `client/src/lib/components/AccountMenu.svelte`, and the space chooser after login, which both lead to `/recruiter`, the page that creates the space), the API authorises on what the account has. Client pages live under `client/src/routes/(app)/`: `/recruiter` (private, rendered in the browser only: signed out, `components/recruiter/RecruiterLanding.svelte` (the age and terms box first, then Google's button: see above), which sells what a portfolio shows of a skill, the projects it was used in and for how long; keep it to what the code does: there is no search of portfolios, by skill or otherwise (a recruiter opens the portfolio a candidate shared), and a job is shared on a Hire page only when the candidate's journey has a job step; signed in, the dashboard: first the meetings the account booked on candidates' Hire pages (`components/recruiter/UpcomingMeetings.svelte`, helpers in `client/src/services/bookedMeetings.ts`; `GET /appointments/booked`, `server/services/bookedMeetings.ts`: only bookings made signed in, the soonest 20, each checked with the owner's calendar so one deleted or moved in Google Calendar is dropped like `dropIfStale` drops it, answered from the booking when Google cannot be asked or over 60 checks an hour per account; never the owner's account, calendar or event; a Join link only for `https://meet.google.com/`), then, while matching is on, the mutual interests (`RecruiterMatches.svelte`), then the job descriptions, `/recruiter/jobs/new` (`?duplicate=<id>`: from a copy of that posting, as a new draft, nothing saved until the recruiter creates it), `/recruiter/jobs/:id` (the posting, its status, Edit and Duplicate, and while matching is on its matching panel: no public page, no applicants), `/recruiter/jobs/:id/candidates` (matching: the anonymous cards proposed for the job, one at a time), `/recruiter/jobs/:id/edit` with `client/src/lib/components/job-editor/JobEditor.svelte`). There is no job board and no applying: a job description is never public, its recruiter shows it to a candidate by picking it on the candidate's Hire page (the job step; only an `open` posting can be picked, `OPEN_JOB_STATUS` of portfolio-common), the candidate then reads it on its private page (`/opportunities/:id`, linked from the meeting invitation), and `/jobs` answers 410. A recruiter can also propose an open job to the candidates whose criteria it meets, once a reviewer approved it (matching, Path 2, behind `MATCHING`: the matching panel of the posting's page, the anonymous cards at `/recruiter/jobs/:id/candidates`, the mutual interests on the dashboard, the editor's choice for a job created open; see "Matching", "The recruiter's matching"; the reviewers read it at `/recruiter/reviews`, "The reviewers' page"). Rules the API keeps: a posting's DTO never names the recruiter; deleting a posting deletes the versions of it shared on hiring journeys (see "The version shared"); the top of its pay range is at most `JOB_LIMITS.pay.maxRangeRatio` (1.5) times its bottom (see "Perfect job"); `PUT /jobs/:id` with the `updatedAt` the editor loaded answers 409 when the posting changed since (the editor sends it). **A job's terms are locked once it is opened**: opened is `publishedAt` set (the first time it left draft), whatever its status afterwards (on hold, filled, closed, back to draft); its terms are `LOCKED_JOB_FIELDS` (`common/models/jobTerms.ts`: every path of `JOB_FIELD_CRITERIA` whose list is not empty, so it follows the criteria). `PUT /jobs/:id` on an opened posting answers 409 `JOB_TERMS_LOCKED` (`server/protocol.ts`; `requireUnchangedTerms` of `server/services/jobPostings.ts`, after the 422 of an invalid body and the 409 of an older `updatedAt`) when a locked field differs once normalised (`changedLockedFields`; the editor sends the whole posting, so unchanged terms pass; the top of the pay range is compared as it is scored, at most 1.5 times the bottom, so a range saved wider than that before the cap can come down to that top, and no further); the description, the fields no criterion reads and the status stay editable. An edit of a posting never opened is saved only while it still is not (`$where` `publishedAt: null`): one without `updatedAt` cannot change the terms of a posting opened meanwhile (409 `JOB_CHANGED`). The client: before a posting never opened leaves draft (`locksJobTerms`: the status control of its page, the editor's save, from a Hire page's `?journey=` too) `components/recruiter/OpenJobDialog.svelte` (on `ConfirmDialog.svelte`) asks, with Open / Cancel; the editor of an opened posting shows its terms read-only (`LOCKED_FORM_FIELDS` of `client/src/services/jobPosting.ts`, a lock on each, described to screen readers; every locked control is a read-only text input with `LOCKED_CONTROL_CLASS` of `job-editor/context.ts`, a locked choice showing its label in one, never a disabled one, so it stays in the tab order), a note at the top saying why, which fields (`lockedFieldsText`, also listed by `OpenJobDialog`), that the rest stays editable, and Duplicate (a range saved wider than 1.5 times its bottom shows, and is saved with, the top it is scored with: `openedJobForm`); a draft kept in the browser that changed its terms before the posting was opened (another tab opened it meanwhile) comes back with its other changes in the form, never its terms (`startingJobForms` with `locked`), and the terms it changed are not lost: `droppedTerms` names them in a notice, and they stay with the draft (a save of the rest included) until the recruiter duplicates the posting with them or discards them. Duplicate (the job's page, the note) opens `/recruiter/jobs/new?duplicate=<id>`: the editor starts from `duplicateJobForm` (every field, status draft; a copy of an opened posting from what its editor shows, `openedJobForm`, so a range saved wider than the cap starts at the top it is scored with), its draft under `jobDraft:<userId>:copy:<id>`; a parameter that names no posting of theirs says so, and a copy started of a posting deleted since goes on from a blank form. The editor's 409 for locked terms (and the notice) says so in its own words, with Reload and "Duplicate with my changes" (the form, all of it, held terms included, goes to the copy's draft; a copy kept already with other changes is replaced only once confirmed): nothing typed is lost. The Terms of use say it (`#recruiters`). Job descriptions are Markdown rendered without raw HTML (`Markdown.svelte` with `html={false}`), each link to another site (an http(s) address, or one written without its scheme that a browser reads as one, `//host`, inline or by reference) with the host it leads to beside its text, inside the link (its name says it to a screen reader, with the new tab; left out only for a link whose text is its own address, never for an address with a name before an `@`, which the link drops), opened in a new tab without a referrer (`linkHosts`: `JobDetails.svelte` and `OpportunityCard.svelte`, so a reviewer sees a tracking link behind harmless words, and a candidate matching proposes the job to sees where a link leads before clicking), and the job import removes HTML from the drafts.

### Matching (Path 2)
Mutual matching on open jobs, the second way recruiters meet candidates (the first is the candidate's link): behind the API's `MATCHING` flag (`env.matchingEnabled`, read once in `server/env.ts`; off by default, on on staging, off in production until its legal texts ship). While it is off, `createApp` does not register the matching routes (`matchingRoutes()` of `server/plugins/matches.ts`, the flag read when the app is built; `/swagger` lists none), so each answers the 404 of a route that does not exist whatever the request, signed in or not, its body unread (a body that is not JSON or too large changes nothing); an `onTransform` in front of `userLogged` answers it too, before the session is read, should the flag be turned off once the app is built (tests do). No matching route answers and nothing is proposed (a sign-in records no activity, `POST /jobs` ignores its `matching`, the recruiter routes' postings carry no `matching`, the hiring journeys and the job's private page read no mutual interest) and its metrics are 0: nothing a person sees changes; what a job's changes do to its matches runs whatever the flag (it only ends, drops or deletes matches, or sends an edited job back for review: see below). Built so far: discovery, its API and its portfolio-common rules, the anonymous card and the candidate's preview of it, the travel times its feeds read (from the cache only, the rest asked in the background: see "Commute" under "Hiring journey"), the recruiter's switch that puts a job into matching, the review of each such job by the operator's reviewers, the Match model with what a job's changes do to it, the feeds (the jobs proposed to a candidate, the anonymous cards proposed for a recruiter's job), and the decisions of each side, the mutual interest they make and where it leads (the candidate's own hiring journey), the building blocks of its screens ("Screens" below), the candidate's screens (discovery's settings in the Perfect job tab, their opportunities and the actions of a job's private page, the account menu's badge), the recruiter's (a job's matching panel, the anonymous cards proposed for it, their mutual interests, the job editor's choice, the account menu's mark, the candidate's page for recruiters after a mutual interest: its banner, the job step holding the job, the score frozen, the meeting), and the reviewers' (`/recruiter/reviews`: the jobs waiting for a review, approved or rejected); its legal texts and the landing's copy later. The candidate screens read a 404 from `GET /discovery` or `GET /me/notifications` as matching being off, and show nothing of it (no answer says so otherwise); the recruiter screens, the absence of `matching` on their postings (and a 404 of the routes they call); the reviewers' page, a 404 of `GET /matching/reviews` as a 403, "not available".

**Discovery.** A candidate asks to be proposed to recruiters as an anonymous card (opt-in), and stops at once. Routes (`server/plugins/matches.ts`, logic in `server/services/discovery.ts`; the session's own account, they take no account or portfolio): `GET /discovery` → `{ state, enabledAt, consentExpiresAt, missing, minScore, card }` (reads only; `minScore`: the journey's job match minimum, the one bar a job is held to), `PUT /discovery` `{ card: { headline?, hiddenExperiences } }` (what the anonymous card shows, on or off: portfolio-common's `parseDiscoveryCard`, 422 on `card...`; a headline of `DISCOVERY_LIMITS.headline` characters, folded by NFKC (`jane＠acme.fr` is an email address) and cleaned of what cannot be seen, without a link (a scheme, `www.`, a host followed by a path such as `linkedin.com/in/jane` or `behance.net/jane`, or a host alone under a domain people take for their own pages, `janedoe.dev`, `jane.io`; technologies written like a host are no link: `Node.js/React`, `ASP.NET/Azure`, `ML.NET`, `Socket.IO`), an email address or a phone number; then 422 on `card.headline` (`matchingMessages.card.headlineIdentity`) for one that says who the candidate is, by the rule the card keeps all its texts to (`identifiesCandidate` of `server/services/candidateCard.ts`, see "Anonymous card"): their name, their portfolio's title or address name, a company or a place of their experiences (a hidden one's too), a place of their perfect job, whole, whatever the case or accents, or a page of the site (an `ALLOWED_DOMAINS` host followed by `/`), the card being anonymous until both sides are interested; only experiences of the candidate's own portfolio stay hidden), `POST /discovery/consent` `{ consent: { termsVersion, adultConfirmed: true } }` (the opt-in: 422 on `consent...` (`parseDiscoveryConsent`), then 422 on `requirements.<requirement>`, the first missing, in the request's language (`discoveryRequirementMessage`), then 429 within `DISCOVERY_REJOIN_DAYS` (7) of the withdrawal that last turned it off (with `Retry-After`: a withdrawal drops recruiters' passes on the candidate with their other decisions, so turning discovery on again at once would put them back before every recruiter who passed them, and tell them which jobs those were; a withdrawal of an account that was not on holds nothing back; checked again in the write that records the consent, so a withdrawal asked just before the opt-in that turns discovery off while it runs holds it back too), then 429 over 10 a day per account (`DISCOVERY_GRANTS_PER_DAY`), which an opt-in refused before never uses), `DELETE /discovery/consent` (the withdrawal: at once, whatever is missing, never limited).
- **Requirements** (`DISCOVERY_REQUIREMENTS`, in order): a portfolio; the terms in force accepted; `DISCOVERY_MIN_CRITERIA` (3) criteria rated, the pay among them; the gate journey (a job step, then a job match, then a meeting, whatever comes between them: a mutual interest will go on into it, with its one minimum); Google Calendar connected, and not refused since, on a site that takes it; a meeting type recruiters can book (`bookableScheduleFilter`); signed in within `DISCOVERY_INACTIVITY_DAYS` (180) days. They are portfolio-common's `discoveryRequirements(readiness, { termsAccepted, lastActiveAt })`, read from `candidateReadiness` (see "Candidate readiness": never a second readiness), computed by the API (the screens show them) and checked again at the opt-in.
- **States** (`discoveryState`): `off` (never on, or withdrawn), `on` (proposed), `paused` (on, but a requirement went missing since: proposed to nobody, nothing written, on again once it is back), `lapsed` (the consent is `DISCOVERY_CONSENT_MONTHS` (24) old: the candidate gives it again, which records a new one). A candidate on can confirm their consent again in its last `DISCOVERY_CONSENT_RENEWAL_DAYS` (30) days (`discoveryConsentRenewable`: `POST /discovery/consent` records a new one, counted in the day's opt-ins, from which the 24 months count again); earlier, an opt-in of a candidate on records nothing, so nobody drops out on the day their consent lapses for want of a way to confirm it. Activity is `lastActiveAt`, written at sign-in (`touchDiscovery` from `POST /login`: once a day at most, for a candidate who is on, never failing the sign-in; a session lasts 7 days, so whatever a candidate does is within 7 days of one), at the opt-in, when the card is saved and when they read the jobs proposed to them (`touchDiscovery` again).
- **Consent**: 18 or over (`MINIMUM_DISCOVERY_AGE`), a box of its own apart from the 16+ terms confirmation, worded `legalMessages.discoveryConsent`: what is matched (the candidate's criteria, both ways: the open jobs that meet them are shown to the candidate, the card is proposed to their recruiters), everything the card shows before both sides are interested, field by field (`CANDIDATE_CARD_FIELDS`: the headline, the role titles with the time in each and whether each is held now, the total time of professional experience, the skills and how long each was used, and, when the journey's job match shows details, the outcome of each criterion but the commute and the location), that a job's recruiter sees the candidate's interest in it, that the name and portfolio come only with a mutual interest, and how to stop: a card that shows more needs a new wording. Its key per language `DISCOVERY_CONSENT_KEYS` stands for that exact wording (a new key when it changes, which `server/tests/matching.test.ts` pins, keeping the older keys' wordings: `discovery-18-v3` today, which also says that a job's recruiter sees the candidate's interest in it (the `interested` of their feed); `v2` did not, `v1` named neither the total nor whether a role is held now). Appended to the profile's `consents`, never edited: `granted` with the terms version and the key of the wording read (the request's language), `withdrawn`; recorded once, atomically (two opt-ins at once append one entry, one already on records nothing). A withdrawal unsets `enabledAt` (out of every feed at once), appends `withdrawn` and drops the decisions about the candidate that no mutual interest came of (`discoveryWithdrawal.dropPendingDecisions`: its matches without a mutual interest, see "Matches" below). Every withdrawal, of an account never on too, first keeps when it was asked (`withdrawnAt`, `$max`), and an opt-in records nothing where a withdrawal was asked after it started: the later request wins whatever order their writes land in, so a candidate who turns discovery on then off at once is off.
- **Anonymous card** (`server/services/candidateCard.ts`): what a recruiter reads of a candidate before both sides are interested, built on the server only from what may be shown, as the consent words it: `{ headline, experienceMonths, roles, skills }`. The headline they wrote; their months of professional experience in all (`professionalMonths`); their professional roles, the most recent first as the experiences page orders them (`sortExperiences`), `MATCHING_LIMITS.roles` (8) at most, each `{ title, months, current }` (the months spent so far, both ends included, up to the current month: a role ending later is `current`; `null` for a role without dates; one not started yet is not a role); their technical skills, the most used first (by months, those without a time after, then by projects, then by name; spellings the card writes alike are one skill), `MATCHING_LIMITS.skills` (15) at most, each `{ name, months }`, the months as the experiences page's skill preview counts them (`skillUsesByKey`: equal to `skillMonths` with `projectUsesSkill`, on technical and soft entries alike), `null` when no project using it can be placed (their experiences have no dates: the page shows no time either), and a skill only planned (every project using it starts later, a role not started yet's included) is none of the card's. Never a name, the portfolio's title, subtitle or address, the email, a company, a place, a project's name or summary, a date, an id, the perfect job, a score or a travel time: a project's name and summary are not even loaded. An experience the candidate hides counts for nothing on it (not its role, not its months, not its projects' skills). A text that says who the candidate is (portfolio-common's `cardIdentityNames` and `cardTextIdentifies`, names of three letters or more: their name, the account's given name and surname in both orders and the surname alone, and, since a Google sign-in keeps no name, the local part of their email address in both orders and each of its words (`marchetti` of `zoe.marchetti92@…`, but words that stand for nobody, `contact`, `dev`, `data`...), their portfolio's title or address name in both orders (`gentil louis`; never a word of them alone: an address may be `data-engineer`), a company of their experiences, also without its legal form or what companies add (Globex for Globex SAS or Globex Corporation; Data Group stays whole, `data` names nobody), a place of their experiences or a part of one (Lyon of `Lyon, France`), a place of their perfect job (its towns, the town of the commute's place, never its street; in memory only, never logged or answered), an acronym of two capitals of a company or a place only as written (EY in `Senior consultant EY`; `Chef de projet` does not name Berlin, DE), a link, an email address, a phone number; or a page of the site; words that stand for no company or place, Freelance, Remote, left out) is left out: a role with such a title, a skill with such a name, a headline that came to name them since it was saved (a company added). Beside the card, for a recruiter's job, only the outcomes the journey's job match already shows on the page for recruiters (`showDetails`), never the commute or the places (`CARD_WITHHELD_CRITERIA`, `cardOutcomes`: no score, no deal-breaker flag; the feeds use it). - **Jobs in matching** (`server/services/jobMatching.ts`): a recruiter proposes one of their jobs to the candidates whose criteria it meets with `PUT /jobs/:id/matching` `{ enabled }` (recruiter routes' rules: their own posting, else 404; a recruiter space, else 403; the terms in force, else 422 on `consent`), or `matching: true` on `POST /jobs` (ignored while `MATCHING` is off, as if not sent; checked before anything is written; only for a posting created open, 422 on `matching` otherwise: a draft is put into matching with `PUT /jobs/:id/matching` once it is opened, so the job editor's choice (see "The recruiter's matching") is offered for a job created open, or made after the opening, never stored on a draft). On: only an open posting (409 `MATCHING_NEEDS_OPEN_JOB` of `server/protocol.ts`), one that names its company (decision of the founder: candidates decide before they know who the recruiter is) and has a description (`matchingJobProblem`, 422 on `company` or `description`), whose stored version passes the rules a posting is saved under today (`requireCurrentRules`: a posting opened before the 1.5 times pay cap with a wider range gets the 422 on `pay.max` of `validateJobPosting`, one only the request schema refuses a 422 on `matching`, until its recruiter saves it again, the editor showing the top it is scored with: matching proposes what could be saved today, and a mutual interest's snapshot of it must read back), at most `MATCHING_LIMITS.matchingJobsPerRecruiter` (10) at once (409, counted again after the write, so it holds for requests at once; a request refused after its write leaves the job as it was, its review included); already on, nothing is written; it is then sent for review, and its office looked up in the background (`jobMatchingWarmUp`, `warmOffice`). The write is conditioned on the version read (its `updatedAt`, which an edit changes and matching's own writes do not): a posting edited meanwhile is read and checked again, once (then 409 `JOB_CHANGED`), so an approval kept for a version is never put back on another. Off: in any status, at once. Stored as `JobPosting.matching` `{ enabledAt, review }` (not part of the posting, `JobPostingInput`: neither changes `updatedAt`, so an edit started before is not refused for it); `enabledAt` unset while off, the review kept. A job a recruiter first shared on a candidate's page for recruiters can be put into matching too (off by default: nothing puts it there but its recruiter). Its terms are locked once opened (`LOCKED_JOB_FIELDS`, see "Recruiter space"), so what a candidate's criteria read never changes under a job in matching: no cap on edits of scored fields is needed. While `MATCHING` is on, an edit that takes the company out of a job in matching is refused (422 on `company`: turn matching off first); while it is off, such an edit takes the job out of matching instead. The recruiter routes' postings (`GET /recruiter/jobs`, `GET /recruiter/jobs/:id`, `POST /jobs`, `PUT /jobs/:id`, `PUT /jobs/:id/status`, `PUT /jobs/:id/matching`) carry `matching: { enabledAt, review: { status, requestedAt, reviewedAt, reason } | null }` while `MATCHING` is on (absent while off: matching is not offered); a candidate's view of a job never does.
- **Review** (`server/services/matchingReviews.ts`, the founder's decision): every job put into matching is read by hand before it reaches any candidate. It starts `pending`; only `approved` makes it proposed (`isLiveInMatching` and `liveJobsQuery` of `jobMatching.ts`: open, in matching, approved, as portfolio-common's `jobLiveInMatching` reads the job (`LIVE_IN_MATCHING` of `jobMatching.ts`, the same rule as a MongoDB filter), its version reading back as a job step keeps one (`versionReadsBack`, `storedJobSnapshot`: a job opened under rules made tighter since is proposed to nobody, as a job step refuses to share it, so no mutual interest is made on a version the journey cannot hold), and its recruiter has accepted the terms in force, `legalAcceptances.version` `LEGAL_VERSION`, as a job picked on a job step holds only while its recruiter has: after a bump a recruiter's jobs are proposed to nobody, and will be decided on by nobody, until they accept the new terms, so a mutual interest never reveals a portfolio to a recruiter who did not agree to them; what the feeds, the private page's `feed` access, the decisions and the counts follow); `rejected` carries a reason its recruiter reads (`parseReviewReason`: required, `MATCHING_LIMITS.reviewReason` characters, cleaned, the reviewer's own words). No reviewer is named or stored: the review keeps when it was decided, on which version, and why not. A review holds for that version: an approved or rejected job in matching that its recruiter edits (its description, or another field no criterion reads) is pending again (its decisions and mutual interests stay), in the edit's own write (`reviewSavedWithEdit`: its new text is never proposed unreviewed), a write conditioned on the matching the edit loaded (`matchingAsLoaded`: a reviewer's decision, or matching switched on or off, landing while the edit ran makes it 409 `JOB_CHANGED`, and the editor reloads it, so no approval of the version before is ever saved over the new text), and again from what is stored once it is saved (`afterJobEdited`; a decision taken meanwhile on the version saved is not undone); turned off then on again, a job keeps its decision only when it has not changed since. The feeds do not compare the version themselves: a release that changes how a posting is normalised would take every approved job out of them while its recruiter reads it approved and no reviewer is shown it. Logged: the job's id and the decision. The `matching_job_reviews` metric counts the jobs waiting: no email tells the reviewers. The reviewers decide on the web, "The reviewers' page" below.
- **Feeds** (`server/services/matchFeeds.ts`): computed when read, from what is stored (nothing written but the candidate's activity), each read counted against `MATCHING_FEED_READS` (120 an hour per account, both feeds together, never given back; 429 with `Retry-After`). A candidate is not proposed a job its recruiter shared on their page for recruiters (a job step's pick: they are in touch through it, and they know the job); the recruiter is proposed that candidate all the same, so that their own pick never tells them which card is the portfolio they visited (a mutual interest on such a job replaces the share, as the hand-off does). their score, their minimum and each criterion's outcome, the commute included, theirs to read; `interested`: its recruiter said they are interested in them, each feed's `interested` being the other side's). `GET /recruiter/jobs/:id/candidates` (a recruiter route: space and terms, their own job, else 404; 409 `JOB_NOT_PROPOSED` unless it is proposed now) → `{ cards, more }`: one card at a time (`MATCHING_LIMITS.recruiterCardsPerRead`, 1: a page that is not full would be a count of the job's candidates, and counts compared across jobs that differ by their pay would tell candidates' floors), the next once it is answered, and whether there are more, never how many; the candidates interested in the job first, then in the order of `hashValue('<job>:<candidate>')` (keyed: the same at every read, different for every job, nothing to do with the score, the sign-up date or anyone's name), never by score; - **Matches** (`Match`, `server/models/database/match.ts`): one per job and candidate (unique), created by the first decision of either side (see "Decisions"): `candidateDecision` and `recruiterDecision` (`MATCH_DECISIONS`: `interested` or `pass`, with when and the `version` of the posting it was taken on, `reviewedVersion`), `candidateFirstAt` and `recruiterFirstAt` (when each side first answered the pair, kept through an undo and when the job leaves matching, its interests or decisions dropped: the other side's pass made after it never shows, see "Feeds"), `matchedAt` (both interested: a mutual interest, which no decision undoes), `revealedAt` (the portfolio revealed: at the mutual interest today, the hook should terms of introduction ever come first), `snapshot` (what each side saw then, kept whatever changes after: the posting, a `JobSnapshot`, the score, the minimum, each criterion's outcome), `changedAt`, `candidateSeenAt`/`recruiterSeenAt`, `endedAt`/`endReason` (`MATCH_END_REASONS`: `candidate`, `recruiter`, `job_closed`), `expiresAt` (a TTL index). - **Decisions** (`server/services/matches.ts`): a candidate says whether a job proposed to them interests them, `PUT /opportunities/jobs/:id/decision` `{ decision: 'interested' | 'pass' }` (403 `NOT_PROPOSED_TO_RECRUITERS` unless they are proposed now; 404 `JOB_NOT_FOUND` for a job not proposed to them now, like an unknown id: `jobProposedTo` of `matchFeeds.ts`, the candidate feed's rule, their own earlier answer aside; it is activity, `touchDiscovery`); a recruiter whether the candidate of a card does, for their job, `PUT /recruiter/jobs/:id/candidates/decision` `{ token, decision }` (recruiter routes' rules: their own job, else 404, a space and the terms in force; 409 `JOB_NOT_PROPOSED` unless the job is live; 409 `CANDIDATE_UNAVAILABLE` for a token that does not open for this recruiter and job, or a candidate not proposed for it now: `candidateProposedFor`, the recruiter feed's rule, their own earlier answer aside, a candidate held back for a travel time included). Recorded with one atomic upsert on the Match (unique per job and candidate; a first decision of the other side inserted at the same moment is retried once; on a mutual interest the insert hits the unique index: 409), with the version of the posting read (`reviewedVersion`), kept `MATCH_RETENTION.decisionMonths` after the earliest decision at most (`$min` on `expiresAt`), with when that side first answered (`$min`); an undo removes the decision and keeps that first answer (the Match stays until it expires), and a decision refused once written (below) is undone with the first answer it was. Once written, the pair is read again (`proposalAfterWrite`: the job still live, `isLiveInMatching`, and the candidate not withdrawn, `withdrawnFromDiscovery` of `discovery.ts`, a consent in force with no withdrawal asked since): a withdrawal, or the job leaving matching, that landed between the check and the write dropped the decisions before this one was there, so it is undone and refused as it would have been before (403 or 404 to the candidate, 409 `CANDIDATE_UNAVAILABLE` or `JOB_NOT_PROPOSED` to the recruiter); never a decision on a candidate who withdrew, nor a mutual interest on a closed job. A decision asks no outside service (travel times from the cache, as the feeds read them).
- **Mutual interests** (`server/services/matches.ts`): a decision that leaves both interested makes one by a write conditioned on both interests, on the candidate's being on the version the request read, and on none made yet (`matchedAt`), so two interests at once make exactly one, in either order, and a pass or an undo landing between them makes none (`server/tests/matches.test.ts` sends both at the same moment, in both orders, holds two decisions of one side until both are written so both reach that write, and lands a pass just before it). Once made, the pair is read again (`proposalAfterWrite`): a withdrawal, or the job leaving matching, that landed after the decision's own check had dropped the decisions before the mutual interest was there, and would leave it alone, so it is taken back before anything is revealed or handed off (`takeBackMutualInterest`: the decision that made it undone, then what the withdrawal or the job's change does done again) and the decision refused as it would have been a moment later; never a mutual interest of a candidate who withdrew, nor one on a closed job (the tests land a withdrawal's first writes, and a close's status, just before that write). A candidate's interest holds for the version they read: given on another (the job edited, and reviewed again, before its recruiter answered), the recruiter's interest asks them again instead (their interest is dropped, the job is proposed to them again as it is now, with its recruiter's interest; the recruiter's feed does not count it as an interest), so a mutual interest is never made on a version the candidate did not read. It keeps what the candidate said yes to as the decision read it (`snapshot`: `versionNow` of the posting, its `updatedAt` as `version`, the score, their minimum, each criterion's outcome, the transit service to credit), is marked `changedAt` when an edit saved meanwhile already made the posting differ, unsets `expiresAt` (kept while it lasts), counts as seen by the side whose decision made it (`candidateSeenAt` or `recruiterSeenAt`: the other side's is unseen), and reveals the candidate's portfolio (`revealedAt`, written once the pair is read again after the mutual interest is made, so a withdrawal or the job leaving matching that landed before takes it back before anything of the portfolio can be read, and a take-back stopped midway leaves one that leads nowhere; set when `introductionTerms.revealAllowed(match)` says so: always today, the one hook should terms of introduction ever come first, which tests replace; a mutual interest not revealed leads nowhere and names no portfolio, `candidate: null`). Revealed, it leads into the candidate's journey (`handOffToJourney`, best effort, its failure logged without ids; see "After a mutual interest" under "Hiring journey"), and is read a last time: ended meanwhile, what it handed off is removed again (the end's own removal ran before it was written). A mutual interest is made clean (no end, change or other side's seen left by a request that raced a take-back). Each side reads theirs: `GET /matches?side=candidate|recruiter` → `{ matches, next }` (active and ended until they expire, the latest first, `MATCHING_LIMITS.matchesPerRead` a page, the next one with `after=<next>`, a cursor of the last one's time and id; `job=<id>` keeps one job's, as its recruiter one of their own jobs, else 404 `JOB_NOT_FOUND`), `GET /matches/:id` (404 `MATCH_NOT_FOUND` for anyone but its two sides), as `{ _id, side, matchedAt, changedAt, endedAt, endReason, seen, ... }`: the candidate with the version they said yes to (`job`, a `JobSnapshot` with its id and status now: never who posted it), their score, minimum and outcomes then; the recruiter with their job (title, company, status) and the candidate's portfolio once revealed, `candidate: { domain, title }` (where their page for recruiters is: never their name or email address); as a recruiter, with a recruiter space and the terms in force (403, 422 on `consent`), as every recruiter route. `PUT /matches/:id/seen` marks it seen for the caller's side (it and the end below write only on the mutual interest read, its `matchedAt`: one taken back meanwhile is 404); `GET /me/notifications` → `{ mutualInterests: { candidate, recruiter } }` counts the mutual interests going on that each side has not seen (decision 10 of the founder: in-app only, no email). `POST /matches/:id/end` ends it as the caller's side (`endReason` `candidate` or `recruiter`, `expiresAt` `endedMatchExpiry`; one ended already is answered as it is) and removes what it stored in the journey (`dropHandOffs` of `jobMatching.ts`, as its job's end does): the recruiter's job step is to do again, as anyone's. One whose version no longer reads back (a rule made tighter since) leads nowhere: the recruiter shares a job as anyone does, and the candidate reads it with `job: null`.
- **What a job's changes do to its matches** (`jobMatching.ts`, called by `server/plugins/jobs.ts` whatever the flag: they only end, drop, delete or send back for review). Filled, closed or back to draft (`PUT /jobs/:id/status`, or an edit through `PUT /jobs/:id`): out of matching, every decision no mutual interest came of gone (when each side first answered stays, until the match expires: `dropDecisions`, `EMPTY_MATCH`), every mutual interest ended (`job_closed`, kept 3 months more with its snapshot) and what it stored in the candidate's journey removed (`dropHandOffs`: nothing outlives the match, nor reads as a share once it ended); on hold: nothing (proposed to nobody until open again). ### Résumé import quotas and limits
Billed to the operator's `ANTHROPIC_API_KEY` (feature off without it, `GET /experiences/import` then says `enabled: false` and `POST` answers 404). Per user: `RESUME_IMPORT_MONTHLY_LIMIT` imports per 30-day window; whole site: `RESUME_IMPORT_DAILY_LIMIT` per UTC day; per user: `RESUME_IMPORT_ATTEMPTS_PER_DAY` attempts per UTC day (never given back); all `RateLimitCounter`s, taken after the file checks (base64, 4 MB → 413, `%PDF-`) and before a free `countTokens` pre-check (over 60,000 input tokens → 422). Over a limit → 429 with `Retry-After`. The paid call is streamed (`messages.stream(...).finalMessage()`), sent once (`maxRetries: 0`) with a 3-minute deadline (`resumeImportTimeouts`). The API sends nothing meanwhile: Bun's 30 s `idleTimeout` (Elysia's default) does not cut it because Bun 1.4.4 does not apply that timer while it handles a request with a body (only body-less requests are cut), which `tests/resumeImport.test.ts` ("over a real connection", a real socket with a 1 s `idleTimeout`) pins; Railway's edge allows 5 minutes without data (`docs/DEPLOYMENT.md`, "Silent connections"). Never give an import back once the paid request may have run the model: it counts once sent (drafts; refusal or `max_tokens` → 422; deadline, lost connection or an error event in the stream → 503 "did not finish"), and only failures before it or an HTTP error status from Anthropic (429/5xx/529, 400/401/403/404: not billed → 503) are given back (`refundRateLimit`). A count_tokens 400 is an operator problem (503, logged at error with the masked API message), not the user's PDF. The SDK client is built with `logLevel: 'warn'` and `openTelemetry: { traces: { contentMode: 'metadata_only' } }` so neither the PDF nor the extracted data reaches logs or spans; `tests/resumeImport.test.ts` fails if the key or the PDF appears in any response or log line. Request bodies: Bun caps them at 6 MB (`app.ts`); every route but the PDF imports (`POST /experiences/import`, `POST /jobs/import`) is capped at 1 MB (413), by `Content-Length` in `onRequest` and by the bytes actually read in a global `onParse` (chunked or repeated-`Content-Length` bodies); a PDF import without a valid session JWT gets 401 in `onRequest`, before its body is read. Traces: `RedactingSpanProcessor` (`instrumentation.ts`) drops bodies, cookies, `Authorization` and query strings (`url.query`, and the query of `url.full`) as spans end, before the `BatchSpanProcessor` queue (the exporter redacts again).

## Deployment

Two stages, each two services from the repo root: **staging** deploys every push to `develop` (`develop.portfolio.gentil.tech`, `develop.api.portfolio.gentil.tech`), **production** every push to `main` (`portfolio.gentil.tech`, `api.portfolio.gentil.tech`). `main` only receives `develop` through a release pull request (base `main`, compare `develop`, titled with the new version: `Release v1.2.0`), merged with **Create a merge commit** so `main` keeps `develop`'s history and the next release merges cleanly; `main` has no commits of its own. Both branches are protected by the rulesets in `.github/rulesets/` (applied on GitHub by importing them: pull request required, required CI checks, no force-push or deletion; squash only into `develop`, merge commit only into `main`; a PR into `develop` must be up to date with it, which `main` cannot require of a release): renaming a CI job means updating them. All services are built with **Railpack** (it reads Bun 1.4.4 from `packageManager` and runs `bun install --frozen-lockfile`): API (start `bun run start:server`, healthcheck `/health`) and web (build `bun run build:client`, start `bun run start:client`, healthcheck `/healthz`). Settings live in the Railway dashboard; there is intentionally no `railway.json` (Config as Code is deprecated and stops being read on 2026-12-01) and no `nixpacks.toml`. Live layout (verified 2026-11-15): Railway project `personal-api`, environment `production` (holding both stages): production web `portfolio web` and API `portfolio api` (branch `main`), staging web `portfolio` and API `portfolio api develop` (branch `develop`), and `MongoDB` (`mongo:7` with a volume), shared by both stages with one database each (production's holds the real data). CI (`.github/workflows/main.yml`) runs on push/PR to `develop` and `main`: quality (lint, svelte-check, server tsc, client build), tests (server + client unit against MongoDB 7, like production, and 9) and Playwright e2e; `.github/workflows/release-guard.yml` ("Only develop merges into main": the source branch, and the next semantic version in the title, one step after the latest `vX.Y.Z` tag) on PRs to `main`; `.github/workflows/release.yml` makes a release when run by hand (`workflow_dispatch`, with patch, minor or major): it opens the release PR from `develop` into `main`, titled with the next version, with auto-merge on (it needs the repository secret `RELEASE_TOKEN`, a maintainer's token: the CI of a pull request opened with the workflow's own token waits for someone to approve it, and a merge made with it starts neither the publication nor the CI on `main` that the production deploy waits for; it only ever asks for auto-merge, never a plain merge, which an admin's token would be let through before the checks), and when a release PR is merged, opened by it or by hand, it publishes the GitHub Release (tag `vX.Y.Z` on the merge commit, generated notes). Its "Tag only" input merges nothing: it publishes `main`'s current commit, for a release merged without its tag. The `develop` branch is the main development branch and the default branch.

## Cloud sessions

Claude Code cloud sessions run in a container without Docker. The cloud environment `portfolio` (Claude Code's environment settings, not this repo) has a setup script that runs before each new session: it installs `mongod` (MongoDB 7, from MongoDB's Ubuntu 22.04 apt repository: 7.0 has no 24.04 one, and the 22.04 package installs), runs `bun install`, copies each `.env.example` missing its `.env`, installs the Chromium of the project's Playwright version (the image's is older) and seeds the database once (`db:seed`, `seed:e2e`), leaving `mongod` stopped. In a session, `bun run db:up` starts that `mongod` in about a second (`scripts/db.ts`: without a Docker daemon it runs `mongod --fork` on 127.0.0.1, data in the gitignored `.mongo/`), then `bun run dev`, the server tests or the e2e flow work as described above. The e2e recruiter's jobs shared on `e2e-journey`'s scored journey count against a daily cap that only `seed:e2e` clears (see Testing): run `bun run --cwd server seed:e2e` again before a third e2e run of `client/tests/hire-journey.test.ts` on the same UTC day. So does a run of `client/tests/matching-candidate.test.ts` after another (its deck test answers the job seeded for its candidate, then withdraws for real, which holds the next opt-in back `DISCOVERY_REJOIN_DAYS`), and of `client/tests/matching-recruiter.test.ts` after another (its recruiter answers the card seeded for its job). Change the script in the environment's settings when the setup changes (a new seed, another MongoDB version).

## Claude Code Setup (new device)

Everything portable is committed to the repo:
- **CLAUDE.md** (this file) — project instructions
- **.mcp.json** — project MCP servers (railway, github, context7, svelte, chrome-devtools), auto-enabled via `.claude/settings.json`
- **.claude/settings.json** — shared permissions allowlist; local overrides go in `.claude/settings.local.json` (gitignored)
- **.claude/launch.json** — dev server configs for the browser preview (client:5173, server:3000)
- **server/.env.example**, **client/.env.example** — templates for every env var (required ones preset for local dev)
- **compose.yaml** — local MongoDB (`bun run db:up`)

Manual steps on a new device:
1. Install Bun **1.4.4** (the `packageManager` version, see README) and Docker, then run `bun install` at the repo root.
2. Copy the `.env.example` files to `.env` (the defaults work locally; never commit `.env`), then `bun run db:up` and `bun run db:seed`.
3. Export `GITHUB_PERSONAL_ACCESS_TOKEN` in your shell profile — the github MCP server in `.mcp.json` (GitHub's hosted server at `api.githubcopilot.com/mcp/`) sends it as a Bearer token.
4. Install the Railway CLI (`bun add -g --trust @railway/cli`, or `scoop install railway` on Windows, `brew install railway` on macOS) and run `railway login` — the railway MCP server in `.mcp.json` is `railway mcp`, which proxies to Railway's hosted MCP with the CLI's credentials.
5. The other MCP servers (context7, svelte, chrome-devtools) run through `bunx` with pinned major versions; nothing to install.
6. claude.ai connectors (Gmail, Calendar, Railway, etc.) are tied to the Anthropic account, not the repo — re-authorize them in claude.ai connector settings or via `/mcp` in an interactive session if needed.
7. Install Graphify (see below) — the skill files in `.claude/skills/graphify/` are committed, but the CLI must be installed per device.

## Graphify (knowledge graph)

[Graphify](https://github.com/Graphify-Labs/graphify) builds a queryable knowledge graph of the repo (code via local tree-sitter AST parsing, docs via a semantic pass) exposed as a `/graphify` skill in Claude Code.

**Install on a new device** (the CLI is machine-level, the skill is committed):

```bash
winget install astral-sh.uv        # Windows; Mac: brew install uv
uv tool install graphifyy          # NOTE: package is 'graphifyy' (double y) — other graphify* packages on PyPI are typosquats
graphify install --project         # registers the skill into .claude/skills/graphify/ (committed to this repo)
```

**Usage:** type `/graphify .` in Claude Code to (re)build the graph, then prefer `graphify query "<question>"`, `graphify path A B` and `graphify explain "<concept>"` over grepping when exploring the codebase.

**Outputs** land in `graphify-out/` (graph.html, graph.json, GRAPH_REPORT.md) — gitignored, regenerate locally with `/graphify .`.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
