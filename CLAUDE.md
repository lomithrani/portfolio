# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Tooling

**Always use Bun** — not Node, npm, or npx. Use `bun`, `bunx`, `bun add`, `bun run`, etc.

## Project Overview

A portfolio web application with a Bun workspace monorepo structure:
- **client/** — SvelteKit 3 frontend (Svelte 5 with runes, Skeleton 5, Tailwind CSS 4, `@sveltejs/adapter-bun`)
- **server/** — Elysia backend API (Bun runtime, MongoDB via Mongoose)
- **common/** — Shared code used by both client and server (the two languages of the site, `common/i18n.ts`: `LOCALES`, `getLocale`, `defineMessages`, `plural`, `intlLocale`, see "Languages" below; `ExperienceType`, `EXPERIENCE_LIMITS` (field lengths and counts the API enforces and the editor validates), domain-name validation, `DEFAULT_GOOGLE_CLIENT_ID`, the résumé import time limits `RESUME_IMPORT_TIMEOUTS`, booking calendar dates: `bookingHorizon`, `splitDateRange`, job postings: `JobPostingInput`, `JOB_LIMITS`, `normalizeJobPosting`, `validateJobPosting` (the rules the API enforces and the job editor shows) and their display labels, `opportunityPath` (the address of a job's private page, which the meeting invitation links and the client routes to), account spaces: `USER_MODES`, `RECRUITER_PLANS`, the hiring journey: the step types' manifests (`WorkflowStepManifest`, `stepManifest`, `stepManifests`), `parseWorkflow` (the rules of a journey the API enforces and the owner's editor shows), `newWorkflowStep`, `openWorkflowSteps`, `DEFAULT_WORKFLOW_STEPS`, `WORKFLOW_LIMITS`, `NOTE_STEP_LIMITS`, step suggestions: `STEP_SUGGESTION_LIMITS`, `parseStepSuggestion` (the rules of the "Suggest a step" form, enforced by the API, checked on the text `cleanStepSuggestionText` keeps), feedback (`common/models/feedback.ts`): `FEEDBACK_LIMITS`, `FEEDBACK_KINDS`, `FEEDBACK_ISSUE_TYPES`, `FEEDBACK_THEMES`, `FeedbackContext`, `parseFeedbackContext`, `isFeedbackRoute`, `parseFeedback` (the rules of the "Send feedback" dialog, enforced by the API), and `cleanIssueText` (`common/models/issueText.ts`: what a text filed as a GitHub issue keeps; `cleanStepSuggestionText` and `cleanFeedbackText` are it), the terms of use and age confirmation (`common/models/legal.ts`): `LEGAL_VERSION`, `MINIMUM_AGE`, `AGE_CONFIRMATION_KEYS` / `ageConfirmationKey()` (the key of the confirmation's wording, one per language), `legalMessages` (that wording, and the messages of a refused confirmation such as `legalMessages.staleTerms`), `ConsentInput`, `CONSENT_SOURCES`, `parseConsent` / `consentProblem` (the rule the API enforces), `currentConsent()` (what the client sends once the box is ticked), the address search: `ADDRESS_SEARCH`, `addressSearchText`, `AddressSuggestion`, `OfficePlace` (`common/models/address.ts`), the perfect job: `PERFECT_JOB_CRITERIA`, `parsePerfectJob` (the rules of the criteria a candidate rates, enforced by the API and shown by the admin tab), `scorePerfectJob` (a job posting scored against them out of 100), `JOB_FIELD_CRITERIA` (for every field of a job posting, the criteria that read it), `ROBOTS_NOINDEX` (`common/models/robots.ts`: the directive the web pages that are not listed and every API answer send, see "Search engines"))

Bun 1.4.4 is pinned in the root `package.json` (`packageManager`); the text lockfile `bun.lock` uses the isolated linker (each workspace has its own `node_modules`).

## Common Commands

All from the repo root (`bun run --cwd <workspace> <script>` runs a workspace script from there).

### Development
```bash
bun install                       # Install all workspaces (CI and Railway use --frozen-lockfile)
bun run db:up                     # Local MongoDB 7 (as in production): Docker (compose.yaml) when it runs, else a local mongod (scripts/db.ts)
bun run db:seed                   # Seed owner user + 'louis.gentil' domain (idempotent)
bun run dev                       # API (port 3000, watch) + SvelteKit dev server (port 5173) in parallel
bun run dev:server                # API only
bun run dev:client                # Web only
bun run db:down                   # Stop MongoDB (data kept in a Docker volume)
```

### Build & Run
```bash
bun run build:client              # Build SvelteKit for production (client/build)
bun run start:server              # Start the API without watch mode (production behaviour needs NODE_ENV=production)
bun run start:client              # Start built client (port 4000)
```
`build:client`, `start:server` and `start:client` are the Railway build/start commands: do not rename them, and do not add a root `build`/`start` script. `start:server` sets no `NODE_ENV`: production behaviour (Secure cookie, no `/swagger`) needs `NODE_ENV=production`, which Railpack sets on Railway. Do not add it to the script (the local e2e flow and CI run it over plain http).

## Architecture

### API Communication (Type-Safe)
The client uses **Eden Treaty** (`@elysiajs/eden`) for type-safe API calls. The Elysia server's type (`Portfolio`) is imported directly by the client, so API changes are caught at compile time. See `client/src/services/portfolio.ts`.

### Routing
SvelteKit dynamic routes under `[domain]/`; each portfolio is loaded by domain name via `+layout.server.ts` calling the API, through `portfolioTextApi` (Eden Treaty without its date parsing, so a title, a subtitle or an experience titled "2027-01-01" stays text), then `reviveExperienceDates` of `client/src/services/experienceDates.ts` makes Dates of the only real dates, the `start` and `end` of each experience and project. The root (`/`) is the candidate landing page (no longer a redirect: `louis.gentil` is linked as an example). Three route groups: `(site)/` (the landing page, `/legal/*`, `/account`), `(app)/` (the recruiter space, and `/opportunities/[id]`, the private page of a job description shared with a candidate: see "Hiring journey"; there is no job board: `/jobs` answers 410 Gone, `routes/(app)/jobs/+server.ts`, in the visitor's language, and `/jobs/[id]`, where meeting invitations linked a job before, answers 308 to `/opportunities/[id]`, `routes/(app)/jobs/[id]/+server.ts`), and `[domain]/`. Since `(site)` owns `/`, link to it with `resolve('/(site)')` (`resolve('/')` does not type-check). The `(site)` layout passes `showSignIn={false}` to `Header.svelte`: no Login button, so no Google script and no One Tap on those pages (the session check and the account menu still run); it ends with `LegalFooter`. `(app)` and `[domain]` end their scrolling page with compact `LegalLinks`, so the legal pages are reachable from every page. `(site)` and `(app)` have no bar of links under the header: the account menu leads from one space to the other, the header's logo is a link to the landing page there (`homeLink`; a portfolio's logo is not a link), and `LegalFooter` has the link a signed-out visitor needs ("For recruiters"). The light/dark switch (`ThemeToggle.svelte`, one per page) is in the footer on those pages (`LegalFooter`, and next to the compact legal links in `(app)`) and in the rail (`LeftBar.svelte`) on a portfolio; the language switch (`client/src/lib/i18n/LanguageSwitch.svelte`, one per page too) sits next to it in each.

In the three layouts the page scrolls in `main#page`, which is `relative`: keep it. A page's absolutely positioned elements (the hidden input of a Skeleton `Switch`, `sr-only` text, live regions) are then placed in it and scroll with the page; placed in the box around it, focusing one scrolls that box and the whole page goes out of sight (`client/tests/hire-journey.test.ts`, "keeps the page in sight").

New top-level route segments must be added to `RESERVED_DOMAIN_NAMES` (`common/models/domainName.ts`): a domain with that name would be hidden behind the route. Their pages must also choose whether search engines list them (see "Search engines" under "Languages"); a page under `[domain]` is never listed. Reserved today, among others: `account`, `about`, `contact`, `cookies`, `help`, `jobs`, `legal`, `opportunities`, `privacy`, `recruiter`, `report`, `signup`, `start`, `terms`.

**Navigation rail.** The portfolio's rail (`client/src/lib/components/LeftBar.svelte`, mounted by `[domain]/+layout.svelte`) is a drawer laid over the page, collapsed to a handle on the left edge: hovering or pressing the handle opens it over the page. On load it shows for 3 s, as a hint, only where it fits in the margin beside the page (`--peek-fits` in its CSS, which its script reads): from 72rem for content centred in at most 56rem (`max-w-4xl`), from 96rem on a page with a `data-page-wide` element (at most 80rem, `max-w-7xl`: the timeline). A page under `[domain]/` keeps its content centred within `max-w-4xl`, or marks what is wider with `data-page-wide`; `client/tests/experiences-owner.test.ts` ("the navigation rail") fails when the rail shows over a page on load. The peek ends early when it stops fitting (a resize, a page that becomes wide), and a collapsed rail's links are hidden with `visibility` in the CSS, not `inert`, so they are out of the tab order before the page hydrates too. Its labels are `Navigation.TriggerText` (12 px: the page's text size does not fit the rail).

### Languages (English and French)
The whole site is in English and French: pages, API answers, the labels and validation messages of portfolio-common. Full rules, French style and glossary: `docs/I18N.md`. The language of a page request is, in order: `?lang=fr|en` in the URL (which also saves it for a year in the `lang` cookie, unless the visitor had already chosen and the link comes from another site: a shared link never replaces a choice; only a page load saves it, never a SvelteKit data request), that cookie, the browser's `Accept-Language`, English (`client/src/hooks.server.ts`, which writes it on `<html lang>`; `hooks.client.ts` reads it there). It is ambient: `getLocale()` of portfolio-common gives it anywhere, both servers keeping it per request with `AsyncLocalStorage` (the client's hook; `server/services/locale.ts`, an Elysia `wrap` that reads the `Accept-Language` the client sends with every API call, `client/src/services/portfolio.ts`); outside a request (unit tests, scripts, module load) it is English. The language switch is a plain link to the current page with `?lang=`, loaded from the server: a page never changes language while it lives, nothing is reactive. Search engines find each language of a page they list at its own address: English is the address alone, French adds `?lang=fr` (`localeAlternate` of `client/src/lib/i18n/urls.ts`); `client/src/lib/i18n/LocaleLinks.svelte` writes the canonical and `hreflang` links for the recruiter landing (mounted by the `(app)` layout, which leaves it out on its pages that are not listed), the landing page and the legal pages write their own; a portfolio, which is not listed, has none (see "Search engines").

**Search engines.** Portfolios are not listed by search engines but stay crawlable (`client/src/lib/robots.ts`): every page under `[domain]`, the pages under `/recruiter/jobs`, `/opportunities` and `/account` (`NOINDEX_ROUTES`, matched on whole segments of the route id) answer with `x-robots-tag: noindex, nofollow, noarchive` (`NOINDEX`, portfolio-common's `ROBOTS_NOINDEX`), which `client/src/hooks.server.ts` sets on every answer of those routes, their `__data.json` and error pages included (the 404 of a name nobody claimed is the root `+error.svelte`, without the portfolio's layout: it has the header alone), and carry a robots meta: `client/src/lib/components/PortfolioHead.svelte` in the `[domain]` layout (with `og:url` and `og:locale` for link previews, and no canonical or `hreflang`: a page that asks not to be listed names no address to list), the `(app)` layout on its routes of `NOINDEX_ROUTES` (written in the browser: the recruiter space and `/opportunities` are not rendered on the server), the account page. The API sends the same `X-Robots-Tag`, the same `ROBOTS_NOINDEX`, on every answer, errors (4xx and 5xx), unmatched 404s and CORS preflights included (Elysia's default headers, `server/app.ts`). `client/static/robots.txt` refuses nothing, on purpose: a crawler must fetch a page to read its noindex, LinkedIn or Slack fetch a shared portfolio to preview it, and a `Disallow` could not name portfolios (top-level paths); in production Cloudflare puts its managed rules above it (`docs/DEPLOYMENT.md`, "Search engines"). The landing page, the legal pages and the recruiter landing stay listed, with their canonical links. **A page added under `[domain]` is not listed, by its route**; a new page elsewhere must choose, under one of `NOINDEX_ROUTES` or among the listed pages of `client/src/lib/robots.test.ts`, which fails until it has (and when the `[domain]` layout stops mounting `PortfolioHead`, or a page under it resets its layout); `client/tests/robots.test.ts` checks the headers, metas and robots.txt of the running site. A text that says who can find a portfolio (the landing FAQ, the privacy policy's `#summary` and `#data-portfolio`) says that search engines are asked not to list it, never that it cannot be found.

**Every text a person reads is a message**: `{ en, fr }` (two strings, two functions for a text with values, or two arrays) declared with `defineMessages()` in a `*.messages.ts` file next to the code that shows it (`Foo.svelte` → `Foo.messages.ts`, `+page.svelte` → `page.messages.ts`, `services/foo.ts` → `foo.messages.ts`; shared words in `client/src/lib/i18n/common.messages.ts`). Rules to keep: **read a message when it is shown, never at module load** (a module-level constant holding a text is English for everyone: use the messages object, a function or a getter); whole sentences, never glued fragments; plurals through `plural()`; dates and numbers with `intlLocale()`; a sentence with a link in it stays one message with the passage tagged (`'the <terms>terms of use</terms>'`), rendered by `client/src/lib/i18n/Rich.svelte`; English is the reference and the tests read it. Not messages: what people wrote, names, log lines (the API logs in English whatever the visitor's language), texts sent to a model or filed on GitHub, and the API bodies the client compares (`'Domain not found'`...), which stay English constants (`server/protocol.ts` lists them with the client code that matches each; the client then says it in its own words). In the API an error takes a function reading its message (`new BadRequestError(() => m.invalidDate)`, `server/errors.ts`): the answer is in the visitor's language and the error keeps the English for the log. The legal texts stay one component per document and language. **Portfolio is the site's name**, a brand: capitalised, without an article, never translated ("On Portfolio, a skill is not a keyword", « Sur Portfolio… »); the common noun is kept for one person's page ("your portfolio", "a candidate's portfolio"), never "a portfolio" or "portfolios" for the product (`docs/I18N.md`, "Portfolio is a name"). A portfolio's title is its owner's, not translated either; a portfolio without one is headed by its address name (`[domain]/+layout.svelte`). `client/src/lib/i18n/i18n.test.ts` and `server/tests/i18n.test.ts` fail when a `*.messages.ts` file lacks a language or its tags differ; TypeScript refuses a message without its French.

### Landing page and onboarding
`routes/(site)/+page.svelte` (rendered on the server, in English or French: title, description, canonical and `hreflang` links (English is `/`, French `/?lang=fr`), Open Graph and `twitter:card` tags, image `client/static/og-image.png` or `og-image-fr.png`, 1200×630), its texts in `routes/(site)/page.messages.ts`: hero ("Your portfolio, your way. No more calls about the wrong job."; "Create your portfolio" scrolls to the onboarding card and focuses its address field; "See an example" → `/louis.gentil/experiences`), "Calls you can stop taking" (three cases the perfect job's criteria stop: too far, underpaid, not remote enough), "First the match, then the call" (the journey's steps, the perfect job), "Make it yours" (themes, title and tagline, list or timeline, skills backed by projects), how it works, FAQ. The page is written for talent and sells the site as their job matchmaker: it saves them the calls about jobs that do not fit, then lets them make the portfolio their own. It does not sell the address (a portfolio is a path of the site, not a domain of its own): keep the copy to what the code does. Two sections have a demo, `client/src/lib/components/landing/DemoVideo.svelte`: a silent recording of the app on a phone (`client/static/landing/demo-style.*`: the experiences page in five themes, as a list and a timeline; `demo-journey.*`: a recruiter whose job fails the commute deal-breaker; `.webm`, `.mp4` and the first frame as `.jpg`), downloaded and played only while it is on screen, with a pause button, and not started by itself with "reduce motion". They are recorded from the real app, in English, with `client/scripts/landing-demos/` (`seed.mjs`: a fictional candidate and recruiter in the local database, the recruiter accepting the terms in force through the API, so run it again after a `LEGAL_VERSION` bump; `record.mjs`: the steps filmed, how to run it at its top): record them again when what they show changes. The share images carry the hero's headline, read from the page's messages by `client/scripts/og-image/render.mjs`: run it again when the headline changes. The onboarding card is `client/src/lib/components/landing/CandidateOnboarding.svelte`, a stepper of three steps:
- The address field shows from the start, signed out too: a live preview `{host}/{name}` (`portfolioUrlPreview` of `client/src/services/account.ts`) and an availability pill from `checkDomainAvailability` (350 ms debounce, `AbortController`, stale answers dropped; invalid and reserved names answered locally, without a request), backed by the public `GET /domain/:name/availability` (advisory: the claim decides). What was typed before signing in is kept (`suggestDomainName` fills only an empty field).
- **1. Sign in with Google**: the `AgeTermsConsent` checkbox comes first, and Google's script (accounts.google.com) is loaded and its button rendered **only while it is ticked** (the legal pages state this: keep it); the handler checks the box again and calls `login(credential, 'candidate', currentConsent())`. Until `$sessionCheckedStore`, no step is highlighted (no flash of the wrong step).
- **2. Claim your address**: `claimPortfolio(name, consent?)` then `switchMode('candidate')`; the checkbox shows again when the account has not accepted the current terms or the API answers with cause `consent`.
- **3. Add your résumé**: when `GET /experiences/import` is enabled with imports left, "Upload my résumé (PDF)" (with the notice that the PDF goes to Anthropic in the US) → `/<domain>/experiences?import=1`; otherwise "Add my experiences". The experiences page opens the résumé import for `?import=1` once the owner's import status is known (an info toast when it is not available), then removes the parameter with `replaceState`, so a reload or Back does not reopen it.

### Legal pages, consent and account deletion
**Legal pages**: `/legal` (legal notice), `/legal/privacy`, `/legal/terms`, `/legal/cookies`, rendered on the server in the site's language (see "Languages": English or French; `?lang=fr` asks for French and is the French version's canonical address); `(site)/legal/+layout.server.ts` reads the `LEGAL_*` variables (see Environment Variables) and returns `{ publisher }`; each page reads its language with `getLocale()` (the language the page was loaded in, like its header and footer, not that of a later data request). The texts are Svelte components, one per document and language, in `client/src/lib/components/legal/content/` (`LegalNoticeEn.svelte`, `PrivacyFr.svelte`...; English and French share their section ids), shared facts (host, CNIL, Calendar scope, session length, import limit) in `content/facts.ts`, document metadata, helpers, `LOG_RETENTION` and `CLOUDFLARE_LOG_RETENTION` (the log retention figures the operator must confirm) in `legalDocuments.ts`, the page shell in `LegalDocument.svelte` ("Last updated" is `LEGAL_VERSION`). Without a publisher name and contact email the pages say "Publisher details are not configured yet." (never a made-up identity). The texts describe what the code and the operations do (data kept, processors, cookies and localStorage keys, retention): the privacy policy names Cloudflare, Inc. as the content delivery network and proxy in front of the web pages, not of the API, which is reached directly, and says nothing of it changing the pages or storing anything in the browser, so its Email Address Obfuscation and Network Error Logging stay off (`docs/DEPLOYMENT.md`, "Legal pages": the checks, and what to change if any of that changes); the Terms name the activity placement (article L5321-1 of the Labour Code: the site puts candidates and recruiters in touch, takes no part in hiring decisions, is not a party to the employment contract, and scores only job descriptions, against a candidate's own criteria, never candidates) and say that candidates never pay (article L5321-3: nothing may ever be charged to a candidate) and that recruiters, free for now, are told before any paid feature applies to them. **When a change alters any of it, update both languages, and when the Terms of use or the Privacy policy change materially, bump `LEGAL_VERSION`** (`common/models/legal.ts`): accounts that accepted an older version see the checkbox again (landing sign-in, claim forms, `/account`, the recruiter pages) and must accept before their next claim or their next use of the recruiter space, and a page loaded before the bump gets a 422 on `consent.termsVersion` (`legalMessages.staleTerms`: reload). The cookies page lists the `lang` cookie (the language a visitor chose) next to the session cookie: a new cookie or localStorage key goes there, in both languages.

**Consent record**: `AgeTermsConsent.svelte` (`client/src/lib/components/legal/`) is the shared unticked checkbox (`legalMessages.ageConfirmation`, in the page's language, links to the terms and privacy policy in a new tab so the form keeps what was typed). Once ticked the client sends `currentConsent()` (`{ termsVersion: LEGAL_VERSION, ageConfirmed: true }`); `parseConsent` accepts only that. The API appends an entry to `User.legalAcceptances` (`recordConsent` of `server/services/legal.ts`: one atomic update, never twice for the same version; the key of the wording ticked, `ageConfirmationKey()`, is the request's language's; no birth date, no IP) from `POST /login` (`consent`, `consentSource` `landing` (default), `claim` or `recruiter` (always `recruiter` with the mode `recruiter`, whatever `consentSource` says: that sign-in opens the space): an invalid confirmation is checked before the Google token, and its 422 creates no account and issues no session; the mode `recruiter` without the terms in force is a 422 on `consent` once the account is found or created, as for any sign-in (the Google id and email): no session, no space), `PUT /me/consent` (source `claim`, `account` or `recruiter`, default `account`; `landing` refused), `POST /domain/claim` or `PUT /me/mode` (source `recruiter`). A claim requires the current terms: an account that has not accepted `LEGAL_VERSION` sends `consent` with it or gets a 422 on `consent` (after the 400 of an invalid name, before the 409s); portfolios claimed before the terms existed stay online. So does the recruiter space (`CONSENT_SOURCES` `recruiter`): opening it (`setActiveMode` of `server/services/users.ts`, behind `PUT /me/mode` and `POST /login` with the mode `recruiter`) calls `requireCurrentTerms(userId, consent, 'recruiter')` before `enableRecruiterSpace`, so no space is created without the terms in force (422 on `consent`, "…to open your recruiter space"; switching to an existing space needs nothing), and every recruiter route (`requireRecruiterSpace` of `server/services/recruiters.ts`: the job postings, `GET`/`POST /jobs/import` (before the file is read or an import counted), the job step's submit) answers 403 without a space, then 422 on `consent` (`recruiterTermsRequired`) while the account has not accepted `LEGAL_VERSION`; a job picked on a job step holds only while its recruiter has (the step's `evaluate`: after a bump it is `pending` again, so the steps after it lock, booking included, until they accept): a space opened before recruiters accepted the terms, or before a bump, accepts them again (`PUT /me/consent`, source `recruiter`) from the recruiter pages, which show `TermsAcceptance` (`source="recruiter"`, `required`) in place of what the API refused (the dashboard, a posting's page and editor, the job step, which then reloads the journey; the new job page shows it before the form as soon as the session says the terms in force are not accepted; the job editor's save says to open the recruiter space). On `/account`, `TermsAcceptance` names the recruiter space for an account that has one (and the portfolio too when it has both). An account that already accepted the version in force elsewhere opens the space without a new record (one acceptance per version): the box shows only to an account that has not, and `RecruiterRules.svelte` (`client/src/lib/components/legal/`) says what the terms ask of recruiters instead. `UserDto` has `termsVersion` (the latest acceptance) only when set; `hasAcceptedCurrentTerms` of `client/src/services/account.ts` hides the checkbox for accounts that already accepted. It opens so that the shortest bar drawn is 120 px wide (`defaultMonthWidth`, `TIMELINE_ZOOM` of `timeline.ts`: a 2-month project makes a month 60 px), scrolled so that the latest end of a bar (the current month for an ongoing one, later for one planned further) is near the right edge (not the axis' end: the axis runs to the end of that year, which can be a screen or more of nothing at this zoom), and goes from the whole axis in sight (the scroller's measured width, which that zoom keeps following; a page wider than the axis stretches it) to 240 px a month (`closestMonthWidth`, which also caps the axis at 48,000 px). ### Hiring journey (workflow)
The Hire page (`routes/[domain]/hire/+page.svelte`) is the portfolio's hiring journey: the steps a recruiter goes through, in the order the owner chose. A journey is a list of steps `{ id, type, config }` (`common/models/workflow.ts`): the id is unique in the journey (a visitor's progress is kept under it), the type names a step type, `config` is that type's settings. The same type can appear more than once unless its manifest sets `max`. Adding a step type, and the rules a step must keep: `docs/WORKFLOW_STEPS.md`.

A step type is defined in three places under the same `type` name, each with a registry (`index.ts`): its manifest in `common/models/workflowSteps/` (`kind` `requirement`|`access`, label and description (getters over the messages of `workflowSteps.messages.ts`), `max`, `needs`: the step types it needs earlier in the journey, `defaultConfig`, `parseConfig`: the settings' rules), its behaviour in the API in `server/services/workflowSteps/` (`ServerStep` of `types.ts`: `evaluate` → the visitor's `status` and `view`, optional `visitorConfig`, `submit`, `describe`; the context gives a step its own `config` and `data`, and `earlier`: the steps before it with what they stored) and its entry in `client/src/lib/components/hire/steps/` (`ClientStep` of `types.ts`: what the visitor sees, the settings form of the owner's editor, and for an `access` type the `goal` the Hire page is titled after). `server/tests/workflows.test.ts` fails when the API's registry and the manifests differ. Four types today: `note` (the owner writes a Markdown note, the visitor reads it and confirms; any number per journey), `job` (the recruiter picks or writes one of their open job descriptions; one per journey; writing a job goes through `/recruiter/jobs/new?journey=<domain>`, back on the Hire page with `?job=<id>`), `job-match` ("Match the perfect job": the job picked on the job step is scored out of 100 against the owner's perfect job, see "Perfect job" below; settings `minScore` and `showDetails`; `failed` under the minimum; needs a `job` step before it; one per journey; nothing to submit, nothing stored), `meeting` (book a meeting, `client/src/lib/components/hire/MeetingBooking.svelte`; one per journey).

The engine is `server/services/workflows.ts`: it owns the order, the locks and the storage, and knows nothing about what a step is. A step is open once every step before it has the status `succeeded` (`openWorkflowSteps`; statuses `pending`|`succeeded`|`failed`; only the job match produces `failed`, which stops the journey like `pending` and shows the step to the visitor as not passed, with what its type says: `failedNote` of its client entry); nothing stores a status, each type's `evaluate` computes it at every read. A stored step whose type no longer has a manifest or a server step is kept and can never succeed: the journey fails closed, it never skips a step. The owner is never stopped by their own journey. The owner edits the steps in the admin tab "Hiring journey" (`client/src/lib/components/admin/WorkflowsTab.svelte`: add, remove, move up and down, each step's settings; `GET`/`PUT /workflow`); `PUT` goes through `parseWorkflow` (at most 12 steps, unique ids, known types, `max`, each type's `parseConfig`, a step's `needs` before it, a requirement step needs an access step after it) and answers 422 naming `steps`, `steps.<index>` or `steps.<index>.config.<field>`. An owner who never saved has `DEFAULT_WORKFLOW_STEPS` (one `meeting` step: the page is the booking page, open to anyone, as before journeys).

Visitors read the journey with `GET /workflow/domains/:domainName` (optional session: the route reads the cookie itself, `server/services/session.ts`): each step with its `status`, the `config` its type's `visitorConfig` returns (settings are private otherwise; what it returns is public, signed in or not) and the `view` its type gives the signed-in visitor about their own progress. Anonymous callers and the owner are `pending` on every step (`own: true` for the owner). A visitor submits a step with `POST /workflow/domains/:domainName/steps/:stepId`, body `{ input }` (session; `submitStep`: 403 on one's own portfolio, 409 when the journey has no such step or its type takes no submission, 403 until the steps before succeeded); the type's `submit` checks `input`, which is untrusted, and returns the data to store. Progress is kept per step id: reordering keeps it, removing a step (or giving its id another type) drops it, a step entering the journey starts from nothing whatever was left under its id, changing a step's settings keeps it. The journey's routes go through `portfolioTextApi` in the client (`client/src/services/portfolio.ts`: Eden Treaty without its date parsing, so a note titled "2027-01-01" stays text).

The API enforces the journey on `available-dates`, `available-slots` and `book` (`openStepOfType` of `server/services/workflows.ts`, for the type `meeting`: 404 when the journey has no meeting step, 401 signed out, 403 until the steps before succeeded). `book` invites the address the visitor typed and the owner's account email (Google never emails an event's organizer, so the owner only gets the invitation when the schedule's calendar is not their sign-in account's primary one; `GET /appointments/upcoming` leaves the owner out of the guests it lists), puts where a meeting outside Google Meet takes place (the schedule's `locationDetails`: for a phone call the owner's number, which the visitor calls; the booking asks the visitor for none) in the event's `location` and the first line of its description, sets the event's reminders with `bookingReminders` of `server/services/googleCalendar.ts` (an email reminder Google sends the calendar's owner a minute after the booking, at most 4 weeks ahead, which is how the owner of a primary calendar is told, and a pop-up 10 minutes before, since they replace the owner's defaults), and puts in the invitation the lines of each earlier step's `describe` (the job step: title, company, and the link of the job's private page, `opportunityPath(id)` of portfolio-common (`/opportunities/<id>`), on the request's allowed `Origin`), and records the booking on the meeting step (`recordStepData`: only for a visitor who already has progress with this owner, an open booking page keeps no journey progress of its visitors; the slot reservation keeps the account of one who booked signed in, until the slot ends, for `GET /appointments/booked`). Pure client helpers in `client/src/services/workflow.ts`.

**The job's private page.** `/opportunities/[id]` (`client/src/routes/(app)/opportunities/[id]/+page.svelte`, rendered in the browser only, `opportunities/+layout.ts`, not listed by search engines; helpers in `client/src/services/jobView.ts`) shows a job description to the people it was shared with, from `GET /opportunities/jobs/:id` (`server/plugins/opportunities.ts`: session only, 401 signed out, 422 for an id that is not one) → `{ job, access }`. Who may read it is one function, `readableJobPosting` of `server/services/jobAccess.ts`: `access: 'recruiter'` for the posting's own recruiter, whatever its status (the page sends them on to `/recruiter/jobs/:id` with `replaceState`), `access: 'journey'` for each portfolio owner on whose journey the recruiter picked it (a recruiter can pick one posting on several journeys), as the current pick of a job step of the journey the owner has now (`pickedJobId` of the job step, compared with the posting's own id, whatever the case of the id in the URL; a later pick, a step removed or the posting deleted ends it), whatever its status but `draft`; anyone else gets the 404 of an unknown id (`JOB_NOT_FOUND`), never a 403, and the answer never names the recruiter. The page's states: the session being checked, signed out (`hire/SignInButton.svelte`), not shared with you (with the account signed in), an error to retry, and the job (`JobDetails`, dated with its publication). `spaceToRecord` counts it in the candidate space for an account with a portfolio, and `recordSpaceShown` records one page after the other, so the recruiter sent on ends in the recruiter space. A new way for a posting to reach a candidate is a new `JobAccess` there, never a second view.

The job step offers the recruiter's PDF import too (`JobStep.svelte` mounts `components/job-import/JobImport.svelte` when `GET /jobs/import` says it is available): the draft opens in the job editor with `?journey=<domain>&import=1`, and saving it comes back to the Hire page like a job written by hand.

**Perfect job.** The admin tab "Perfect job" (`client/src/lib/components/admin/PerfectJobTab.svelte`, its controls in `admin/perfect-job/`, form helpers in `client/src/services/perfectJob.ts`; `GET`/`PUT /perfect-job`, owner only) is where the owner says what they look for in a job: thirteen criteria (`PERFECT_JOB_CRITERIA` of `common/models/perfectJob.ts`: job titles, seniority, management, work mode and remote days, location, commute, contracts, working time, RTT days, pay, skills wanted and avoided, travel), each read from the fields a recruiter fills in for a posting, each switched on with an importance from 1 to 5 and an optional deal-breaker flag. `PUT` goes through `parsePerfectJob` (422 naming `criteria` or `criteria.<criterion>.<setting>`; lists cleaned, settings that do not apply and unknown keys dropped). `scorePerfectJob` scores a posting out of 100: each criterion counts for its importance by how well the job matches it (some match partly: pay down to 20% under, remote days, hours, RTT days, the share of the job's skills that are wanted), the pay asked is compared with the bottom of the job's range (`pay.min`, brought to a year or a day; the top of the range is shown to candidates but never scored, so widening a range never raises a score, the job editor tells recruiters so, and the PDF import never makes a ceiling ("up to 60 k€") the bottom: it leaves the minimum for the recruiter to give), what the posting does not state counts as not matching, a deal-breaker not matched at all brings the score to 0, and no criterion at all scores 100. The `job-match` step uses it (`server/services/workflowSteps/jobMatch.ts`, which reads the job through `pickedPosting` of the job step). Rules to keep: the perfect job is private (no route returns it to anyone but its owner); a visitor gets their score and the step's minimum, and with the owner's `showDetails` the name of each criterion and its outcome (`match`|`partial`|`miss`, not stated, missed deal-breaker), never what is asked or a criterion's importance; a stored minimum that is not a score reads as 100 (fails closed).

**Criteria and job fields go together.** A candidate can only ask for what a recruiter can say: `JOB_FIELD_CRITERIA` (`common/models/perfectJob.ts`) lists, for every field of a job posting (`JobFieldPath`, the dotted paths of `JobPostingInput`), the criteria that read it, or none on purpose (`pay.max`: the pay is scored on the bottom of the range). Adding a field to `JobPostingInput` does not compile until it is listed there and has an input in the job editor (`FIELD_OF_PATH` of `client/src/services/jobPosting.ts`). Adding a criterion means reading it from posting fields declared there: `server/tests/perfectJobScore.test.ts` fails when a criterion is read from no field, or when its scorer reads a field it does not declare (or declares one it does not read); `server/tests/perfectJob.test.ts` that the API stores and returns every field (`tests/completePostings.ts`: postings that state everything), `server/tests/jobExtraction.test.ts` that the PDF import can read every scored field, `client/src/services/tests/jobPosting.test.ts` and `client/tests/recruiter.test.ts` that the editor has and shows an input for each.

**Commute.** The `commute` criterion is the travel time the owner accepts a week (`maxMinutesPerWeek`), from an address they give (`from`; `place`, where the API found it, is set by the API on save whatever the client sends) by the modes they accept (`COMMUTE_MODES`: `transit`, `bike`, `car`, `walk`). A job counts the way there and back for each day at the office (`officeDaysPerWeek`: 5 on site, 5 minus the remote days of a hybrid job, 4 when it does not say, none when fully remote, which always matches): once a week can be further than every day. Over the time accepted it matches less, and not at all 50% over (`COMMUTE_TOLERANCE`). The travel time is not in the posting: the API computes it (`server/services/commute.ts`, `commuteContext`) and passes it to `scorePerfectJob` as its `context`; without one (travel times off, a service that did not answer, the daily cap reached) the criterion is `unavailable`: left out of the score and of the deal-breakers, and shown to the recruiter as "could not be computed". A posting whose address is not found counts as not stated. Off unless `COMMUTE_TIMES=true` (`GET /perfect-job` says `commute: { enabled, modes }`; a new address is refused with 422 while off). Services: the Géoplateforme (IGN, `server/services/geoplateforme.ts`: geocoding, the way by car and on foot; by bike the time is estimated from the distance on foot, `BIKE_METERS_PER_MINUTE`) and, for public transport, the service `COMMUTE_TRANSIT` names (`server/services/transit.ts`): `here` with `HERE_API_KEY`, the HERE Public Transit API (`server/services/hereTransit.ts`: commercial, a free monthly allowance, its key in the URL of each request, which is never logged), or `transitous` with `COMMUTE_CONTACT`, Transitous (`server/services/transitous.ts`; its usage policy is for open-source, non-commercial projects). `GET /perfect-job`'s `commute.transit` and the job match step's `view.transit` name the service in use, which the owner's tab and the Hire page credit. A posting gained `location.address` (street and number, optional) for this; without it the town is used, as when the street is not found. Rules to keep: every answer is cached (`CommuteCache`, keys are HMACs of the question; a public transport answer's question names its provider, so a site that changes `COMMUTE_TRANSIT` asks again) and every outside call counted against `COMMUTE_DAILY_LIMIT`; a failure is remembered for 10 minutes so a read never waits twice; redirects are never followed; the owner's address and place are never logged, never cached (they live in their `PerfectJob` only) and never reach a recruiter (`server/tests/commute.test.ts`, which fakes the three services); the tests and CI never call them (the e2e test answers `/perfect-job` in the browser).

**Address search.** The two fields that take an address, the commute's `from` (`PerfectJobTab.svelte`) and a posting's office address (`JobEditor.svelte`), are `client/src/lib/components/address/AddressSearch.svelte`: a text field that is also a combobox (ARIA: arrows, Enter, Escape closes the list only), which after a 300 ms pause in typing asks `POST /addresses/search` (`q`, and the `postalCode` and `city` a posting already has, which narrow it while the geocoder finds a good match there, else it asks again without the postal code, then without the town: `suggestAddresses` of `server/services/geoplateforme.ts`, at most three requests; client helpers in `client/src/services/addressSearch.ts`, shared rules `ADDRESS_SEARCH`, `addressSearchText`, `AddressSuggestion` in `common/models/address.ts`) and lists the addresses the Géoplateforme knows. Picking one writes it as the map service does (the owner's field takes the whole label, a town's with its postal code so the right one is found again; a posting takes the street, postal code and town in their fields, and a town picked empties the street only when what was typed there was that town's name), so the address kept is one the lookup on save or at scoring finds again; what is typed without picking stays as typed. Under a posting's address, `job-editor/OfficePlace.svelte` says where the office is found (`POST /addresses/office`: its street, only its town, which is a warning when a street was typed, or nowhere), looked up when the three fields are left and for the office the editor opened with; an address picked in the list is not asked again. API side: `server/plugins/addresses.ts`, `server/services/addressSearch.ts`. Rules to keep: session required, and the browser never calls the map service itself; what is typed travels in a POST body, never a URL (traces also drop every query string, `server/instrumentation.ts`); both routes answer `enabled: false` and send nothing while `COMMUTE_TIMES` is off (the field is then a plain text field: the component stops asking for the page); what is typed is never logged, cached or stored; searches have their own limits (60 a minute and 500 a UTC day per account, 10,000 a UTC day for the site), not `COMMUTE_DAILY_LIMIT`, and their counters are keyed by a hash of the account (`rateLimitKey`); an office lookup goes through the commute's cache and daily cap like at scoring (`locateOffice`), at most 40 new lookups per account and UTC day (a street not found takes two); suggestions carry no coordinates. `server/tests/addressSearch.test.ts` fakes the geocoder; the e2e tests answer both routes in the browser (`client/tests/support/addresses.ts`).

**Step suggestions.** Under the step types, the owner's editor shows "Missing a step? Suggest a step" (`client/src/lib/components/admin/StepSuggestion.svelte`, helpers in `client/src/services/stepSuggestion.ts`) when `GET /workflow/step-suggestions` says `enabled`: a form (name, what a recruiter would do, why it would help) that `POST /workflow/step-suggestions` files as an issue labelled `enhancement` in `GITHUB_ISSUES_REPO`, with the operator's `GITHUB_ISSUES_TOKEN` (feature off without it: `enabled: false`, `POST` 404). Logic in `server/services/stepSuggestions.ts`: portfolio owners only (403), portfolio-common's `parseStepSuggestion` (422 naming `name`, `description` or `reason`), 3 per owner and 20 for the site per UTC day (`RateLimitCounter`s, 429 with `Retry-After`), then one `fetch` to `api.github.com` (10 s, `redirect: 'manual'`: never followed); a refusal by GitHub (a redirect included) → 503 and the suggestion is given back, no answer → 503 and it still counts; the requests sent to GitHub are capped too (10 per owner per UTC day, never given back), so a refusing GitHub cannot be retried in a loop. Rules to keep: the owner's text is untrusted and public on GitHub, so it only ever goes inside fenced code blocks whose fence is longer than any run of backticks in it (nothing in it mentions, links or renders), nothing invisible is filed (portfolio-common's `cleanStepSuggestionText`: controls, every `Default_Ignorable_Code_Point` such as zero-width, bidi and tag characters, lone surrogates; the rules are checked on what is left), the title cannot mention or reference (`@ name`, `# 12`, `GH- 12`), and the issue names nobody (the user id and issue number are in the API's log only); the token never reaches a response or a log line (`tests/stepSuggestions.test.ts` fails if it does). The form never signs the page out on a 401 (the journey editor around it would lose its unsaved steps): it says so and keeps the text. The e2e test answers the two routes in the browser: GitHub is never called.

### Feedback
"Send feedback" lets any signed-in account (candidate, recruiter or neither; no portfolio needed) report a bug or share an idea, filed as a GitHub issue. Entry points, shown only signed in and while `GET /feedback` says `enabled`: the account menu's "Send feedback" (`AccountMenu.svelte`) and a small text button in the footer of every page (`client/src/lib/components/feedback/FeedbackButton.svelte`, in `LegalFooter` and in the `(app)` and `[domain]` footers next to the compact `LegalLinks`); no floating button (a portfolio already has its floating corner). Both open one dialog per page, `client/src/lib/components/feedback/FeedbackDialog.svelte`, mounted by `Header.svelte` (it says the text is published on GitHub and links to `/legal/privacy#data-feedback`); shared state and calls in `client/src/services/feedback.ts`. French: « Donner votre avis », the noun is « avis » (`docs/I18N.md`). API: `server/plugins/feedback.ts`: public `GET /feedback` → `{ enabled, classifies }` (`enabled`: `GITHUB_ISSUES_TOKEN` is set; `classifies`: `ANTHROPIC_API_KEY` is set), `POST /feedback` (session) `{ message, context?: { route?, viewport?, theme? } }` → `{ created: true, kind, classified, issueUrl? }` (`issueUrl` only when GitHub's `html_url` is exactly `https://github.com/<GITHUB_ISSUES_REPO>/issues/<number>`); 404 while off, 422 on `message` (portfolio-common's `parseFeedback`; the context is checked by `parseFeedbackContext`, which drops what breaks a rule and never refuses), 429 with `Retry-After`, 503 when GitHub did not take it. Logic in `server/services/feedback.ts`; the GitHub plumbing it shares with the step suggestions (`fenced`, `issueTitleText`, the request itself: 10 s, `redirect: 'manual'`, the token never logged) in `server/services/githubIssues.ts`; the browser's description in `server/services/userAgent.ts` (`describeBrowser`). **Classification**: Claude Haiku 5.5 (`claude-haiku-5-5`, `createClaudeClient` of `claudePdfExtraction.ts`) sorts the text into `bug`|`feature`|`task` and writes a short neutral English title and summary; the issue gets the repository's issue type (`FEEDBACK_ISSUE_TYPES`: `Bug`, `Feature`, `Task`; when GitHub refuses the type, filed again once with the label `bug`, `enhancement` or `task`: `FEEDBACK_KIND_LABELS`) and the label `feedback`. Without the key, or when Claude fails, refuses, answers junk or times out, it is still filed, as a `Task` titled with the first words of the message, and the body says it was not classified (`classified: false`). Rules to keep: the issue names nobody (no name, email, user id or portfolio address: the user id, the issue number and its kind are in the API's log only); what the person wrote and what Claude derived from it are untrusted and public, so the body has them only inside fenced code blocks longer than any backtick run in them, the title goes through `issueTitleText`, nothing invisible is filed (`cleanIssueText`); the page is its SvelteKit route id (`/[domain]/experiences`, never the real path: `isFeedbackRoute` takes only ids under `/(site)`, `/(app)` or `/[domain]`), the browser and OS come from the closed lists of `userAgent.ts` (family and major version, "Firefox 132 on Windows", never the raw User-Agent), the language is the request's, then the viewport size and the theme. Limits (UTC-day `RateLimitCounter`s, keys from `rateLimitKey`, an HMAC of the user id): 5 per account and 30 for the site, and 10 GitHub-bound attempts per account, never given back (the request filed again without a type takes one too, and is sent only after a 422 that does not name another field); GitHub refusing → 503 and given back to the first two, no answer → 503 and it counts (as for step suggestions); 60 classifications for the site (`FEEDBACK_CLASSIFICATIONS_PER_DAY`), taken when Claude is called and never given back, then filed without one. Claude has 8 s and GitHub 12 s for both its requests (`feedbackTimeouts`): the whole request stays under the 30 s idle timeout Elysia sets on Bun's server (which Bun does not apply to a request with a body, see "Résumé import quotas and limits": keep the budget all the same). `issueTitleText` also breaks `://`, so a title holds no link. Feedback stores nothing in the database. The privacy policy covers it (`#data-feedback`, Anthropic and GitHub as recipients): a change to what is filed or sent means updating both languages (and `LEGAL_VERSION`). The e2e test `client/tests/feedback.test.ts` answers `/feedback` in the browser: neither GitHub nor Claude is called.

### Authentication Flow
Google OAuth 2.0 → server verifies token → upserts user in MongoDB → records the age and terms confirmation when the body has `consent` (see "Legal pages, consent and account deletion") → issues JWT (7-day, httpOnly cookie). Client tracks auth state via `svelte-persisted-store`. Protected server routes use the `userLogged` Elysia plugin middleware.

### Recruiter space
One Google account can be a candidate (it owns a portfolio domain) and/or a recruiter (job postings); the spaces, labels and plans are `common/models/account.ts`. The recruiter space is free and created by the first `PUT /me/mode` to `recruiter` (or `POST /login` with that mode), once the account accepted the terms in force, and its routes need them too (see "Legal pages, consent and account deletion"); `activeMode` only decides what the client shows (the account menu, `client/src/lib/components/AccountMenu.svelte`, and the space chooser after login, which both lead to `/recruiter`, the page that creates the space), the API authorises on what the account has. Client pages live under `client/src/routes/(app)/`: `/recruiter` (private, rendered in the browser only: signed out, `components/recruiter/RecruiterLanding.svelte` (the age and terms box first, then Google's button: see above), which sells what a portfolio shows of a skill, the projects it was used in and for how long; keep it to what the code does: there is no search of portfolios, by skill or otherwise (a recruiter opens the portfolio a candidate shared), and a job is shared on a Hire page only when the candidate's journey has a job step; signed in, the dashboard: first the meetings the account booked on candidates' Hire pages (`components/recruiter/UpcomingMeetings.svelte`, helpers in `client/src/services/bookedMeetings.ts`; `GET /appointments/booked`, `server/services/bookedMeetings.ts`: only bookings made signed in, the soonest 20, each checked with the owner's calendar so one deleted or moved in Google Calendar is dropped like `dropIfStale` drops it, answered from the booking when Google cannot be asked or over 60 checks an hour per account; never the owner's account, calendar or event; a Join link only for `https://meet.google.com/`), then the job descriptions, `/recruiter/jobs/new`, `/recruiter/jobs/:id` (the posting and its status: no public page, no applicants), `/recruiter/jobs/:id/edit` with `client/src/lib/components/job-editor/JobEditor.svelte`). There is no job board and no applying: a job description is never public, its recruiter shows it to a candidate by picking it on the candidate's Hire page (the job step; only an `open` posting can be picked, `OPEN_JOB_STATUS` of portfolio-common), the candidate then reads it on its private page (`/opportunities/:id`, linked from the meeting invitation), and `/jobs` answers 410. Rules the API keeps: a posting's DTO never names the recruiter; `PUT /jobs/:id` with the `updatedAt` the editor loaded answers 409 when the posting changed since (the editor sends it). Job descriptions are Markdown rendered without raw HTML (`Markdown.svelte` with `html={false}`), and the job import removes HTML from the drafts.

### Résumé import quotas and limits
Billed to the operator's `ANTHROPIC_API_KEY` (feature off without it, `GET /experiences/import` then says `enabled: false` and `POST` answers 404). Per user: `RESUME_IMPORT_MONTHLY_LIMIT` imports per 30-day window; whole site: `RESUME_IMPORT_DAILY_LIMIT` per UTC day; per user: `RESUME_IMPORT_ATTEMPTS_PER_DAY` attempts per UTC day (never given back); all `RateLimitCounter`s, taken after the file checks (base64, 4 MB → 413, `%PDF-`) and before a free `countTokens` pre-check (over 60,000 input tokens → 422). Over a limit → 429 with `Retry-After`. The paid call is streamed (`messages.stream(...).finalMessage()`), sent once (`maxRetries: 0`) with a 3-minute deadline (`resumeImportTimeouts`). The API sends nothing meanwhile: Bun's 30 s `idleTimeout` (Elysia's default) does not cut it because Bun 1.4.4 does not apply that timer while it handles a request with a body (only body-less requests are cut), which `tests/resumeImport.test.ts` ("over a real connection", a real socket with a 1 s `idleTimeout`) pins; Railway's edge allows 5 minutes without data (`docs/DEPLOYMENT.md`, "Silent connections"). Never give an import back once the paid request may have run the model: it counts once sent (drafts; refusal or `max_tokens` → 422; deadline, lost connection or an error event in the stream → 503 "did not finish"), and only failures before it or an HTTP error status from Anthropic (429/5xx/529, 400/401/403/404: not billed → 503) are given back (`refundRateLimit`). A count_tokens 400 is an operator problem (503, logged at error with the masked API message), not the user's PDF. The SDK client is built with `logLevel: 'warn'` and `openTelemetry: { traces: { contentMode: 'metadata_only' } }` so neither the PDF nor the extracted data reaches logs or spans; `tests/resumeImport.test.ts` fails if the key or the PDF appears in any response or log line. Request bodies: Bun caps them at 6 MB (`app.ts`); every route but the PDF imports (`POST /experiences/import`, `POST /jobs/import`) is capped at 1 MB (413), by `Content-Length` in `onRequest` and by the bytes actually read in a global `onParse` (chunked or repeated-`Content-Length` bodies); a PDF import without a valid session JWT gets 401 in `onRequest`, before its body is read. Traces: `RedactingSpanProcessor` (`instrumentation.ts`) drops bodies, cookies, `Authorization` and query strings (`url.query`, and the query of `url.full`) as spans end, before the `BatchSpanProcessor` queue (the exporter redacts again).

### Metrics and Grafana dashboards
With telemetry on, the API exports two metrics of its own every minute: the request counter and duration histogram of `server/app.ts` (`http.server.requests`, `http.server.request.duration`; attributes `method`, `route`: the matched route pattern, never the raw path, and `status`: the status of the answer, `responseStatus`), and `portfolio.records` (`server/services/siteMetrics.ts`, registered by `index.ts`): one gauge with a `kind` attribute (`SITE_RECORD_KINDS`: portfolios, accounts, recruiters, experiences, job postings, open job postings, journeys started, upcoming bookings), read from MongoDB at most every 5 minutes, only when metrics are exported, and reporting nothing while MongoDB is away. Counts only: a metric attribute must stay a small fixed set (never a portfolio name, a user id or a path: each value is a series kept in memory and billed). The three Grafana dashboards that read them, with the logs and traces, are in `docs/grafana/` (JSON exported from the stack's Portfolio folder, and what each panel reads: `docs/grafana/README.md`): a new record kind or a renamed route, metric or `OTEL_SERVICE_NAME` means updating them. The site counts no views in the browser: the privacy and cookies pages say "no analytics", so a view counter would change them (and `LEGAL_VERSION`).

### Database Models
Mongoose schemas in `server/models/database/`. Key entities: Domain, User, Experience, Company, Project, Skill, Workflow (an owner's hiring journey: its ordered `steps`, each `{ id, type, config }` as portfolio-common's `parseWorkflow` returned it, `type` without an enum (the registries validate it) and `config` a `Mixed` kept even when `{}`; unique on `user`, collection `hiringworkflows`; the old `workflows` collection is no longer read), WorkflowInstance (a visitor's progress in an owner's journey: `steps`, a map from step id to `{ data, updatedAt }`, what each step's type stored for this visitor; created by the visitor's first submit; unique on `(owner, visitor)`), AppointmentSchedule, AppointmentBooking (slot reservations of `POST /appointments/book`, unique on `(schedule, start)`, released on cancellation, removed by a TTL index once the slot ends; `visitor`: the account that booked signed in, never the owner, unset when that account is deleted; `meetLink`: the event's Google Meet link; logic in `server/services/appointmentBookings.ts`), RateLimitCounter (Mongo fixed-window counters of `server/services/rateLimit.ts`: booking and availability rate limits, résumé and job import quotas, step suggestions, feedback; `takeRateLimit` / `refundRateLimit` / `peekRateLimit`), CommuteCache (what the travel time services answered, `server/services/commute.ts`: `_id` is the kind of answer and an HMAC of the question, `value`, `expiresAt` with a TTL index), PerfectJob (an owner's perfect job: `criteria`, a `Mixed` holding what portfolio-common's `parsePerfectJob` returned, read again through `storedPerfectJob`, which leaves out a criterion that is not one anymore; unique on `user`), JobPosting (a recruiter's job description, never public: the fields of portfolio-common's `JobPostingInput`, normalised and validated there, `publishedAt` the first time it leaves draft). The `jobapplications` collection of the removed job board is no longer read or written, except by account deletion, which removes the account's own documents from it until it is dropped (after the deploy, `docs/DEPLOYMENT.md`). The User's `activeMode` (`candidate`|`recruiter`, unset until chosen) and `recruiter` space (`enabledAt`, `plan`, `jobImportsUsed`, created by `enableRecruiterSpace` of `server/services/recruiters.ts`). The User's `legalAcceptances` (unset until the first): append-only history of the terms accepted, `{ version, acceptedAt, ageConfirmationKey, source }` (`source` one of `CONSENT_SOURCES`), written only by `recordConsent` of `server/services/legal.ts`. The User's Google Calendar OAuth tokens (`googleCalendar.refreshToken` / `accessToken`) are `select: false`: only `services/googleCalendar.ts` loads them (`.select('+googleCalendar.refreshToken')`), and `tests/appointments.test.ts` fails if any API response contains one. Every Calendar call goes through `callGoogle` there: a grant Google refuses (`invalid_grant`, `unauthorized_client`, Calendar 401) is cleared (`googleCalendar.revokedAt` set) and becomes a 409 `GoogleCalendarReconnectRequiredError`, not a 500. Disconnecting the calendar, a refused grant and account deletion revoke the grant at Google with `revokeGoogleToken` there (`POST https://oauth2.googleapis.com/revoke`, the token in the form body, never the URL, 5 s, `redirect: 'manual'`, never throws, never logs the token). Elysia request validation schemas use TypeBox in `server/models/elysia/`.

## Deployment

Two stages, each two services from the repo root: **staging** deploys every push to `develop` (`develop.portfolio.gentil.tech`, `develop.api.portfolio.gentil.tech`), **production** every push to `main` (`portfolio.gentil.tech`, `api.portfolio.gentil.tech`). `main` only receives `develop` through a release pull request (base `main`, compare `develop`, titled with the new version: `Release v1.2.0`), merged with **Create a merge commit** so `main` keeps `develop`'s history and the next release merges cleanly; `main` has no commits of its own. Both branches are protected by the rulesets in `.github/rulesets/` (applied on GitHub by importing them: pull request required, required CI checks, no force-push or deletion; squash only into `develop`, merge commit only into `main`; a PR into `develop` must be up to date with it, which `main` cannot require of a release): renaming a CI job means updating them. All services are built with **Railpack** (it reads Bun 1.4.4 from `packageManager` and runs `bun install --frozen-lockfile`): API (start `bun run start:server`, healthcheck `/health`) and web (build `bun run build:client`, start `bun run start:client`, healthcheck `/healthz`). Settings live in the Railway dashboard; there is intentionally no `railway.json` (Config as Code is deprecated and stops being read on 2026-12-01) and no `nixpacks.toml`. Full runbook: `docs/DEPLOYMENT.md`.

Live layout (verified 2026-11-15): Railway project `personal-api`, environment `production` (holding both stages): production web `portfolio web` and API `portfolio api` (branch `main`), staging web `portfolio` and API `portfolio api develop` (branch `develop`), and `MongoDB` (`mongo:7` with a volume), shared by both stages with one database each (production's holds the real data). Each stage has its own `JWT_SECRET`, `ALLOWED_DOMAINS` and `PUBLIC_PORTFOLIO_API_URL`. All app services use the Railpack builder and Root Directory `/` (see the runbook for the full settings).

CI (`.github/workflows/main.yml`) runs on push/PR to `develop` and `main`: quality (lint, svelte-check, server tsc, client build), tests (server + client unit against MongoDB 7, like production, and 9) and Playwright e2e; `.github/workflows/release-guard.yml` ("Only develop merges into main": the source branch, and the next semantic version in the title, one step after the latest `vX.Y.Z` tag) on PRs to `main`; `.github/workflows/release.yml` makes a release when run by hand (`workflow_dispatch`, with patch, minor or major): it opens the release PR from `develop` into `main`, titled with the next version, with auto-merge on (it needs the repository secret `RELEASE_TOKEN`, a maintainer's token: the CI of a pull request opened with the workflow's own token waits for someone to approve it, and a merge made with it starts neither the publication nor the CI on `main` that the production deploy waits for; it only ever asks for auto-merge, never a plain merge, which an admin's token would be let through before the checks), and when a release PR is merged, opened by it or by hand, it publishes the GitHub Release (tag `vX.Y.Z` on the merge commit, generated notes). Its "Tag only" input merges nothing: it publishes `main`'s current commit, for a release merged without its tag. The `develop` branch is the main development branch and the default branch.

## Cloud sessions

Claude Code cloud sessions run in a container without Docker. The cloud environment `portfolio` (Claude Code's environment settings, not this repo) has a setup script that runs before each new session: it installs `mongod` (MongoDB 7, from MongoDB's Ubuntu 22.04 apt repository: 7.0 has no 24.04 one, and the 22.04 package installs), runs `bun install`, copies each `.env.example` missing its `.env`, installs the Chromium of the project's Playwright version (the image's is older) and seeds the database once (`db:seed`, `seed:e2e`), leaving `mongod` stopped. In a session, `bun run db:up` starts that `mongod` in about a second (`scripts/db.ts`: without a Docker daemon it runs `mongod --fork` on 127.0.0.1, data in the gitignored `.mongo/`), then `bun run dev`, the server tests or the e2e flow work as described above. Change the script in the environment's settings when the setup changes (a new seed, another MongoDB version).

## Claude Code Setup (new device)

Everything portable is committed to the repo:
- **CLAUDE.md** (this file) — project instructions
- **.mcp.json** — project MCP servers (railway, github, context7, svelte, chrome-devtools), auto-enabled via `.claude/settings.json`
- **.claude/settings.json** — shared permissions allowlist; local overrides go in `.claude/settings.local.json` (gitignored)
- **.claude/launch.json** — dev server configs for the browser preview (client:5173, server:3000)
- **server/.env.example**, **client/.env.example** — templates for every env var (required ones preset for local dev)
- **compose.yaml** — local MongoDB (`bun run db:up`)

Manual steps on a new device:
1. Install Bun **1.4.4** (the `packageManager` version, see README) and Docker, then run `bun install` at the repo root.
2. Copy the `.env.example` files to `.env` (the defaults work locally; never commit `.env`), then `bun run db:up` and `bun run db:seed`.
3. Export `GITHUB_PERSONAL_ACCESS_TOKEN` in your shell profile — the github MCP server in `.mcp.json` (GitHub's hosted server at `api.githubcopilot.com/mcp/`) sends it as a Bearer token.
4. Install the Railway CLI (`bun add -g --trust @railway/cli`, or `scoop install railway` on Windows, `brew install railway` on macOS) and run `railway login` — the railway MCP server in `.mcp.json` is `railway mcp`, which proxies to Railway's hosted MCP with the CLI's credentials.
5. The other MCP servers (context7, svelte, chrome-devtools) run through `bunx` with pinned major versions; nothing to install.
6. claude.ai connectors (Gmail, Calendar, Railway, etc.) are tied to the Anthropic account, not the repo — re-authorize them in claude.ai connector settings or via `/mcp` in an interactive session if needed.
7. Install Graphify (see below) — the skill files in `.claude/skills/graphify/` are committed, but the CLI must be installed per device.

## Graphify (knowledge graph)

[Graphify](https://github.com/Graphify-Labs/graphify) builds a queryable knowledge graph of the repo (code via local tree-sitter AST parsing, docs via a semantic pass) exposed as a `/graphify` skill in Claude Code.

**Install on a new device** (the CLI is machine-level, the skill is committed):

```bash
winget install astral-sh.uv        # Windows; Mac: brew install uv
uv tool install graphifyy          # NOTE: package is 'graphifyy' (double y) — other graphify* packages on PyPI are typosquats
graphify install --project         # registers the skill into .claude/skills/graphify/ (committed to this repo)
```

**Usage:** type `/graphify .` in Claude Code to (re)build the graph, then prefer `graphify query "<question>"`, `graphify path A B` and `graphify explain "<concept>"` over grepping when exploring the codebase.

**Outputs** land in `graphify-out/` (graph.html, graph.json, GRAPH_REPORT.md) — gitignored, regenerate locally with `/graphify .`.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
